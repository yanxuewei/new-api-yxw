# 压测瓶颈分析（雅加达 dev，2026-10-26）

## 结论摘要

1. **“扩到 2 副本 RPS 没有明显提升”不是副本没生效，而是共享数据库写路径先饱和。**
   2 副本的网关 CPU 只有约 0.8 核/副本（上限 2 核），远未打满；增加副本只是把更多并发压到同一批数据库热行上。
2. 主要瓶颈按影响排序：
   - 每请求同步写消费日志 `INSERT INTO "logs"`（`model/log.go` `RecordLog`）。
   - 同一用户的额度/请求数热行更新 `UPDATE "users" ... WHERE id=2`（所有压测请求共用一个用户）。
   - 每请求 `SELECT count(*) FROM "user_subscriptions" WHERE user_id=...`。
3. **关闭消费日志后，2 副本重新表现出扩容效果**：1450 VU 从 645.7 req/s / P95 712ms 提升到约 736 req/s / 615–635ms；1550 VU 由失败转通过；1650 VU 通过（804.8 req/s / 796ms）；1750 VU 才失败。
4. 公网路径扩到 2 副本没有收益（最优档反而从 1450 退到 1350），更像入口/EIP 边界，和数据库瓶颈是两件事。
5. **已在 `new-api-perf` 落地 4 项优化**（批量更新、关闭消费日志、索引确认、多用户压测）：1450 VU 由 645.7 req/s / 712ms 提升到 736.3 / 623ms；1550 VU 由失败转为通过；1650 VU 处于 796–817ms 的边界。详见文末“十一”。

## 三、对照实验：客户端与上游都不是瓶颈

| 实验 | 结果 |
|---|---|
| 同客户端直连 mock（绕过网关，1450 VU） | **763.9 req/s，P95 425ms**，mock 每副本 CPU 约 60–80m |
| 经网关（2 副本，1450 VU） | 645.7 req/s，P95 712ms |
| k6 单 Job CPU（1450 VU） | 约 1.1 核（上限 2 核） |
| 网关 CPU（2 副本，1450 VU） | 合计约 1.6 核，单 Pod 峰值约 830m |

结论：客户端能跑到 764 req/s，mock 处理同样请求仅用少量 CPU；差值是网关链路引入的。

## 四、根因证据

### 4.1 goroutine 栈（pprof，1450 VU / 2 副本，测试中抓取）

每副本约 3000–3400 goroutine，按首帧聚合：

| 首帧 | Pod A | Pod B | 说明 |
|---|---:|---:|---|
| `internal/poll.runtime_pollWait` | 682 | 748 | 等网络可读（正常流式） |
| `net/http.(*persistConn).writeLoop` | 645 | 713 | 空闲 keep-alive 写循环 |
| `relay/helper.StreamScannerHandler` | 471 | 598 | 流式扫描（正常业务） |
| `net/http.(*persistConn).readLoop` | 471 | 598 | 读上游响应 |
| `net/http.(*persistConn).roundTrip` | 174 | 57 | 等上游响应 |
| **`database/sql.(*DB).conn`** | **53** | **30** | **等数据库连接** |
| **`database/sql.(*Tx).awaitDone`** | **29** | **19** | **等事务结束** |

没有大面积互斥锁；但数据库中确实存在排队。

### 4.2 慢 SQL（阈值 200ms）

默认配置下 30 分钟出现 **23,039 条慢 SQL**。开启批量更新后 10 分钟仍有 **12,895 条**，分布：

| 来源 | 条数 | 语句 |
|---|---:|---|
| `model/log.go:103` | 8,668 | `INSERT INTO "logs" (...)`（每请求同步写消费日志） |
| `model/subscription.go:873` | 4,218 | `SELECT count(*) FROM "user_subscriptions" WHERE user_id=$1 AND status=$2 AND end_time>$3` |
| `model/channel.go:924` | 3 | `UPDATE "channels" SET used_quota=... WHERE id=$2` |
| `model/user.go:516` | 2 | 用户查询 |

典型热行更新（批量更新关闭时）：

```sql
UPDATE "users" SET "request_count"=request_count + $1,
                   "used_quota"=used_quota + $2
WHERE id = $3 AND "users"."deleted_at" IS NULL
-- 实测单条 220–318ms
```

所有压测请求共用 `user_id=2`、`channel_id=3`，因此这些写操作在数据库侧被行锁串行化；副本越多，争用越大。

## 五、干预验证

| 配置 | 1450 VU | 1550 VU | 1650 VU | 1750 VU |
|---|---|---|---|---|
| 默认（日志开 / 批量更新关） | 645.7 req/s / 712ms | 646.4 / 887ms FAIL | — | — |
| 仅开 `BATCH_UPDATE_ENABLED=true` | 641.0 / 834ms | — | — | — |
| 关闭消费日志（`LogConsumeEnabled=false`） | **735.5 / 635ms**、**736.2 / 614ms** | **776.8 / 665ms** | **804.8 / 796ms** | 834.7 / 882ms FAIL |

要点：

- 开启批量更新后 `UPDATE users` 从慢日志消失，但性能几乎不变 → 说明消费日志 INSERT 与订阅计数影响更大。
- 关闭消费日志后，2 副本在 1650 VU 仍能通过（P95 796ms，已接近边界），说明网关本身具备更高吞吐，之前测到的是数据库写上限。
- 1650 → 1750 是新的破线区间。

---

## 六、为什么扩副本没有提升 RPS

1. 每请求固定成本中，数据库写入（日志 INSERT、额度更新、订阅计数）占比较高。
2. 单用户/单渠道导致热行锁：并发越高，单条 UPDATE 排队越久，抵消了副本带来的并行度。
3. 网关 CPU 与 mock CPU 都远未饱和，客户端也能跑到 764 req/s，因此不是算力问题。
4. 在 constant-VU 模型下，吞吐 = 并发 ÷ 单请求耗时；DB 排队把单请求耗时抬高，吞吐自然上不去。

---

## 七、公网路径的额外问题

公网 2 副本最优档（1350 VU）反而低于 1 副本（1450 VU），且 1450 VU 即破线。这与数据库瓶颈无关，更可能是 NAT/EIP/ALB 入口边界或运行波动；需要用 EIP 实际监控确认，不能仅凭本次数据下结论。

## 八、建议

### 8.1 压测配置（测网关真实容量时）

1. 开启 `BATCH_UPDATE_ENABLED=true`（默认 5s 合并），避免额度/请求数热行锁。
2. 关闭或异步化消费日志（`LogConsumeEnabled=false`，或把 `LOG_DB` 指向 ClickHouse/独立库）。
3. 确认 `user_subscriptions` 查询有可用索引（`user_id, status, end_time`），或对订阅状态做缓存。
4. 使用多用户/多 token（例如每 50 VU 一个）复测，量化热键影响；单用户结果应标注为最坏场景。

### 8.2 产品侧优化

- 消费日志改为批量/异步写入，避免请求路径同步 `INSERT`。
- 额度与请求数继续使用批量更新，并评估合并周期。
- 订阅计数改为缓存或增量维护，避免每请求 `count(*)`。
- 需要区分“网关容量”和“数据库写入容量”两个指标，避免用单一 RPS 判断扩容收益。

## 十一、perf 环境已实施的优化（2026-10-26）

### 11.1 落地内容

| # | 措施 | 落地方式 | 状态 |
|---|---|---|---|
| 1 | 开启批量更新 | `BATCH_UPDATE_ENABLED=true` 写入 `perf-master-slave.yaml` 并 `kubectl set env`，滚动完成 | 已生效 |
| 2 | 关闭消费日志 | 管理接口 `PUT /api/option/` 设置 `LogConsumeEnabled=false`（写入数据库，重启保留） | 已生效 |
| 3 | 订阅查询索引 | 检查发现已存在 `idx_user_sub_active (user_id, status, end_time)`，无需新建 | 已确认 |
| 4 | 多用户/多 token | 创建 30 个 `perfmulti01..30` 用户（各 1 个令牌），令牌列表写入 Secret `perf-load-test-credentials/tokens`；`sse.js` 按 VU 轮转令牌，日志记录 `token_mode` 并参与容量分组 | 已启用 |

> 用户密码为测试固定值；令牌只存于 Secret，不落日志。第 4 项用于量化热键影响，单用户结果仍标注为最坏场景。

### 11.2 复测结果

| 场景 | 优化前（默认配置） | 优化后 |
|---|---|---|
| 1450 VU（2 副本） | 645.7 req/s / P95 712ms | 735.5 / 635ms（单用户）、736.3 / 623ms（多用户） |
| 1550 VU（2 副本） | 646.4 / 887ms FAIL | 776.8 / 665ms PASS（单用户） |
| 1650 VU（2 副本） | — | 804.8 / 796ms PASS（单用户，边界）、802.6 / 817ms FAIL（多用户，边界） |
| 1750 VU（2 副本） | — | 834.7 / 882ms FAIL |

- 1450 VU 吞吐提升约 14%，P95 下降约 90ms。
- 单用户与多用户结果几乎一致（736.3 vs 735.5），说明批量更新已经消除了用户热行锁；当前瓶颈转移到 token 查询与日志/INFO 输出。
- 1650 VU 处于 SLO 边界，不宜作为稳定通过档。

### 11.3 优化后慢 SQL 变化

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 慢 SQL（折算 15 分钟） | 约 11,500 条 | 709 条 |
| `INSERT INTO "logs"` | 8,668 条 / 10 分钟 | 0（消费日志关闭） |
| 剩余热点 | — | `SELECT * FROM "tokens" WHERE "key"=$1` 588 条；用户查询 65 条；订阅计数 56 条 |

日志总量仍约 374,683 行/15 分钟（INFO 级），写入压力未完全消除。

### 11.4 结论与后续

- 4 项措施已使网关在 2 副本下稳定通过 1550 VU，1450 VU 的 P95 降至 623–635ms。
- 1650 VU 仅处于边界，建议容量记录不超过 1550 VU（2 副本、内网）。
- 剩余可优化点：token 校验走内存缓存（`MEMORY_CACHE_ENABLED`）、降低 INFO 日志量、消费日志改异步/独立库。
- 公网路径仍未从 2 副本获益，需要 EIP/入口侧监控单独分析。
