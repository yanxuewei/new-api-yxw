## 一、「16 副本 × 300 连接打爆 PG」中 16 的出处

**16 = stable Deployment 的 HPA `maxReplicas` 上限**（`impl_deploy.md` §7.4.2）：

```yaml
minReplicas: 4        # 常态 4 副本，跨 2 AZ（单 AZ 故障仍有 2）
maxReplicas: 16       # ← 出处
metrics:
  - CPU 利用率 55%
  - newapi_active_connections 均值 1200
```

连接数预算必须按**扩容上限**算，不是常态副本：

```
300（SQL_MAX_OPEN_CONNS）× 16（HPA 上限）= 4800 条
16C64G RDS PG max_connections ≈ 800（I-3 按 800×0.8=640 收口）→ 必须加 PgBouncer/RDS 代理
```

⚠ 修正提醒（指南 P1-21）：代码默认值是 **1000** 不是 300（`model/main.go:212`）。若不显式设 env，最坏 `1000×16=16000`。指南 §3.10（G11）已把「`SQL_MAX_OPEN_CONNS` 已显式设置」列为上线硬项。

## 二、g8i 节点加入后，app 单 Pod 资源配置

§7.4.2 容器声明：

```yaml
resources:
  requests: { cpu: "2", memory: 2Gi, ephemeral-storage: 20Gi }
  limits:   { cpu: "4", memory: 4Gi }    # 内存 limit 必设，配合 GC 与过载保护
```

| | CPU | 内存 |
|---|---|---|
| Pod requests（调度依据） | 2 核 | 2 Gi |
| Pod limits（运行上限） | 4 核 | 4 Gi |
| 节点 g8i.2xlarge | 8 核 | 32 Gi |

- 按 requests 调度，单节点最多放 **4 个 app Pod**（8÷2）；
- 常态 4 节点 × 4 副本 = 16，正好对齐 HPA 上限；节点池自动伸缩 4→8 台为突发留余量（§7.2：节点池不开自动伸缩，HPA 扩到上限会因无节点而 Pending）。

## 三、`*.likha.com` 通配符证书能否覆盖 `www.likha.com` / `likha.com`？

| 域名 | 覆盖？ | 说明 |
|---|---|---|
| `www.likha.com`（及 api/ops/static） | ✅ | 通配符匹配**一级**子域 |
| `likha.com` 裸域 | ✅（赠送，见下） | 通配符本身按 x.509 规则不匹配裸域，但阿里云各品牌签发时**自动把主域名加进 SAN** |
| `a.b.likha.com` 二级 | ❌ | 通配符只吃掉一个 label（指南 §9.8 坑 2，域名规划统一二级） |

## 四、把 `likha.com` 加进 SAN 会涨价吗？不加的副作用？

**价格：不变。** 国际站选型指南原文：「绑定通配符域名，**自动赠送对应的主域名**」，DigiCert / GeoTrust / GlobalSign / Rapid 各品牌统一，零加价。真正会变贵的只有：追加**不相关域名**（走证书合并/多域名，按个数计费）——本方案用不到。

因此指南 §3.7 的"证书加 likha.com SAN"落地动作 = **签发后验证赠送生效**（并入 G5 验证）：

```bash
aliyun cas DescribeUserCertificateDetail --CertId ${CERT_ID} | jq -r '.Sans'
# 期望同时含：DNS:*.likha.com, DNS:likha.com
# 若个别订单未带（CA 政策会变，以签发结果为准）→ 提工单补或走合并签发
```

**若证书真不含裸域，副作用：**

1. 用户访问 `https://likha.com` → TLS 握手阶段 SAN 不匹配 → `NET::ERR_CERT_COMMON_NAME_INVALID` 全屏警告；
2. **301 救不了裸域 HTTPS**：重定向是握手成功后应用层才返回的，握手失败请求根本到不了 ALB；只有 `http://:80` 明文 301 能工作，但浏览器默认先试 HTTPS + 全站 HSTS，该兜底不可靠；
3. 实际影响面有限：业务入口是 `api.likha.com`（覆盖 ✅），裸域非服务入口，副作用集中在品牌跳转与用户手敲体验，不影响 SLA 链路。
