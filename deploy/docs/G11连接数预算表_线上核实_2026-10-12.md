### 2.3 I-2（服务端侧 → RDS，约束 ≤ 640）

**`pool_mode = session` 实况下**——池中 server 连接数**仍受 `default_pool_size` 每池封顶**（PgBouncer 语义：`default_pool_size` 是每 `(user, db)` 对的 server 连接上限，**与 pool_mode 无关**；session 与 transaction 的差别在 client **何时归还** server 连接，不在总数）：

| 来源 | 走池 | `(user, db)` 池 | 预算 |
|---|---|---|---|
| mnl stable + canary（内网串 6432） | 是 | `(newapi, newapi)` | ≤ **50** |
| sg 备站（公网串 6432，裁定②乙路） | 是 | `(newapi_sg, newapi)` | ≤ **50** |
| master 迁移/运维（内网串 5432 直连，I-3 预留） | **否** | — | ≤ **100**（1 副本 × 100，实际按需） |
| 运维预留 | 否 | — | **20** |
| **合计** | | | **≤ 220** |
| 判定 | `220 ≤ 640` | | ✅ **成立，余量 420（66%）** |

> 📌 **本次核实纠正了任务卡的一处论断**：任务 41 卡写「session 模式下一条 client 独占一条 server，`default_pool_size=50` **不再是上限**」——**该表述不准确**。`default_pool_size` 在任何 pool_mode 下都是每池 server 连接数上限。session 模式的真实后果**不是**"服务端连接数失控"，而是 **"client 排队等 server"**（见 §2.4）。因此 I-2 在两种模式下**数值相同**，且都成立。

### 2.4 I-4（**本次新增** · session 模式特有：并发服务能力）

| 项 | 值 | 说明 |
|---|---|---|
| 池内 server 连接（并发上限） | **50**（mnl 主库池） | session 下 client 独占至断开 |
| 常态 client 数 | `4 × 100 = 400` | stable 4 副本 |
| 接管态 client 数 | `13 × 100 = 1300` | HPA 上限 |
| **并发供需比（接管态）** | **1300 : 50 = 26 : 1** | 即 96% 的 client 在队列中等待 |
| 等待超时 | `query_wait_timeout = 120s` | 等不到 ⇒ 连接报错 |
| 缓解因素 | `SQL_MAX_LIFETIME = 60s`（默认） | 连接每 60s 重建，周期性释放 |

**判读**：在**当前零负载**（`ConnectionUsage ≈ 2%`）下不可见；一旦进入真实 relay 流量或 HPA 扩容，会出现**查询排队 → P99 恶化 → 超时报错**，且**扩容副本不解决问题（反而加剧排队）**。

⇒ **`session` 是"兼容性安全、性能不安全"的兜底态**。按任务 41 步骤 3b，它是**小时级窗口态，不得作为稳态过夜**。

### 2.5 三不变量结论矩阵

| 不变量 | 约束 | session（实况） | transaction（文档口径） |
|---|---|---|---|
| **I-1** 客户端 | ≤ 2000 | ✅ 1600 | ✅ 1600（同） |
| **I-2** 服务端 | ≤ 640 | ✅ ≤220 | ✅ ≤220（同） |
| **I-3** 迁移旁路 | 5432 直连 | ✅ 实测 | ✅ |
| **I-4** 并发服务 | server 连接不被长期独占 | ⚠️ **不满足**（26:1 供不应求） | ✅ 满足（事务结束即归还） |

> **结论**：文档口径的三条不变量**全部成立**；但实况的 `session` 使**新增的 I-4 不成立**。**I-4 是本次核实暴露的真实缺口。**
