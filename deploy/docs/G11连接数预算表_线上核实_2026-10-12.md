### 2.3 I-2（服务端侧 → RDS，约束 ≤ 640）

**`pool_mode = session` 实况下**——池中 server 连接数**仍受 `default_pool_size` 每池封顶**（PgBouncer 语义：`default_pool_size` 是每 `(user, db)` 对的 server 连接上限，**与 pool_mode 无关**；session 与 transaction 的差别在 client **何时归还** server 连接，不在总数）：

| 来源 | 走池 | `(user, db)` 池 | 预算 |
|---|---|---|---|
| mnl stable + canary（内网串 6432） | 是 | `(newapi, newapi)` | ≤ **50** |
| sg 备站（公网串 6432，裁定②乙路） | 是 | `(newapi_sg, newapi)` | ≤ **50** |
| master 迁移/运维（内网串 5432 直连，I-3 预留） | **否** | — | ≤ **100**（1 副本 × 100，实际按需） |
| 运维预留 | 否 | — | **20** |
| **合计** | | | **≤ 220** |
| 判定 | `220 ≤ 640` | | ✅ **成立，余量 420（66%）** |

> 📌 **本次核实纠正了任务卡的一处论断**：任务 41 卡写「session 模式下一条 client 独占一条 server，`default_pool_size=50` **不再是上限**」——**该表述不准确**。`default_pool_size` 在任何 pool_mode 下都是每池 server 连接数上限。session 模式的真实后果**不是**"服务端连接数失控"，而是 **"client 排队等 server"**（见 §2.4）。因此 I-2 在两种模式下**数值相同**，且都成立。

### 2.4 I-4（**本次新增** · session 模式特有：并发服务能力）

| 项 | 值 | 说明 |
|---|---|---|
| 池内 server 连接（并发上限） | **50**（mnl 主库池） | session 下 client 独占至断开 |
| 常态 client 数 | `4 × 100 = 400` | stable 4 副本 |
| 接管态 client 数 | `13 × 100 = 1300` | HPA 上限 |
| **并发供需比（接管态）** | **1300 : 50 = 26 : 1** | 即 96% 的 client 在队列中等待 |
| 等待超时 | `query_wait_timeout = 120s` | 等不到 ⇒ 连接报错 |
| 缓解因素 | `SQL_MAX_LIFETIME = 60s`（默认） | 连接每 60s 重建，周期性释放 |

**判读**：在**当前零负载**（`ConnectionUsage ≈ 2%`）下不可见；一旦进入真实 relay 流量或 HPA 扩容，会出现**查询排队 → P99 恶化 → 超时报错**，且**扩容副本不解决问题（反而加剧排队）**。

⇒ **`session` 是"兼容性安全、性能不安全"的兜底态**。按任务 41 步骤 3b，它是**小时级窗口态，不得作为稳态过夜**。

### 2.5 三不变量结论矩阵

| 不变量 | 约束 | session（实况） | transaction（文档口径） |
|---|---|---|---|
| **I-1** 客户端 | ≤ 2000 | ✅ 1600 | ✅ 1600（同） |
| **I-2** 服务端 | ≤ 640 | ✅ ≤220 | ✅ ≤220（同） |
| **I-3** 迁移旁路 | 5432 直连 | ✅ 实测 | ✅ |
| **I-4** 并发服务 | server 连接不被长期独占 | ⚠️ **不满足**（26:1 供不应求） | ✅ 满足（事务结束即归还） |

> **结论**：文档口径的三条不变量**全部成立**；但实况的 `session` 使**新增的 I-4 不成立**。**I-4 是本次核实暴露的真实缺口。**

## §6 裁定落地与新增事项（2026-10-13）

### 6.1 `pool_mode` = `session`（维持）—— 风险登记

- **裁定**：先不切回 `transaction`，维持现网 `session`。
- **含义**：§2.4 的 **I-4 继续不成立** —— 接管态 `1300 client : 50 server = 26:1`，超出部分在 `query_wait_timeout=120s` 到点报错。
- **当前不可见**：RDS `ConnectionUsage ≈ 2%`（零负载）；风险在真实 relay 流量或 HPA 扩容时才显现。
- **复核触发（建议）**：① 进入真实流量压测前；② 任务 44 接管演练前；③ 任何 HPA 打到 `maxReplicas` 的时段。三者任一触发即重评是否热切 `transaction`。
- **安全侧事实**：`session` 对**兼容性**安全（应用侧已是 `PreferSimpleProtocol: true` + `PrepareStmt: false`，全仓无 session 级 advisory lock / `LISTEN`），仅对**并发服务能力**不友好。

### 6.2 ⛔ 备站 conns 覆盖 `10/5` 被删除 —— 判定：**不建议删，建议恢复**

**事实**：2026-10-13 10:56 HKT（RS `new-api-ph-standby-65c4b9576b`）备站 Deployment 的 `SQL_MAX_OPEN_CONNS=10` / `SQL_MAX_IDLE_CONNS=5` **两个 env 已被移除**，Pod 内实测已回落 **`100`/`50`**（来源 = ConfigMap `new-api-config`）。

**为什么这不该删**：

| 依据 | 说明 |
|---|---|
| ① 是**书面裁定** | `standby-deployment.yaml` 明文写「卡片裁定②（2026-09-29）… **覆盖** cm 里的 100/50」；指南 §任务 17/28/41 多处把 `10`/`5` 写成**验收期望值**（如任务 28 卡 `期望 10（IDLE 期望 5）`） |
| ② 是 **I-1 预算的组成部分** | §2.2 的 `20×10 = 200` 就是它。删后备站 worst-case `20×100 = 2000`，**I-1 合计 `1300 + 100 + 2000 = 3400 > 2000`** ⇒ 击穿 `pgbouncer.max_client_conn`，PgBouncer 直接拒连（`no more connections allowed`） |
| ③ 备站定位 | 备站是**低流量旁站**，不应长期占用主库连接位；`SQL_MAX_IDLE_CONNS` 由 5→50 意味着**每个备站 Pod 常驻 50 条空闲连接**（16 副本 = 800 条），把共享的 2000 client 预算吃掉一大块 |
| ④ 经池也拿不到额外吞吐 | 备站与主站**共用同一 PgBouncer**（实测 `SQL_DSN` = `…pub.pgsql.ap-southeast-6.rds.aliyuncs.com:6432`），其 `(newapi_sg, newapi)` 池 server 侧仍被 `default_pool_size=50` 封顶 ⇒ 把 client 槽位从 200 抬到 2000，**不增加任何服务能力**，只增加排队与挤占 |

**判定**：**不建议删除；建议恢复 `10`/`5`**（恢复命令见下）。若确有理由要保留 `100/50`，则必须**同时重算 I-1 并落地其一**：抬 `max_client_conn`（如 2000→4000，需评估 PgBouncer 内存）、或下调主站 `SQL_MAX_OPEN_CONNS`、或压低备站 HPA `maxReplicas`（使 `N×100 ≤ 2000 − 1400 = 600` ⇒ `N ≤ 6`，与"接管 20 副本"直接冲突）。

```bash
# 恢复（幂等；在集群内执行，或经 deploy/lib/ack_remote.sh sg <body>）
kubectl -n new-api patch deploy new-api-ph-standby --type=json -p='[
  {"op":"add","path":"/spec/template/spec/containers/0/env/-","value":{"name":"SQL_MAX_OPEN_CONNS","value":"10"}},
  {"op":"add","path":"/spec/template/spec/containers/0/env/-","value":{"name":"SQL_MAX_IDLE_CONNS","value":"5"}}]'
# 校验（期望 10 / 5）
kubectl -n new-api get deploy new-api-ph-standby -o jsonpath='{.spec.template.spec.containers[0].env[?(@.name=="SQL_MAX_OPEN_CONNS")].value}{"\n"}'
```

**现状影响**：删除后**未造成即时故障**（RDS `ConnectionUsage` 仍 <5%，备站仅 2 副本）。风险只在"备站扩容 + 主站扩容同时发生"时兑现。
