# 新增域名转发配置的口径 —— 只改 Ingress，不动 ALB 监听规则

- **日期**：2026-10-12
- **结论**：✅ **只能改 Ingress（必要时 AlbConfig）**；控制台「转发规则」页的**插入新规则 / 排序 / 批量删除全部不可用**，**不要尝试手动增加**。
- **性质**：不是"建议"，是**平台级技术强制**（见 §1 实测证据）。
- **相关**：`REFERENCE.md §10` · `域名规范化与Host收敛_最佳实践方案_2026-10-12.md`

---

## 1. 硬证据：手动写入被服务端拒绝（3/3）

对两地 ALB 的监听直接调用 `CreateRule`（`--DryRun true`，**零变更**）：

| 目标 | 监听 | 返回 |
|---|---|---|
| mnl ALB `alb-1riqckb1h8ezm0y7s9` | 443 `lsn-hjl2cz2g9oqvee4eix` | ❌ `OperationDenied.ServiceManagedResource` |
| mnl ALB 同上 | 80 `lsn-ihrgkty2sjdy8s5p4h` | ❌ 同上 |
| sg ALB `alb-amdwm60xmznh7s1nae` | 443 `lsn-iqn5i233mvv7eu4u6w` | ❌ 同上 |

原文：`The operation is not allowed because the current resource is managed resource.`

**为什么被拒** —— 这两个 ALB 是 **ACK 托管的派生资源**，其标签直接说明归属：

```
ack.aliyun.com                    = cd57e40ce9a634c1698c2f5c5e09bd93c   ← 集群 ID
ingress.k8s.alibaba/albconfig     = kube-system/mnl-alb                  ← 由该 AlbConfig 创建
ingress.k8s.alibaba/resource      = ApplicationLoadBalancer
```

⇒ ALB 实例、监听、规则、服务器组**全部由 ACK ALB Ingress Controller 从集群资源派生**。控制台看到的那一列规则，是 Controller **渲染出来的结果**，不是可编辑的原件。

> 截图里「插入新规则」「排序」「批量删除」三个按钮是**灰态不可点**，与上述 API 行为一致。

## 2. 就算能改，也不该改（三条后果）

| 后果 | 说明 |
|---|---|
| **被 reconcile 覆盖** | Controller 持续对账；任何一次 Ingress 变更、AlbConfig 变更、控制器重启，都会按集群声明**重算规则集** ⇒ 手改的规则**静默消失** |
| **RuleId 无稳定性** | 实测多次漂移：同一条规则 ID 会在不同 Host 间**复用**（本次 80 监听 `rule-0f7ru4csbcn41ygmb4` / `rule-b1t5tod05rdsfdua8n` 再次重编号）⇒ 任何"按 ID 记账"的方案必然失效 |
| **IaC 漂移** | 手改后仓库与云端不一致，下次 `apply` 表现为"神秘回滚"，排查成本极高（本项目已因此吃过一次：`ingress-sg-standby.yaml` 漏回写 `listen-ports`） |

## 3. 正确姿势：五步

### ① 先定三要素

| 要素 | 取值来源 |
|---|---|
| **Host** | 目标域名（`a.likha.hk` 这类二级域**不在**通配符覆盖范围，见 §3.④） |
| **端口** | 80 / 443（**分别声明**，漏一个该端口就没有规则） |
| **后端** | `Service 名` + `port`（mnl 业务 = `new-api-stable`，sg 业务 = `new-api-ph-standby`，端口 `80`） |

### ② 选载体

| 需求 | 做法 |
|---|---|
| **转发**到业务 | 加进**已声明对应 `listen-ports` 的 Ingress**，或**新建 Ingress**（新建时**必须带** `alb.ingress.kubernetes.io/listen-ports`，否则不生成规则） |
| **跳转**（30x） | 用注解 `alb.ingress.kubernetes.io/actions.<伪服务名>` + `RedirectConfig` + `httpCode`；Ingress 里 `service.name` 必须**与注解后缀逐字同名**、`port.name: use-annotation` |

### ③ 定优先级（`alb.ingress.kubernetes.io/order`）

- 现有取值（实测）：跳转 = **1**（最先匹配）、canary = 45/46、**兜底 = 50**、catchall-404 = 100。
- **要压过兜底，新规则的 `order` 必须 < 50**（mnl/sg 两地兜底都是 50）。
- ⚠️ 上线后**以 `ListRules` 的 `Priority` 实测为准**，不要靠推算。

### ④ 443 的证书覆盖

- 当前 443 默认证书 = 通配符 `*.likha.hk`（SAN 另含裸域 `likha.hk`）。
- **覆盖**：`www.likha.hk`、`sg.likha.hk`、`likha.hk` ✅
- **不覆盖**：`.internal.` 类（`ph-verify.internal.likha.hk`）、多级域（`a.b.likha.hk`）⇒ 内部域名继续走 **80**；对外新域名若不在覆盖内，需单独挂证书（Ingress `certificate-id` 注解，或 AlbConfig listener 的 `certificates` 列表，字段名是 **`CertificateId`**）。
- **IP 永远不行**：CAS 的 DV 证书不签发 IP SAN ⇒ 裸 IP 的 HTTPS 不可用（`REFERENCE §4.5`）。

### ⑤ 验收（两步，缺一不可）

```bash
# 1) 查云侧真实动作 —— 不能只看 curl（错字段名会静默失败且 HTTP 仍回 200）
aliyun alb ListRules --region <region> \
  --LoadBalancerIds.1 <alb-id> --ListenerIds.1 <listener-id> --MaxResults 100
#    核对：RuleConditions[].HostConfig.Values / RuleActions[].Type / HttpCode / Priority

# 2) 客户端实测 —— HTTP 与 HTTPS 各一遍（只测一个会漏掉整类缺口）
curl -sS -o /dev/null -w "%{http_code} %{num_redirects}\n" https://<host>/api/status
curl -sSL -o /dev/null -w "%{http_code} %{num_redirects} %{url_effective}\n" https://<host>/api/status
```

### ⑥ 回写真源

改完集群**必须**同步 `deploy/manifests/*.yaml`（或在 `deploy/tasks/*/bodies/*.sh`），否则重演漂移。

## 5. 静默失败对照表（血泪，全部实测过）

| 写法 | 后果 |
|---|---|
| AlbConfig 里写 `httpDefaultActions` / `defaultActions` | **不生效**，Controller 一律用派生占位组覆盖 ⇒ 想让 default 兜底**只能靠 Ingress 规则** |
| `certificates: - CertIdentifier: xxx` | CRD 静默忽略（正确字段名 **`CertificateId`**）⇒ HTTPS 无证书 |
| 跳转写 `redirectConfig` / `statusCode` | 静默忽略，退化成 ForwardGroup + 404 规则，且 **HTTP 仍回 200**（强伪装） |
| `service.name` 与 `actions.<name>` 不一致 | 动作找不到 ⇒ **规则不生成**，不报错 |
| `port.name` 从 `use-annotation` 改成 `number` | Controller 会真去找同名 Service ⇒ 不存在 ⇒ 规则不生成 |
| 漏写 `listen-ports` | 该端口**完全没有规则**（SG 的 `www.likha.hk:443` 曾因此缺规则） |
| 443 上没有匹配的 Host 规则 | 落**监听器默认动作** = 派生占位组 `kube-system-fake-svc-443`（节点 IP:3000、健康检查 off）⇒ **502** |

## 6. 附：两个操作细节

**① "DryRun 探针法"在托管 ALB 上的准确边界（本次修正）**

- 参数**齐备**时 → 回 `OperationDenied.ServiceManagedResource`，可确证"会被拒"。
- 参数**不齐**时 → **先回参数校验错**（本次实测 `MissingRuleActions.1.Order`），**看起来像"没被托管拦截"**，极易误判。
- ⇒ 结论不变：**DryRun 无法用于预演参数正确性**（永远到不了 `DryRunOperation`）；仅可用于确证托管拒绝，且必须参数齐备。

**② `ListRules` 偶发返回空（本次踩到）**

复核时 80 监听计数一度从 **6 变成 0**，重试第 1 次即恢复 6 条（301 规则完好）。⇒ **计数/断言必须重试 ≥3 次并校验返回是合法 JSON**，否则会把查询抖动误判成生产事故。

## 7. 附：Ingress ↔ ALB 规则对账表（2026-10-12 实测，原始 ID 级）

### 7.1 对账规则（只需记住这一条）

> **1 个 Ingress → N 条 ALB 规则**，`N = (host × path 组合数) × 该 Ingress 声明的监听端口数`。

⇒ 控制台「路由」页按 **Ingress 聚合**显示（一个 Ingress 一行，`规则` 列把所有 path 平铺出来）；「转发规则」页按 **ALB 规则逐条平铺**，**不带 Ingress 归属信息**。**两者不是 1:1** —— 这就是"看着对不上"的唯一原因。

**服务器组命名规则**：`<namespace>-<service>-<port>`（如 ns=`new-api` + svc=`new-api-stable` → `new-api-new-api-stable-80`）。

### 7.2 马尼拉 ALB `alb-1riqckb1h8ezm0y7s9`

**`:443`（3 条）**

| prio | RuleName | IF | THEN | 来源 Ingress |
|---|---|---|---|---|
| 1 | `rule-443-1` | Host=`likha.hk` & Path=`/*` | **Redirect 308** → `https://www.likha.hk` | `new-api-https-canonical` |
| 2 | `rule-443-2` | Host=`ph-verify.internal.likha.hk` & Path=`/*` | ForwardGroup → `sgp-j4qrgy3f7bcv1r67na` | **`new-api-stable-ip` path #1** |
| 3 | `rule-443-3` | Path=`/*`（**无 Host**） | ForwardGroup → `sgp-j4qrgy3f7bcv1r67na` | **`new-api-stable-ip` path #2** |

⇒ `new-api-stable-ip` 有 **2 条 path**（具名 host + 无 Host）⇒ 在 443 上**生成 2 条规则**。**`rule-443-2` 就是它的第一条 path**，第二条（兜底那条）是 `rule-443-3`。

**`:80`（6 条）**

| prio | RuleName | IF | THEN | 来源 Ingress |
|---|---|---|---|---|
| 1 | `rule-80-1` | Host=`www.likha.hk` | Redirect **301** | `new-api-http-redirect` path #1 |
| 2 | `rule-80-2` | Host=`likha.hk` | Redirect **301** | `new-api-http-redirect` path #2 |
| 3 | `rule-80-3` | Host=`ph-verify…` & **Header** | → `sgp-slwubl6v6sb2xtsxrz`（canary w100） | `new-api-canary-header` |
| 4 | `rule-80-4` | Host=`ph-verify…` | → canary `sgp-1eevkvsn0c32t3e1ya` **w5** + stable `sgp-j4qrgy3f7bcv1r67na` **w95** | `new-api-canary-weight`（**含合并**，见 §7.6） |
| 5 | `rule-80-5` | Path=`/*`（无 Host） | → `sgp-j4qrgy3f7bcv1r67na` | `new-api-stable-ip` path #2 |
| 6 | `rule-80-6` | Path=`/*`（无 Host） | **FixedResponse 404** | `new-api-catchall-404` |

### 7.3 新加坡 ALB `alb-amdwm60xmznh7s1nae`

**`:443`（4 条）**

| prio | RuleName | IF | THEN | 来源 Ingress |
|---|---|---|---|---|
| 1 | `rule-443-1` | Host=`likha.hk` | **Redirect 308** | `new-api-sg-https-canonical` |
| 2 | `rule-443-2` | Host=`sg-standby.internal.likha.hk` | → `sgp-rlxs1mqishcxcfkx7u` | `new-api-ph-standby` path #1 |
| 3 | `rule-443-3` | Host=`sg.likha.hk` | → `sgp-rlxs1mqishcxcfkx7u` | `new-api-ph-standby` path #2 |
| 4 | `rule-443-4` | Path=`/*`（无 Host） | → `sgp-8m8eknlyw0z1busl6r` | `new-api-ph-standby-ip` |

**`:80`（5 条）**

| prio | RuleName | IF | THEN | 来源 Ingress |
|---|---|---|---|---|
| 1 | `rule-80-1` | Host=`www.likha.hk` | Redirect **301** | `new-api-sg-http-redirect` path #1 |
| 2 | `rule-80-2` | Host=`likha.hk` | Redirect **301** | `new-api-sg-http-redirect` path #2 |
| 3 | `rule-80-3` | Host=`sg-standby.internal.likha.hk` | → `sgp-rlxs1mqishcxcfkx7u` | `new-api-ph-standby` path #1 |
| 4 | `rule-80-4` | Host=`sg.likha.hk` | → `sgp-rlxs1mqishcxcfkx7u` | `new-api-ph-standby` path #2 |
| 5 | `rule-80-5` | Path=`/*`（无 Host） | → `sgp-8m8eknlyw0z1busl6r` | `new-api-ph-standby-ip` |

⇒ SG 侧 **完全 1:1 展开、无合并**（4 = 1+2+1，5 = 2+2+1），是验证上述对账模型最干净的样本。

### 7.4 RuleName 的命名逻辑

`rule-<监听端口>-<该监听内的序号>` —— 序号**只反映本监听的排序**，**与"第几个 Ingress"无关**。⇒ **不能用 RuleName 做对账锚点**；`RuleId` 更不可靠（会跨 Host 复用/重编号）。

### 7.5 ⚠ 服务器组**同名不同 ID**（务必按 ID 引用）

| 名称 | 实际有 **2 个** ID |
|---|---|
| `new-api-new-api-canary-80` | `sgp-slwubl6v6sb2xtsxrz`（header 规则用）、`sgp-1eevkvsn0c32t3e1ya`（weight 规则用） |
| `new-api-new-api-ph-standby-80` | `sgp-rlxs1mqishcxcfkx7u`（显式 Host 规则用）、`sgp-8m8eknlyw0z1busl6r`（**无 Host 兜底**规则用） |

⇒ **按名字查/改服务器组会拿错对象**，一律用 `ServerGroupId`。

### 7.6 两条推断与一条例外

1. **MNL 80 的 `rule-80-4` 是合并/去重结果（推断）**：`new-api-stable-ip` 在 80 上有一条 `Host=ph-verify` 的 path，与 canary-weight 规则**条件完全相同**，被合并为一条（目标组同时含 canary **w5** 与 stable **w95**，正是 `canary-weight=5` 的语义）⇒ 故 80 是 **6 条而不是 7 条**。（依据：条件相同 + 目标组含 stable；如需确证可临时改 `order` 观察。）
2. **`order` 与 `Priority` 基本同向**：`order=1` 的跳转最先（prio 1/2）、兜底 `order=50` 居中、`catchall-404 order=100` 最后。
3. **⚠ 但 canary 那一对是例外**：`canary-header` 的 `order=46` 实测排在 `canary-weight` 的 `order=45` **之前**（prio3 vs prio4），与 order 大小**相反**。⇒ **`order` 不能用于推算最终优先级，上线后必须以 `ListRules` 的 `Priority` 实测为准。**

## 8. 遗留（未变）

- 两地兜底 Ingress 仍在 ⇒ **任何伪造 Host 走 HTTPS 也会命中业务后端回 200**（任务 47，2026-10-12 用户裁定**暂不推进**）。
- SG 侧 `www.likha.hk` **有意不建显式 Host 规则**（与 mnl 一致，靠兜底）。
- 可编程脚本（AScript）等**若 Ingress/AlbConfig 未暴露**的能力，如确需使用，须先确认 AlbConfig 支持情况；不支持则属例外通道，**必须回写 IaC 并接受可能被 reconcile 覆盖**。
