# 风险发现｜ALB 健康检查路径 `/api/status` 命中全局限流（429）—— 2026-10-06

> 发现路径：任务 26「app-file 纠正版」落地后核对文件侧日志时顺带发现；**与本次改动无关**（见「时间线」）。

## 1. 现象
- `k8s-log-cd57e40ce9a634c1698c2f5c5e09bd93c/{app-file,app-stdout}` 中出现 `429`，**且只出现在 `GET /api/status`**。
- 429 样本源 IP **只有两个**：`10.0.0.137`、`10.0.1.97` —— 即马尼拉 ALB `alb-1riqckb1h8ezm0y7s9` 在两个公网 vSwitch（`vsw-mnl-pub-a`/`b`）的 ENI 地址 ⇒ 来源是 **ALB 健康检查**，不是用户流量。

## 2. 时间线（排除本次改动）
- 15:22 起即有 429 样本（`app-stdout` 近 24h 最早样本）；
- 本次 `app-file` 改动（`args`/`emptyDir`/CRD）**19:16–19:35** 才发生。
⇒ **429 早于改动约 4 小时，属既存问题**（改动的 Pod 滚动只是换了一批后端 IP，非诱因）。

## 3. 机制（代码 + 云端配置双向取证）
- 路由：`/api/status` 注册在 `router/api-router.go:26`，同组第 21 行挂了 `middleware.GlobalAPIRateLimit()`。
- 阈值：`common/init.go:123-125` 默认 `GLOBAL_API_RATE_LIMIT_ENABLE=true`、`GLOBAL_API_RATE_LIMIT=360`、`..._DURATION=180s`；**按 client IP 计**（`middleware/rate-limit.go` → `redisIPRateLimitKey(mark, c.ClientIP())`，Redis 固定窗口 Lua）。
- 现状：集群 `cm/new-api-config` 与 Pod env **均未覆盖限流键**（实测 grep 为空）⇒ 走代码默认值。
- **无限流白名单、无路径豁免**（`middleware/rate-limit.go` 内无 whitelist/127.0.0.1 分支）。
- ALB 侧（`aliyun alb ListServerGroups --VpcId vpc-5tst1tgeessxn1azwasg2`）：
  - `sgp-j4qrgy3f7bcv1r67na`、`sgp-tqgwt413t19mum8oa9` **两个同质 ServerGroup** 都指向同 4 个 Pod ENI（`10.0.43.206/214/217`、`10.0.22.219:3000`）；
  - 健康检查 `HTTP GET /api/status`、`codes=[http_2xx]`、`interval=6s`、`timeout=3s`、`healthy=2`、`unhealthy=3`；
  - `sgp-fm7kdwz99wtzbffkfx`（fake-svc）已关健康检查，不参与。

## 4. 影响判定
- 抽样（近 10min，单查询上限 100 行）：**429 100% 来自上述两个 ENI**；200 同样以这两个 ENI 为主（另有节点 IP = kubelet 探针，正常）。
- ⇒ ALB 健康检查被限流拒绝的比例约 **半数**（样本口径）。
- **当前未致事故**：`ListServerGroupServers` 四后端全部 `Available`（未触发 3 连失败）。
- **风险性质 = 脆弱耦合**：健康检查的限流桶与"任何来自 ALB ENI 的请求"共用（360/180s per IP）。一旦额外请求或检查抖动把桶打满 → 连续 3 次 429 → 后端判不健康 → ALB 摘除 → 用户侧 5xx，且**排障时容易误判为应用 5xx/网络问题**。

## 5. 处置建议（择一/组合，均需授权）
1. **降检查频率 + 合并同质组**（成本最低）：`interval 6s → 15~30s`；并核对**为何两个 ServerGroup 同质重复**（同一 Ingress 被两条规则引用？），合并后再砍一半检查流量。
2. **抬限流阈值**：ConfigMap 调 `GLOBAL_API_RATE_LIMIT`（当前默认 360/180s）。⚠ ConfigMap 变更会经 `checksum/config` 注解触发一次滚动。
3. **代码侧豁免（根治，归 G8）**：为 `/api/status`（或新增 `/healthz`）跳过限流白名单，并把 ALB 健康检查 + kubelet 探针统一切到该路径。

## 8. ⚠ 顺带发现：Host 白名单被「无 Host 规则」架空（早于本次变更）

- 合并后拨测：`Host: bogus.example.com` → **200**（不是 404）。
- 原因：`Ingress/new-api-stable-ip` 的**无 Host 规则**（`order: "50"`，path `/*`）匹配**任意 Host**，优先级高于 `Ingress/new-api-catchall-404`（`order: "100"`）。该 Ingress 于 **2026-10-06 18:17** 生效 ⇒ **任务 47「伪造 Host 全 404」的加固结论自彼时起不再成立**（任务 47 的验证早于该 Ingress 落地）。
- 现状语义：任何 Host（含伪造）都进主站，app 层不校验 Host（`/api/status` 恒 200）。
- **✅ 裁定（2026-10-06，用户）：A —— 接受现状**。裸 IP 直访是既有、用户确认过的取舍（manifest 头已写明"主站将被裸 IP 可访问"），而 Host 白名单与"无 Host 规则"在 ALB 规则层面无法共存 ⇒ **不整改，仅记录**。
  - 连带处置：任务 47 的「伪造 Host → 404」判据在 mnl **作废**（已在 v2.0 四处改为"核验业务 Host 路由正确 + catchall 规则存在"）；
  - **收敛路径**：G5 证书 + 公网 DNS 就绪 → 删除 `Ingress/new-api-stable-ip`（其退役条件）→ 届时 `catchall-404` 恢复为唯一兜底，伪造 Host 自然回到 404（届时补测）。
  - 否决的方案 B：删无 Host 规则（失去裸 IP 直访）或抬 catchall 优先级（裸 IP 也 404）。
- 依据：`deploy/docs/Day3任务47_ALB安全组与SNI_执行报告.md`、`deploy/manifests/ingress-mnl-stable-ip.yaml`（规则顺序说明）、`deploy/logs/task26_sls_index_20261006-165435/alb_curl_after.txt`。
