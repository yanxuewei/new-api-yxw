## 0. 结论先行

new-api 的**三条对外发信路径全部只按 `ClientIP` 限流，没有任何「按目标邮箱」或「按全局发信总量」的闸门**。
在 QQ 免费邮箱（约 **100 封/天**）或 DirectMail（**200 封/天**）这类**硬额度**通道上，这意味着：

> 攻击者用 IP 池 + 邮箱列表，可以在几分钟内把当日全部发信额度烧光；
> 之后**所有真实用户的注册验证码、密码重置邮件全部发送失败** —— 而站点的 HTTP 面完全正常。

**三层闸门设计**（L1 按邮箱 / L2 按 IP / L3 全局熔断），其中 **L3 是唯一能挡住「换 IP + 换邮箱」分布式消耗的一层**，也必须在**邮件发送器内部**实现（中间件层看不到"已发信封数"）。

| 层 | 维度 | 默认阈值 | 挡什么 |
|---|---|---|---|
| **L1** | 目标邮箱（归一化 + 哈希） | 3 次/10 分钟，**5 次/天** | 对单个收件人轰炸、给同一人反复发 |
| **L2** | ClientIP（现状保留 + 补齐） | 2 次/30 秒 | 单机脚本刷（现状已有，但 `/reset_password` 缺） |
| **L3** | **全局出信封数** | **日配额 80%（可配）+ 连续失败熔断** | **分布式消耗日额度** —— 唯一有效防线 |

### 1.4 额度侧硬顶（外部约束，决定 L3 的必要性）

|---|---|---|---|

## 2. 威胁模型

| # | 攻击形态 | 资源成本 | 现有守卫能否挡住 | 后果 |
|---|---|---|---|---|
| T1 | 单机高频打一个邮箱（骚扰/轰炸） | 1 个 IP | ✅ 被 `EV` 2/30s 挡住（路径 1/3）；❌ 路径 2 有 20/20min 窗口 | 骚扰单个收件人 |
| T2 | 单机换邮箱刷（消耗注册额度） | 1 个 IP | ✅ 被 `EV`/`CT` 的 IP 维度挡住 | — |
| T3 | **IP 池 × 邮箱列表**（分布式刷） | N 个 IP | ❌ **全部守卫失效**（IP 维度被绕开，邮箱维度不存在） | **日额度被烧光 → 全站注册/找回密码不可用** |
| T4 | **单一邮箱被跨 IP 轰炸** | N 个 IP | ❌ 同上 | 收件人被骚扰 + 该邮箱侧被服务商标记 |
| T5 | **发信配置错误自伤**（口令过期 / SMTP 拒连） | 0（非攻击） | ❌ 无任何熔断 | 一次故障烧光整日额度，且**要等到次日 0 点才恢复** |
| T6 | 别名绕过（`user+a@x.com`） | — | ❌ 无 | 使「按邮箱」维度形同虚设（见 §6.2） |

**关键判断**：T3/T4/T5 **不可能**靠中间件层的 IP/邮箱维度解决 —— 它们的共同特征是"**单次请求都合法，只有累计量非法**"。只有 **L3 全局出信封数闸门**能覆盖。

## 3. 设计

### 3.1 三层闸门（按请求处理顺序）

```
发信请求
   │
   ├─[L2] 按 IP    ── EV 现状（2/30s）；并给 /api/reset_password 补挂 EV
   │
   ├─[L1] 按邮箱  ── 新增 EVE 维度：3/10min + 5/day
   │
   └─[L3] 全局出信 ── 新增"发信闸门"（在 common.SendEmail 前置）：
                       · 日配额软熔断（默认 = 配额的 80%）
                       · 连续失败熔断（默认 5 次失败 → 冷却 10 分钟）
                       · 冷却期与配额耗尽期一律 fail-closed（不是 fail-open）
```

**为什么 L3 必须在 `common.SendEmail` 前置而不是中间件**：中间件只知道自己这一次请求，**看不到今天已经发了多少封**。全局计数只能落在发信函数入口。

### 3.2 L1 键设计

```go
// 新增于 middleware/rate-limit.go，与既有两个键构造器并列
func redisEmailRateLimitKey(mark string, emailHash string) string {
    return fmt.Sprintf("%s:email:%s:%s", redisRateLimitNamespace, mark, emailHash)
}
```

- **mark** = `EVE`（Email Verification by Email），与 `EV` 区分，避免和 IP 键混淆。
- **`emailHash`** = `sha256(normalizedEmail)` 的前 16 个 hex 字符。
  - 归一化用现成的 `model.NormalizeEmail`（`model/user.go:325`：`ToLower + TrimSpace`）——已在路径 1/2/3 全部生效，**无需改调用点**。
  - **必须哈希**：键会落进 Tair，明文邮箱 = 把用户 PII 写进缓存 + 缓存 Dump 泄露面扩大。哈希后仍能保证同一邮箱命中同一键。
  - 16 hex（64 bit）碰撞概率在邮箱量级（<10⁸）可忽略。

- 内存降级路径与 Redis 路径**共用同一维度**，键为 `EVE:" + emailHash`（对齐现状写法 `:47`）。
- **降级口径必须 fail-closed**：与 G8 主体的「普通限流 fail-open」不同，发信类限流在 Redis 故障时**不能放行**，应退化为内存固定窗口（与 `RATE_LIMIT_CRITICAL_MEMORY_BACKSTOP` 同口径）。理由：`/readyz` 把 Redis 定为 SOFT 依赖，Tair 抖动时若发信限流 fail-open，恰好是攻击者最容易得手的窗口。

### 3.3 L3 全局闸门设计

在 `common.SendEmail`（`common/email.go`）入口加一个进程内 + Redis 双计的闸门：

| 计数器 | 键 | 语义 |
|---|---|---|
| 日成功发信数 | `mailer:quota:<yyyymmdd>:used` | 跨 Pod 共享（Redis INCR） |
| 连续失败数 | `mailer:breaker:failstreak` | 失败 +1、成功清零 |
| 熔断标记 | `mailer:breaker:open_until` | 存在即拒发 |

- **预占式计数**：请求发出前先 `INCR`，失败**不回滚**（因为失败邮件也计入服务商配额）。这正是 §1.4 的教训。
- **日配额阈值**：默认 `MAIL_OUTBOUND_DAILY_QUOTA` **无默认值（0 = 不启用）**，必须显式配置 —— 因为 QQ(100) 与 DirectMail(200) 差一倍，写死一个数会在某条通道上产生假安全感。推荐值见 §4。
- **连续失败熔断**：`MAIL_OUTBOUND_FAILURE_BREAKER=5` —— 这是**唯一能救 T5 的机制**。SMTP 口令过期后第 6 封起全部拒发并告警，而不是把 200 封额度烧在一个必然失败的循环里。
- **熔断期间返回**：`503`（依赖不可用，客户端应退避重试），**不是** 429（语义是"你请求太频繁"，会把责任推给用户）。
- **Redis 不可用时**：日配额降级为**单 Pod 内存计数 × 副本数误差**，并**记 WARN 日志 + 指标**。宁可少发，不可无限发。

### 3.4 观测（必须有，否则闸门等于隐形）

| 指标 | 类型 | 标签 |
|---|---|---|
| `newapi_email_send_total` | counter | `path`(`verification`/`reset_password`/`email_bind`)、`result`(`sent`/`failed`) |
| `newapi_email_send_suppressed_total` | counter | `reason`(`ip`/`email`/`quota`/`breaker`) |

≥2 条告警（接任务 32 的 SLO 体系）：

1. `newapi_email_send_total{result="failed"}` 5 分钟增长 > 5 → P1（SMTP 配置/通道故障）
2. `newapi_email_send_suppressed_total{reason="quota"}` 出现 → P1（**当日额度已接近耗尽**，真实用户即将收不到邮件）

## 4. 新增配置项

| 变量 | 默认 | 取值 | 说明 |
|---|---|---|---|
| `EMAIL_RATE_LIMIT_BY_EMAIL_ENABLE` | `true` | bool | L1 总开关 |

> ⚠️ 所有变量**默认值必须等于"现状行为 + 安全默认"**：L1 默认开启（这是修复而非新特性），L3 默认为"不启用"（因为它依赖通道额度，属于部署方决策）。

## 6. 影响面、残余风险与不做的事

### 6.1 影响面

| 面向 | 影响 |
|---|---|
| 正常用户 | 无感。L1 阈值 3/10min、5/day 对"注册 + 重发一次"绰绰有余；L2 与现状完全一致 |
| 多副本 | L1/L3 走 Redis ⇒ 跨 Pod 一致；Redis 故障期间退化（已声明） |
| 连接预算 | 每个发信请求多 1–2 次 Redis 往返；`EV` 已有同量级开销，**不改变 I-1 连接预算口径**（走同一连接池，非新建连接） |
| 成本 | 无新增云资源费用；L3 反而**降低**超额发信费（DirectMail 0.29 USD/千封） |
