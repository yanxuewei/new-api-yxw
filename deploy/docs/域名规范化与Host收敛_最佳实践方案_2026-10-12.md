## 2. 方案论证

### 2.1 为什么 canonical 选 `www.likha.hk`

1. **用户决策**（2026-10-12）—— 对外入口口径以 www 为准。
2. **`www` 是互联网惯例主域**：与第三方平台（支付、邮件、SaaS 回调、统计）对接时，`www` 子域更常见；也便于将来把根域改成 CNAME/跳转而不影响业务解析。
3. **证书无成本**：`*.likha.hk` 已覆盖 `www`。
4. **风险由 308 兜住**：选 www 做 canonical 意味着**根域 `likha.hk` 的 HTTPS 会被跳转**。而根域恰恰是 API 客户端最可能填的 base_url ⇒ 必须用 **308**（保留方法/body），否则根域上的 POST 会被降级为 GET（详见 §2.3）。

> ⚠️ **需要同步的口径**：凡是已经对外提供过 `https://likha.hk` 作为 base_url 的地方（文档、客户配置、SDK 示例），应统一改成 `https://www.likha.hk`。**跳转只是兜底，不是替代** —— 让客户端少跳一次总是更好的。

### 2.2 为什么 443 那一跳「必须做」而不是可选

只做 80 的跳转，会漏掉一整类流量：

- 用户直接输入 `https://likha.hk`（浏览器地址栏会**自动补 https**）
- 外部链接、书签、邮件签名里的 `https://likha.hk`
- **HSTS 生效后**浏览器**强制 https，根本不经过 80** ⇒ 80 的 301 永远不触发

⇒ 也就是说：**只改 80，`https://likha.hk` 会继续 200，canonical 形同虚设。**

### 2.3 为什么用 `308` 而不是 `301`（本方案的关键取舍）

`new-api` 是 **API 网关**，`likha.hk`（本次被收敛的一方）很可能被客户当作 API base_url（`POST /v1/chat/completions`）。而 HTTP 语义上：

| 状态码         | 永久性    | 是否保留方法/body                        |
| ----------- | ------ | ---------------------------------- |
| `301`       | 永久     | ❌ **客户端普遍把 POST 降级为 GET 并丢弃 body** |
| `302`/`303` | 临时     | ❌ 同样会改方法                           |
| `307`       | 临时     | ✅ 保留                               |
| **`308`**   | **永久** | **✅ 保留**                           |

⇒ 若用 301 对承载 API 的域名做收敛，**客户端的 POST 会被静默改成 GET**，表现为「调用失败 / 参数丢失」，且极难排查。  
⇒ 用 **308** 则**永久重定向 + 保留 POST/body** 两者兼得，SEO 上 Google 对 301/308 视为等价（权重传递相同）。

**ALB 支持性（已核实）**：`RedirectConfig.HttpCode` 取值 **301 / 302 / 303 / 307 / 308**（ALB `CreateRule` API 文档 + 《ALB 网关路由最佳实践》互相印证）。另：**HTTPS 监听只允许跳转到 HTTPS 协议** —— 本方案正是 HTTPS→HTTPS，符合。

### 2.4 为什么 80 侧要「一步到位」

现状 `http://likha.hk` → 301 → `https://likha.hk` → （本次加 443 跳转后）→ 308 → `https://www.likha.hk` = **三跳**。  
改成 `RedirectConfig.host` 写字面量 `www.likha.hk` 后：`http://likha.hk` → **301 → `https://www.likha.hk`** = **一跳**。首屏更快、链路更短、也少一次 TLS 握手。

## 4. 落地实现

### 4.1 修改 `new-api-http-redirect`（80 侧）

**唯一改动**：注解里 `RedirectConfig.host` 由 `${host}` 改为字面量 `www.likha.hk`。

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: new-api-http-redirect
  namespace: new-api
  annotations:
    # ↓ 与现状的差异只有 host：${host} -> www.likha.hk（字面量）
    alb.ingress.kubernetes.io/actions.redirect: >-
      [{"type":"Redirect","RedirectConfig":{"host":"www.likha.hk","path":"${path}","port":"443",
        "protocol":"HTTPS","query":"${query}","httpCode":"301"}}]
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTP":80}]'
    alb.ingress.kubernetes.io/order: "1"
spec:
  ingressClassName: alb
  rules:
    - host: www.likha.hk
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: redirect
                port:
                  name: use-annotation
    - host: likha.hk
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: redirect
                port:
                  name: use-annotation
```

两条规则**共用同一个动作注解**，所以「根域 → www」「www → www」都能一跳到位，无需拆开。

### 4.2 新增 `new-api-https-canonical`（443 侧）

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: new-api-https-canonical
  namespace: new-api
  labels:
    app: new-api
    site: ph-mnl
    purpose: canonical-host-redirect
  annotations:
    alb.ingress.kubernetes.io/actions.redirect: >-
      [{"type":"Redirect","RedirectConfig":{"host":"www.likha.hk","path":"${path}","port":"443",
        "protocol":"HTTPS","query":"${query}","httpCode":"308"}}]
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
    alb.ingress.kubernetes.io/order: "1"
spec:
  ingressClassName: alb
  rules:
    - host: likha.hk              # ⚠️ 只放根域；放 www.likha.hk 会变成自跳 = 死循环
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: redirect        # ⚠️ 必须与 actions.<name> 同名
                port:
                  name: use-annotation
```

**三条硬约束**（违反任一条都会静默失效或打挂站点）：

1. **`order: "1"`** —— 必须小于 `new-api-stable-ip` 的 `order=50`，否则压不过 443 的兜底 `rule-443-2`，规则等于没写。
2. **只能放 `likha.hk`（根域）** —— 若把 `www.likha.hk` 也放进来，canonical 会在 443 上跳到自己 ⇒ **无限 308 循环**。
3. **`service.name` 必须与注解后缀 `actions.<name>` 逐字同名**，且 `port.name` 必须是 `use-annotation`；写成真实 Service 名会因找不到该 Service 而**静默不生成规则**（ACK 控制台「规则」列只会原样显示这个名字，不具备诊断价值）。

> 完整字段名依据见 `deploy/manifests/ingress-mnl-http-redirect.yaml` 头部注释与 `REFERENCE.md`「ALB 443 / TLS」§4。

## 5. 上线顺序与验证

### 5.1 顺序

1. **先试跑**（非生产 host）：用临时 host（如 `canon-probe.likha.hk`）建一份等价 Ingress，确认能生成 `Redirect` 动作且 **`HttpCode=308` 被 ALB 接受**，验证后**立即删除**。`RedirectConfig.HttpCode` 在 ALB API 层已确认支持 308，但 Ingress Controller 侧仍以实测为准。
2. **先做 80**（§4.1）：风险最低。
3. **再做 443**（§4.2）：这是行为变更（根域 443 由 200 → 308）。
4. 收尾：443 补 404 兜底、SG 对齐、对外 base_url 口径统一为 `https://www.likha.hk`。

### 5.2 验证清单（`curl`，GET，勿用 `-I`）

```bash
# 目标：#1 301 一跳 / #2 301 一跳 / #3 308 一跳 / #4 200
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' --resolve likha.hk:80:8.212.161.49     http://likha.hk/api/status
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' --resolve www.likha.hk:80:8.212.161.49 http://www.likha.hk/api/status
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' --resolve likha.hk:443:8.212.161.49 https://likha.hk/api/status
curl -sS -o /dev/null -w '%{http_code}\n'                 --resolve www.likha.hk:443:8.212.161.49 https://www.likha.hk/api/status

# 跳转链必须 <= 1 跳、终点 200
curl -sSL -o /dev/null -w '%{http_code} hops=%{num_redirects} final=%{url_effective}\n' \
  --resolve likha.hk:80:8.212.161.49 --resolve www.likha.hk:443:8.212.161.49 \
  http://likha.hk/api/status

# POST 方法保留验证（308 的核心收益）—— 308 后必须仍是 POST，不能被降级为 GET
```

### 5.3 ⚠️ 不可逆点

**301/308 都会被浏览器/中间层长期缓存**。一旦发布，**对已经访问过的客户端，回退无效** —— 它们在不联网确认的情况下直接走缓存的重定向。因此：

- 必须在**非生产 host 先验证**，再上正式 host；
- 上线后**不要**立刻关掉跳转目标的可用性（`https://www.likha.hk` 必须一直 200）；
- 若要保留「随时能反悔」的余地，可先用 **`307`（临时 + 保留方法）**&#x8DD1;观察期，稳定后再切 `308`。

## 6. 风险与回退

| 风险                | 触发条件                                                                  | 影响                       | 回退                                          |
| ----------------- | --------------------------------------------------------------------- | ------------------------ | ------------------------------------------- |
| API POST 被改方法     | 用 301 而非 308                                                          | 客户端调用静默失败                | 本方案已用 308 规避                                |
| 无限重定向             | 把 `www.likha.hk` 也放进 443 canonical Ingress                            | www 打不开                  | 删除该 host 规则即刻恢复                             |
| 规则未生效且无报错         | `order` ≥ 50 / `service.name` 与注解不同名 / `port.name` 非 `use-annotation` | 加了等于没加                   | 查 `ListRules` 的 `RuleActions[].Type`        |
| **根域上有存量 API 客户** | 未评估就收敛                                                                | 根域被 308（保留方法，不损坏调用，但多一跳） | 上线前看 SLS 访问日志里 `likha.hk` 的 `POST` 占比与来源 UA |
| 缓存不可逆             | 301/308 上线后想反悔                                                        | 老客户端继续跳                  | 无法完全回退，只能改目标                                |

**上线前建议评估**：拉 SLS 访问日志，统计 `Host=likha.hk` 的请求里 **`POST` 占比 / User-Agent 分布**。因采用 308，即使存在非浏览器 API 客户端也**不会损坏调用**（方法/body 保留），但可据此确认是否需要同步通知客户改 base_url。

## 7. 本方案明确不做

| 项 | 原因 |

| B | **新建** `Ingress/new-api-sg-http-redirect`（:80，www+根域 → **301**，order=1）+ `Ingress/new-api-sg-https-canonical`（:443，根域 → **308**，order=1） | ✅ 四入口与 mnl 逐项一致 |

**★ 次序是硬约束**：必须**先补 443 兜底、后上 canonical** —— 反过来 `https://likha.hk` 308 会跳到 SG 443 无规则可匹配的 `https://www.likha.hk` ⇒ **502**。

**验收**：四入口 301/301/308/200；端到端 `redirects=1` → 200；**308 方法保留同样成立**（`curl -L -d ''` → `404`，非 200）；回归全绿（`sg.likha.hk` / 内部域名 / 裸 IP http / **裸 IP https 由 502 → 200**）；证书 Verify 0；**mnl 未受影响**。

取证：`deploy/docs/Day2_SG侧域名规范化对齐_2026-10-12.md`

| 步骤    | 回退命令                                                                                |
| ----- | ----------------------------------------------------------------------------------- |
| 80 侧  | 将 `new-api-http-redirect` 的 `host` 恢复为 `${host}` 并重新 apply                          |
| 443 侧 | `kubectl -n new-api delete ingress new-api-https-canonical`（或仅删 `likha.hk` 那条 rule） |
