## 2. 第一步：拿集群操作权限

跳板机上**不用**分发 kubeconfig，也不用长期 AK。跳板机绑定了 ECS 实例 RAM 角色（只读 + 换 kubeconfig 权限），执行：

```bash
newapi-kube
# 输出：kubeconfig 已刷新（60min）: /root/.kube/config
```

它做的事（`/usr/local/bin/newapi-kube`）：调 `cs DescribeClusterUserKubeconfig --TemporaryDurationMinutes 60` 换取 **60 分钟临时 kubeconfig**，写入 `~/.kube/config`（chmod 600）。**每 60 分钟要重跑一次**，令牌过期后 kubectl 会报 401。

> ⚠️ 已知坑：脚本里**必须显式带 `--region ap-southeast-6`**。跳板机全新装机时 aliyun CLI 没有默认 region，不传会直接报 `region can't be empty / Configuration failed`。

验证：

```bash
kubectl get nodes -o wide
kubectl get pods -A -o wide
```

## 3. 进 Pod（最常用）

```bash
# ① 先找到目标
kubectl get pods -A -o wide | grep <关键字>

# ② 交互式进容器（业务镜像通常只有 sh，没有 bash）
kubectl -n <ns> exec -it <pod> -- sh

# ③ Pod 内有多个容器时指定容器
kubectl -n <ns> exec -it <pod> -c <container> -- bash

# ④ 只跑一条命令，不进交互（写脚本/取证时用这个）
kubectl -n <ns> exec <pod> -- <cmd>
```

实测（`EXEC_OK`）：

```bash
kubectl -n kube-system exec logtail-ds-crwjr -- bash -c 'hostname'
# → logtail-ds-crwjr
```

> ⚠️ **目前 `new-api` 命名空间还是空的**——集群里只有 `kube-system` / `arms-prom` 的系统组件，业务 Pod 要等发版任务部署 stable 之后才有。
> 现在想练手，拿系统 Pod 试即可：`kubectl get pods -A | grep -E 'logtail-ds|coredns'`。

**常用变体**

```bash
kubectl -n <ns> logs -f <pod>              # 跟日志
kubectl -n <ns> logs <pod> --previous      # 看上次崩溃的日志
kubectl -n <ns> cp <pod>:/path/file ./     # 从 Pod 拷文件出来
kubectl -n <ns> port-forward <pod> 8080:3000   # 本地端口转发
```

## 4. 进节点（"登录到其他机器"的正路）

### 4.1 先理解：**为什么不能直接 ssh 到节点**

三条实测事实，缺一条都上不去：

1. 节点安全组 `sg-mnl-app` 的入向**只有两条**，**没有 22**：
   - `10250/10250 ← 10.0.0.0/16`（kubelet，供 apiserver 的 logs/exec/metrics）
   - `3000/3000 ← sg-mnl-alb`（只有 ALB 能打业务端口）
2. 跳板机上**没有 `newapi-mnl` 私钥**（`/root/.ssh` 里只有 `authorized_keys`）；
3. 实测跳板机 → 节点 22 端口 = **超时**（TCP 层就不通；2026-09-29 测的是当时的 `10.0.22.194`，结论同样适用于 §1 的现役节点）。

第 1 条是**设计如此**，不是漏配：方案 §8.1 明确写「禁止横向」，给节点开 22 属于安全核查扣分项。**不要为了图方便去给 `sg-mnl-app` 加 22 规则。**

### 4.2 正确做法：`kubectl debug node`

不需要密钥、不需要改安全组，靠 kubeconfig 权限直接在节点上起一个特权调试 Pod：

```bash
# 交互式（推荐）。节点名先用 kubectl get nodes 查，下面是当前节点之一
kubectl debug node/ap-southeast-6.10.0.16.21 -it --image=busybox:1.36 --profile=sysadmin

# 进去后进入宿主机根文件系统（等价于宿主机 root shell）
chroot /host

# 非交互，只跑一条
kubectl debug node/<node> -i --image=busybox:1.36 --profile=sysadmin -- sh -c 'chroot /host hostname'
```

这个调试容器带 `hostPID / hostNetwork / hostIPC` + privileged，宿主机根目录挂在 `/host`，所以进去之后能直接干这些事：

```bash
chroot /host crictl ps                 # 看节点上的容器
chroot /host crictl logs <id>          # 看容器 stdout
chroot /host journalctl -u kubelet -n 200
chroot /host ls /var/lib/kubelet/pods
chroot /host df -h / ; free -g ; top   # 资源排查
```

实测（`NODESHELL_OK`，宿主 ECS 名与台账一致）：

```
NODESHELL_OK
iZ5ts9wk588cliiweawindZ          ← chroot /host hostname
ack-managed-annotation.config    ← chroot /host ls /var/lib/kubelet
...
```

### 4.3 ⚠️ 用完必须删（重点）

`kubectl debug node` 建出来的是 **`default` 命名空间下的 privileged + hostNetwork Pod**，不会自动消失：

```bash
kubectl get pods -A | grep node-debugger
kubectl delete pod node-debugger-<node>-xxxxx
```

留一个特权 Pod 挂着 = 留在生产节点上的一个 root 后门，属于红线（见 §9）。

### 4.4 ⚠️ 报 `cannot exec into a container in a completed pod`（2026-10-18）

现象：

```
[root@newapi-ops-mnl ~]# kubectl exec -it node-debugger-ap-southeast-6.10.0.16.21-6jg5l -- bash
error: cannot exec into a container in a completed pod; current phase is Succeeded
```

原因：`kubectl exec` 只能进 **Running** 的 Pod。`kubectl debug node/...` 建出来的 Pod，如果没给一个**不退出**的命令，busybox 默认 entrypoint 在非 tty 场景立刻结束 → 容器退出 → Pod 阶段变 `Succeeded` → 再也 exec 不进去。不是权限问题，也不是 Pod 坏了。

处理：删掉重建，**命令末尾一定要跟 `-- sleep infinity`** 保活。

```bash
# ① 删掉死 Pod
kubectl delete pod node-debugger-ap-southeast-6.10.0.16.21-6jg5l -n default

# ② 重建，注意节点名是 region.内网IP 格式，不是 Pod 名里的后缀
kubectl debug node/ap-southeast-6.10.0.16.21 \
  --image=busybox:1.36 \
  --profile=sysadmin \
  -- sleep infinity

# ③ 另开一条 exec 进去
POD=$(kubectl get pods --no-headers | awk '/node-debugger/{print $1}' | tail -1)
kubectl exec -it "$POD" -- sh

# ④ 进宿主机根文件系统
chroot /host
```

只做一次性操作、不进交互的，可以不要保活，`-it` 直接带命令（退出后 Pod 仍会变 Succeeded，可接受）：

```bash
kubectl debug node/ap-southeast-6.10.0.16.21 --image=busybox:1.36 --profile=sysadmin \
  -i -- sh -c 'chroot /host hostname'
```

> 镜像固定写 `busybox:1.36`。节点上已有该 tag 缓存，省掉 `docker.io` 拉取失败的风险。

### 4.5 在控制台查看“已退出”的容器

`node-debugger-*` 是**裸 Pod**（无 Deployment/StatefulSet 控制器），所以不在「无状态」列表里；又处在 `default` 命名空间、阶段 `Succeeded`，容器组列表**默认按 Running 过滤**，按常规路径看不见。

**主路径**

```
ACK 控制台 → 集群 → ack-newapi-mnl → 左侧「工作负载」→「容器组」(Pods)
  ├─ 命名空间选 default
  ├─ 状态筛选改成「全部」或勾 Succeeded（部分版本叫「已完成」）
  └─ 搜索框输入 node-debugger
```

点进去能看到：概览（阶段 `Succeeded`、Exit Code `0`、Started/Finished 时间）、日志（stdout）、事件（调度/拉镜像/退出）、YAML（`--profile=sysadmin` 注入的 hostNetwork/hostPID）。

**从节点侧反查**（不确定命名空间时）

```
ACK 控制台 → 集群 → 节点 → 选中 ap-southeast-6.10.0.16.21 → 「容器组」标签页 → 状态筛 Succeeded
```

**Cloud Shell 兜底**（不受页面筛选影响，必定能看到）

```
ACK 控制台 → 集群 → 更多 / 运维管理 → Cloud Shell（或 kubectl 命令行）
```

```bash
kubectl get pod node-debugger-ap-southeast-6.10.0.16.21-6jg5l -n default -o wide
kubectl describe pod node-debugger-ap-southeast-6.10.0.16.21-6jg5l -n default   # State: Terminated / Reason: Completed / Exit Code: 0
kubectl logs node-debugger-ap-southeast-6.10.0.16.21-6jg5l -n default
```

> 控制台的「终端」按钮对 `Succeeded` 的 Pod **同样点不进去**，会报和命令行一样的错误。控制台绕不过这个限制，只能看日志/事件/YAML。看完记得删（§4.3）。
>
> 菜单名各版本有差异：「工作负载」可能叫「应用」，「容器组」可能叫「Pods」。找不到就翻这两处，或直接用 Cloud Shell。

## 5. 进任意 ECS：会话管理（不问网络、不问密钥）

**ECS 控制台 → 目标实例 → 远程连接 → 会话管理**。

- 基于云助手（Cloud Assistant），**不需要公网 IP、不需要 SSH 密钥、不需要开放 22 端口**
- RAM 身份 + MFA 鉴权，**会话全程录制并投递到 `oss://oss-newapi-mnl/ops-sessions/`**
- 跳板机本身就是这么用的入口；**2 台 worker 节点同样可用**

这是「临时 / 应急进任何一台机器」最稳的路。需要注意的是：节点上日常排障仍优先走 §4 的 `kubectl debug node`（在集群视角下操作，能直接配合 `crictl` / kubelet 日志），会话管理更适合「集群不可用 / kubectl 也进不去」的场景。

## 6. 连数据库（RDS 不能 ssh，只能连端口）

RDS 已就绪：`rds-mnl-newapi` = `pgm-5tstdhko64x2c01w`（PostgreSQL 17.0，Running），内外网分离，用内网地址：

```
pgm-5tstdhko64x2c01w.pgsql.ap-southeast-6.rds.aliyuncs.com
```

`sg-mnl-db` 的入向白名单只有两类：

| 源 | 说明 |
|---|---|
| `sg-mnl-app`（`sg-5tsil3ca5dfkqefks1g9`） | `from-app-only` — 只有业务/节点侧能连 |
| 4 个新加坡 NAT EIP（`47.84.126.214` / `47.84.83.76` / `47.84.29.162` / `47.84.184.246`） | `from-sg-nat-eip` — 为备区接管预留 |

**跳板机（`sg-mnl-alb-edge`）不在白名单里 → 直连 RDS 一定超时。**

正确姿势是从 Pod 里连（Pod 走节点/弹性网卡，落在 `sg-mnl-app`）：

```bash
kubectl -n new-api run pgcli --rm -it --restart=Never \
  --image=postgres:17-alpine -- \
  psql -h pgm-5tstdhko64x2c01w.pgsql.ap-southeast-6.rds.aliyuncs.com -U <user> -d <db>
```

- `--rm` 保证退出即删，不留残留 Pod；
- 凭据从 KMS / RDS 控制台取，**不要写进 Git、不要贴群里**。

## 7. 跨区提醒：跳板机只管马尼拉

跳板机在马尼拉 VPC（`10.0.0.0/16`），**私网到不了新加坡 `ap-southeast-1` 集群的 API Server**（未建 VPC 对等 / 云企业网）。所以：

- 马尼拉集群的一切运维走本跳板机即可；
- 新加坡 / 备区实例需要**单独入口**，或先补对等连接；不要指望从这里 `kubectl --context sg`。

**✅ 新加坡侧的既定执行通道（项目负责人 2026-10-09 确认）**：`bash deploy/lib/ack_remote.sh sg <body.sh>`（**云助手 → SG worker 节点内 kubectl**，临时 kubeconfig 用完即删）。任务 17/28/29/30/53 的 SG 侧动作都走它；本轮任务 29 的 Tair 探针、Secret 补键与滚动重启同样经它完成。补充两条实操：① 两集群 API Server 都只有私网端点（sg = `10.1.19.73:6443`），且账号内**没有 CEN**（`DescribeCens` TotalCount=0）⇒ 马尼拉跳板机对 SG 无任何私网可达性；② 本机调用时给执行器单独设 `ACKCTL_DIR`（如 `/tmp/ackctl-sg-fanyan`）可绕开 `/tmp/ackctl-<site>` 被 root 占用与并发竞态；③ SG 侧尚未建对称跳板机，若后续需要"会话录制"级别的合规通道，应新建 `newapi-ops-sg`（新资源+成本，需单独裁定）。

**2026-10-18 实测复验（跳板机 → SG 二次确认不通）**：会话管理登录 `newapi-ops-mnl`（私网 `10.0.0.135`）后直接探测 SG API Server：

```
[probe] 10.1.19.73:6443 BLOCKED rc=124
[probe] 10.1.19.73:443  BLOCKED rc=124
[route] 10.1.19.73 via 10.0.0.253 dev eth0 src 10.0.0.135
```

`rc=124` = TCP 连接超时（SYN 被丢弃），**不是** `Connection refused`。路由把包交给默认网关 `10.0.0.253`，而马尼拉 VPC 路由表没有到 `10.1.x` 的条目。配套核对：账号内 CEN 实例为 0（`DescribeCens` 返回空数组）、两地域 VPN 网关均为 0、SG 集群无公网 endpoint（`api_server_endpoint` 为空）。

⇒ 结论不变：**跳板机只服务马尼拉**，SG 侧一律 `ack_remote.sh sg`。同样的约束在 `deploy/ops/ck_query.sh` 里也有体现——SG 写 ClickHouse 必须用 `-public` 端点，用 VPC 端点跨区不可达。

## 8. 排错速查

### 8.1 连不上跳板机（`ssh` 卡住 / 超时）

跳板机是**零入向**设计，22 端口靠临时规则按需放行：

```bash
bash deploy/ops/ops-access.sh --status        # 看当前入向规则 / 活跃会话
bash deploy/ops/ops-access.sh --allow-ssh     # 放行本机出口 IP（默认 120 分钟）
bash deploy/ops/ops-access.sh --deny-ssh      # 撤销，回到零入向
bash deploy/ops/ops-access.sh --gc            # 清理已过期的临时规则
```

> ⚠️ **已知坑（2026-09-29 实测）**：本机 HTTPS 探测出来的出口 IP 与 SSH 实际出口 IP **不是同一个**
> （前者 `194.56.225.91`，后者 `183.23.96.198`）→ 只放行前者会让 ssh 一直卡在 `Connecting`。
> `--allow-ssh` 已同时放行「阿里云视角（ActionTrail 权威）+ 本机视角」两类 IP。

### 8.2 其他常见现象

| 现象 | 原因 / 处理 |
|---|---|
| `kubectl` 报 401 / Unauthorized | 临时 kubeconfig 过 60 分钟了 → 重跑 `newapi-kube` |
| `newapi-kube` 报 `region can't be empty` | 用脚本自带的 `--region`（显式传 `ap-southeast-6`），别手写命令漏掉 |
| `kubectl exec` 报 `unable to upgrade connection` | 节点 SG 的 10250 规则被清掉了（`deploy/tasks/task22/sg_10250_fix.sh` 就是补这条的） |
| `exec` 连得上、`logs` 超时 | 同上，先查 `sg-mnl-app` 的 `10250 ← 10.0.0.0/16` 是否在 |
| `kubectl debug` 报镜像拉不动 | 换 `busybox:1.36`；仍失败改用 ACR 内网地址的镜像 |
| 跳板机 `psql` 连 RDS 超时 | 正常，见 §6，必须从 Pod 连 |
| `-it` 报 `the input device is not a TTY` | 在脚本/管道里跑时不要用 `-t`，改 `kubectl exec -i` + 直接跟命令 |
| `cannot exec into a container in a completed pod` | Pod 已 `Succeeded`（调试 Pod 跑完退出）→ 删掉重建，尾加 `-- sleep infinity`，见 §4.4 |
| `kubectl debug` 建完 Pod 立刻 Succeeded | 同上，缺保活命令；`-- sleep infinity` 必须在 `--` 之后 |
| 控制台容器组列表看不到调试 Pod | 状态筛选默认只显示 Running → 改「全部」或勾 `Succeeded`，见 §4.5 |

## 9. 红线（别踩）

1. **不要给 `sg-mnl-app` 加 22 入向**。节点不需要被 ssh；要宿主 shell 用 `kubectl debug node`。
2. **不要留下 `node-debugger-*` Pod**。它是 privileged + hostNetwork，用完立刻删。
3. **不要开 `0.0.0.0/0` 入向**。任何"为了让某台机器连上"的临时放行，都必须是 `/32` 源 + 带过期时间，用完撤销（`deploy/ops/ops-access.sh` 就是这个模式）。
4. **凭据不进 Git、不进聊天记录**。DB 密码 / AK 从 KMS 取。
5. **生产操作前先确认在哪个 context / namespace**：`kubectl config current-context`、`kubectl -n new-api get pods`。跳板机上只有一个集群，但习惯要养。
6. **只读优先**。能 `get`/`describe` 查明白的，不要上来就 `delete` / `edit`。
