## 一、P0 必改项（阻断上线，先于 D1）

### P0-1 数据库连接池收敛层整节丢失 —— 全案最大漏洞

`impl_deploy.md` 7.2 资源清单明确有一行「连接池收敛层：RDS 数据库代理（独享型）或 ACK 内自建 PgBouncer 3 副本」，并由 7.4.5 全节（约 220 行）给出三条不变量、容量换算、监控指标、排水流程与 ACK 清单。**本表 29 + 18 项资源、39 项任务中，一条都没有**，却把新加坡 `SQL_MAX_OPEN_CONNS=150`（新加坡表 #15）单独抄了下来 —— 保留了约束的表象，删掉了满足约束的手段。

量化后果（源文档口径，可直接复算）：

| 场景 | 计算 | 结果 |
| --- | --- | --- |
| 主站点扩到 HPA 上限 16 副本 | `SQL_MAX_OPEN_CONNS(300) × 16` | **4,800 条** PG 连接 |
| 备 region 接管到 24 副本 | `300 × 24` | **7,200 条** |
| RDS 16C64G 可承载 | 源文档按 `max_connections = 800` 取值 | 上限的 **6 ~ 9 倍** |

`SQL_MAX_OPEN_CONNS` 只能约束**单个进程自己**（`model/main.go:211-213` 经 `sql.DB.SetMaxOpenConns`），约束不了"副本数 × 每副本连接数"的总量。PG 是"一连接 = 一后端进程"，超限后新连接直接 `FATAL: too many connections`，已有连接性能同步劣化 —— 即 7.4.5 标题所说的"连接打爆导致整站不可用"。

同时丢失的还有四项配套，缺一即等于该层未落地：

1. **I-1 / I-2 / I-3 三条不变量**（7.4.5.1）。最易漏算的是 I-3：PgBouncer 副本之间**不共享**后端连接，真实 PG 连接是 `default_pool_size × 池副本数`（`60 × 3 + 预留 40 ≈ 220 ≤ 800 × 0.8`），不是 `60`。表里连 RDS `max_connections` 的核算动作都没有（7.2 明确要求"`max_connections` 按主站点 + 备 region 连接总和核算"）。
2. **上线前的真实 PostgreSQL 兼容性实测**（7.4.5.4）：pgx 默认 `QueryExecModeCacheStatement` 缓存命名预处理语句，在 `pool_mode=transaction` 下后端被换走会偶发 `prepared statement "pgx_N" does not exist`，**且只在 DDL 或主备切换后偶发**。源文档给了 4 步实测法（含 `pg_terminate_backend` 主动杀后端），并写明「未在真实 PostgreSQL 上完成本小节验证前，不得声称连接池方案已落地」。5 天计划里无此任务。
3. **池层 6 项告警指标**（7.4.5.5：`cl_waiting`、后端利用率、客户端余量、认证/协议失败、主库真实连接、`sv_lifetime`）—— 本表 #23/#26/#32 的观测清单里没有。
4. **master 迁移必须绕开事务池**（7.4.5.4）：本表 #18「部署 master 并跑通 AutoMigrate」未声明 `SQL_DSN` 直连 RDS 这一前置条件。

**要求**：马尼拉 + 新加坡各补 1 项资源（RDS 代理或 PgBouncer 3 副本，固定副本数、**禁止挂 HPA**），落地计划补 3 项任务（池部署 / I-2·I-3 复算 / prepared-statement 实测），观测补 6 项指标，并把 7.4.5.2 的推荐写进来 —— 新加坡备 region 经公网读写主库，源文档要求**额外加一层自建池**，把 `24 × 300 = 7,200` 条客户端连接收敛为 8–16 条跨区后端连接，同时避免接管瞬间的跨区 TCP 重连风暴。

### P0-2 节点数 / 配额 / HPA 上限三者互相矛盾，扩容必然 Pending

本表马尼拉 #12 写「ECS ≥ 4 节点」＋备注「HPA min 4 / max 16」，但**全文没有 Cluster Autoscaler / 节点池自动伸缩的任何条目或任务**。源文档 7.2 对该组合有专门警告：

> 节点池必须开启自动伸缩，否则 HPA 扩到上限会因无节点而 Pending；节点数按 Pod **`requests`** 反算并留 ≥ 20% 系统组件余量，`limits` 不参与反算。

按源文档 8.5 的推导链复算：

| 步骤 | 源文档口径 | 本表口径 | 差异 |
| --- | --- | --- | --- |
| 主站点 `maxReplicas` | 16（min 4 → 峰值 3 倍 = 12 → 上取整留灰度余量 = 16） | 16 ✓ | 一致 |
| 主站点节点下限 | `16 × 2 vCPU ÷ 7.9 可分配`，留 20% → **≥ 5 节点**；7.2 售卖区间 **4–8** | **≥ 4 节点**，无自动伸缩 | **4 节点装不下 16 副本**（4 × 7.9 = 31.6 vCPU < 16 × 2 = 32 vCPU，还没扣系统组件） |
| 备 region 接管上限 | **24 副本 = 16 × 1.5**（全篇唯一权威口径）→ **≥ 7 节点**；7.2 区间 2–12 | **只排 2 副本**，"冷备可置 0 并预留扩容预案" | **"24 副本"这个目标在本表完全不存在** |
| 配额申请（清单 #7） | 主站点 8 节点 = 64 vCPU；备 region 12 节点 = 96 vCPU | 马尼拉 ≥ 64 ✓ / 新加坡 **≥ 32**（= 4 节点） | 新加坡配额按常态 2 节点报，**接管期直接不够** |

**要求**：补节点池自动伸缩资源与任务；马尼拉节点下限改 ≥5（或明确"常态 4 + 弹性至 8"）；新加坡补"接管容量目标 24 副本 / ≥7 节点"，配额工单同步上调到 ≥96 vCPU；并按 8.5 的反算规则提示——若 D5 压测实测的日均容量基准不等于 4 副本，必须同步上修推导链第 3/4/5/6 步，**不允许只改一处**。

### P0-3 上游出口写反：本表用 GA，权威依据三处明确禁用 GA

总览 R11：「上游出口：马尼拉 / 新加坡 NAT 固定 EIP 池 → **全球加速 GA** → OpenAI / Anthropic / Google / Azure / AWS 等」。

`impl_deploy.md` 在 7.1、7.2、7.10 三处以独立段落 / 加粗句强调**不使用 GA**，理由是结构性的而非偏好性的：

- GA 的加速段是「客户端就近接入**我的服务**」，终端节点是**我方后端**，改善的是入站，无法改善「我方 → 上游」的出站跨境链路；
- 若强行把上游地址配成 GA 终端节点，会把上游看到的源 IP 变成 GA 侧地址 —— **直接破坏固定 EIP 白名单模型**（本表 #5/#新加坡 #3 的整条供应商白名单交付前提同时失效）；
- 同时破坏上游基于域名的 SNI / TLS 校验；
- 并新增一笔按出站流量计费的开销，而 LLM 流式出站带宽极大（源文档 8.5 口径：单路 20–50 KB/s，1000 并发 ≈ 40 Mbps）。

本表也没有任何 GA 资源、配额、任务、成本条目 —— 说明这一行是残留错误，但它恰好是全表对「上游出口」的**唯一**一句话描述，是决策者最容易照抄的一格。跨境链路质量的正确兜底是**多供应商 / 多渠道路由与重试**（源文档 8.4），而本表风险清单里也没有这一条。

**要求**：R11 改为「NAT 固定 EIP 池 → 公网直出 → 供应商（不使用 GA，理由见 impl_deploy.md 7.1）」，并把「多渠道路由 + `RetryTimes` 换渠道 + 渠道自动禁用」作为出站链路质量的兜底措施补进风险表。

### P0-4 SLA ≥99.95% 的前提条件被裁掉，口径却照抄

总览 R12 承诺「目标 SLA ≥ 99.95%（月度不可用预算 21.6 分钟）」。源文档 8.2 的可用性串联推导以下列条件为前提：

> **结论：双主站点 + 新加坡备 region + 每主站点 ≥ 4 副本 + RDS 高可用 + Redis 降级改造** 是达成 99.95% 的最低配置；**单区域 3 副本约等于 99.9%（99.95 不达标）**。

本表已把范围收敛为「单主站点（马尼拉）+ 单备 region」，曼谷主站点不在内（R9 只保留"新加坡可与泰国备共用集群"），推导链的第一项即不成立。

更关键的是数据面：**RDS 只存在于马尼拉**（这条本身是对的、且是红线设计），因此马尼拉发生 **region 级** 故障时，GTM 把流量切到新加坡后，备 region 应用虽然活着但连不上任何数据库 —— 本表所谓「区域级容灾」实际只覆盖应用层。同时 8.2 的「Redis 降级改造」在本表被降级为 G8 待办项（承认 Tair 故障 fail-closed），而源文档写明"Redis 故障时限流 fail-closed 返回 500，**实际会把可用性拉低到 Redis 的可用性**"。代码已核实该风险真实存在（见第五节）。

另外源文档 8.1 排除项 ⑤/⑥ 的概念（**新加坡是 PH 备与 TH 备的共享故障域**；两地同时需接管时新加坡无 48 副本容量）在本表完全没有继承 —— 风险表 R21 只谈了成本，没谈共享故障域与零容灾窗口。

**要求**：三选一，并书面记录：① 把 SLA 承诺改为与单主站点口径匹配（如 99.9%）；② 补 8.6-7 的共享故障域演练 + Runbook，把 8.1 排除项 ⑤⑥ 一并继承；③ 保留 99.95% 则必须补数据面跨区域冗余（见 P1-6）。不允许沿用现口径。

## 二、P1 整块漏项（源文档有、本表无，或两源皆需补）

### P1-1 「工期可行」结论是负载率 100% 的自我否证

负荷校验行用的是 `=SUMIFS($V$4:$V$42, $D$4:$D$42,"人员A", $G$4:$G$42,"<=n", $H$4:$H$42,">=n")`，逻辑正确。我按 39 项任务独立重算（脚本见第六节）：

- 人员A = **40 人时**，人员B = **40 人时**，合计 **80**
- S1–S10 **每个时段都是 4/4 满格，一格不空**
- 产能单元格 `K49 = 2*5*8 = 80`，判据 `IF(J49<=K49,"工期可行：总投入未超 2 人 × 5 天产能")` → 80 = 80 恰好命中绿灯

这不是"可行"，是**无任何余量**。且这 80 人时不含：每日站会、**T-3 门禁项要求的"每日 18:00 跟进实名 / 配额工单"**（该动作在本表分配给了"项目负责人 / 运维负责人"，但落地计划里无人时归属，而 R51 声称门禁"不占用 5 天工期人力"）。表格自己在 R15 写「高：无缓冲日」、风险表 R20 写「建议预留 D6 作为缓冲日」，却在结论格给绿灯 —— 判据与结论互相打脸。

**要求**：判据改为 `J49 <= K49 * 0.8`（即 80% 负载上限），结论格改为「负载率 100%，零缓冲」；把 D6 缓冲日写进默认排期而非"建议"；给 T-3 跟进动作分配人时。

### P1-3 WAF 接入方式与 `TRUSTED_PROXIES` 整节决策缺失

`impl_deploy.md` 7.1.1 用一整节 + 三方案对比表处理这件事，本表只字未提：

| 方案 | 结论（源文档） |
| --- | --- |
| ① WAF 云原生 / 服务化接入 ALB（证书只在 ALB 一份、无回源跳） | **首选** |
| ② WAF CNAME 接入 + **强制 HTTPS 回源** | 可售性不满足时的回退方案 |
| ③ WAF CNAME 接入 + HTTP 回源 | **一票否决** —— 该链路承载长期可用的 `Authorization: Bearer <API Key>`、session cookie 与个人访问令牌，明文段等于把可用令牌放到公网上，违反 OWASP ASVS V9 与 Session Management Cheat Sheet |

本表马尼拉 #7 只写「接入 api.example-ph.com」；而「网络与安全规划」`sg-mnl-alb` 入向 443 源 `0.0.0.0/0`、备注「终端用户与 **WAF 回源**」—— 这实际上已经隐含选了 CNAME 接入（方案②），却**没有写"回源段必须 HTTPS"**，也没有证书双份的真源管理（源文档警告：CAS 云产品部署是异步任务，续期窗口内会出现"WAF 已换新、ALB 仍是旧证"，因此自动续期提前量须 ≥30 天，并把"到期 21 天内两产品证书指纹不一致"列入告警）。本表 #17/#18 恰恰把证书"分别部署至 ALB、WAF、DCDN"，是三份人工副本，与源文档"单一真源、两套签发链路不并存"的原则冲突。

**最严重的是 `TRUSTED_PROXIES` 完全缺失**。源文档：选定 WAF 接入方式后必须据此重算 ConfigMap 里的 `TRUSTED_PROXIES`（当前 `10.0.0.0/8`），否则取到的是代理 IP，**`GLOBAL_API_RATE_LIMIT`、WAF CC 阈值、审计日志的 IP 归属同时失真 —— 这类失真不会报错，只会让限流和风控静默失效**。对一个按 token 计费的 AI 网关，这等于计费风控失明。

**要求**：新增一行「WAF 接入方式」决策项（默认方案①，附回退路径）+ 一条 D1/D2 任务（按所选方式重算并验证 `TRUSTED_PROXIES`，验收标准 = 用带真实客户端 IP 的请求验证限流按客户 IP 生效）。

本表 #14 配好了 PITR 与全量/WAL 归档，但**5 天内没有任何一次"真的从备份恢复"的动作**，备份可用性未证。而里程碑 M5 却把「演练报告（含 RTO/RPO）」列为验收证据 —— 没有测量动作，该证据无法产出，RPO/RTO 只能靠猜。

### P1-5 成本结构整节丢失（7.10）

本表无成本 sheet、无月成本估算、无计费模式选择（源文档：按量转包年包月可省 **30–40%**）。但：

- 落地计划 #35 要交付「成本看板」—— 无基准值，看板上线即空转；
- 裁剪预案 #5 的触发条件是「成本优先」、#2 是「成本或工期紧张」—— **没有成本基线，这些决策无法判定**；
- 本表 #7 配额、#R21 风险、里程碑 M5 全部引用了成本概念，却无一处量化。

已知的主要变量（源文档 7.10 口径，需实际报价校准）：ALB LCU 与**出站带宽**（LLM 流式出站，40 Mbps / 1000 并发）、跨区公网 DB 读写流量（接管期）、KMS / WAF 企业版 / GTM 旗舰版 / DCDN / ClickHouse ×2 / Tair ×2 的固定项、以及"上游 token 独立列预算"。

**要求**：补一个「成本结构」sheet（常态 / 接管期两档），至少给区间估算与包年包月 vs 按量对比；备 region 冷备方案（裁剪 #5）的省额与 RTO 代价一并量化。

### P1-6 跨区域数据库冗余被误列为红线

新加坡表 R22 与马尼拉表 #16 把「禁止本地库、**只读副本**、DTS 双向链路」并列为红线。这个并列在逻辑上站不住：

- **DTS 双向 / 双写** → 会产生双写冲突、自增序列错乱、计费对账分裂 → 禁用理由成立 ✓（源文档 7.1 也正是这么论证的）；
- **跨区域只读副本（单向 主→备）** → 不存在回写、不会双写、不产生对账分裂 → 套不上被禁的理由。

而它恰恰是唯一能缓解 P0-4 数据面单点的手段（接管期备 region 至少可读，写入按窗口降级）。源文档 7.2 本身也保留了「可选每站点 1 只读实例」—— 本表马尼拉 #16 同样写了"只读实例（可选）"，与新加坡 R22 的"禁止只读副本"用同一名词得出相反结论（本表内部自相矛盾）。

**要求**：红线收窄为「禁止双写与双向同步链路」；把「跨区域只读副本」单列为**已评估、待决策**项，并写明取舍（RPO > 0、成本、接管期读/写降级策略），而不是用一条红字封掉。

### P1-7 环境矩阵（7.9）与三数据库强制验证缺失

源文档 7.9 定义了 dev / **staging（主站命名空间 `new-api-staging`，复用主站 RDS 的逻辑隔离 schema，不新建实例）** / **perf（`new-api-perf` + mock 上游）** / prod mnl / prod bkk / standby sg 六行矩阵，每行有门禁。本表只有 prod 两套 region，因此：

- 灰度发布没有 staging 前置验证环境，canary 直接在生产集群上跑；
- 压测（#33）没有 perf 命名空间与 mock 上游，压测会打到真实 RDS 与真实上游供应商（既是成本也是数据风险）；
- AGENTS.md / 7.9 强制的**真实 SQLite + MySQL ≥5.7.8 + PostgreSQL ≥9.6 三库矩阵**、以及"迁移需在新建库 + 上一版本存量库各跑、至少启动两次证明幂等"—— 本表只保留了"两次幂等"（#18），三库矩阵与存量库迁移路径无任务。

### P1-8 错误预算管理有看板、无管控规则（8.3）

#32 交付「SLO / 错误预算看板」，但源文档 8.3 的四档燃尽规则未继承：`<50%` 正常发布 → `50–80%` 双人审批 + 灰度观察窗口翻倍 → `>80%` 冻结非必要发布 → **燃尽全部预算则停止所有变更、进入稳定期并触发正式事件复盘**。没有这套规则，看板只是数字，发布行为不受任何约束。

### P1-9 上游模型供应商的账号 / Key / 提额 完全不在清单内

「账号与域名申请」19 项覆盖了阿里云侧一切，但**没有任何一项**关于 OpenAI / Anthropic / Google / Azure / AWS 的商业账号、发票、**速率与额度提升申请**、以及合规条款。对 99.95% 的承诺而言，上游配额才是真正的天花板；且这类审批周期常常**比企业实名认证更长**，而后者已被本表列为"5 天工期最大外部风险"。

相关缺口还有两处：马尼拉 #20 KMS 凭据清单列了「支付渠道密钥」却没列**上游渠道 API Key**（new-api 的渠道密钥存 DB 加密字段，需说明其录入、加密与轮换路径）；落地计划 39 项里**没有"配置渠道 / 模型映射 / 分组倍率"这项任务**，而这是网关能出 token 的前提，属上线必做项。

### P1-10 计费与支付链路的上线前联调无验收

本表只有 #37「主库故障切换演练 → 额度对账一致」一处触及计费。缺：真实支付渠道沙箱联调（菲律宾本地通道 + 国际卡）、兑换码 / 充值 / 退款 三条路径的端到端验证、账单与额度的一致性抽查。WAF 侧只写了"放行支付回调路径"，但回调域名、签名校验、幂等（重复回调不重复入账）无一项进入验收。这是营收正确性，风险等级不低于可用性。

### P1-11 数据合规与跨境传输零条目

部署在菲律宾、备 region 在新加坡，至少两处需要显式确认（本表全无）：

- 菲律宾 **Data Privacy Act of 2012（RA 10173）** 及 NPC 的注册 / 申报义务；
- **跨境数据传输**：新加坡备 region 在接管期读写菲律宾用户的个人数据（账号、用量、日志），属个人信息出境，需法律依据（同意 / 合同必要 / 合法利益）与 DPA；
- AI 网关的日志留存含 prompt / completion，涉及 PII → 与 P2-7 的日志脱敏是同一件事。

若这两项未确认，G0 之外还有一条"法务门禁"，其周期可能长于实名。

### P1-12 DCDN 回源与 bucket 的 HTTPS 约束丢失

源文档 7.2 DCDN 行：**回源协议显式 HTTPS，OSS bucket 开启"仅允许 HTTPS"**。本表 #10 只写了缓存策略（`index.html` no-cache + 指纹 chunk 7 天 ✓），#19 只写了 ZRS / 版本 / 归档 / 防盗链 / 签名 URL。丢的是那条"防降级明文回源"的约束 —— 与 P1-3 的 WAF 回源是同一类问题（凭证在中间段裸奔）。

## 四、P3 增强建议（不阻断，但提升可信度）

1. **可观测缺上游维度**：#23/#26/#32 全是自身指标。AI 网关真正先炸的是上游 —— 补「每渠道成功率 / P95 / 429 数 / 自动禁用次数」「客户维度成本告警」（源文档 R-30 明确要求建立客户维度成本告警）。
2. **缺 Anti-DDoS 定位**：只上 WAF 企业版抗 L7。面向公网、且易被刷的 AI 网关应显式写明"仅依赖 ALB 自带基础防护，Anti-DDoS Pro 不在本期范围"，作为已接受风险登记。
3. **缺回切（failback）程序**：#36 只演"切过去"，无"回得来"。含 DNS TTL 回切、主站数据一致性复核、以及避免 flapping（接管期间主站恢复即被抢回）。源文档 8.1 也提醒需"人工确认后手工降级非核心功能"，本表无对应 Runbook 项。
4. **缺 schema 变更兼容性规范**：canary 与 stable 共存期间由 master 独跑 AutoMigrate ✓（设计正确），但未规定"DDL 必须向后兼容前一个发布版本"。灰度期新 schema + 旧 Pod 混跑是典型事故源。
5. **缺镜像准入策略**：马#13 写了"开启镜像扫描与签名"，但无准入侧（Kyverno / OPA / ACK 策略引擎）拦截未签名镜像，扫描等于只报告不阻止。
6. **KMS 是凭据单点**：KMS / RRSA 不可用时 ExternalSecret 无法刷新，Pod 一旦重启即拿不到密钥。应在 Runbook 写明"集群内保留最后一次 Secret 快照 + 应急直投凭据流程"。
7. **GTM 切换语义要写清**：`切换 ≤ 60s` 依赖权威 DNS TTL 与中间 resolver 缓存，需明确 TTL 取值（≤60s），并注明"仅对新连接生效、存量 SSE 长连接不迁移"（客户端需重连语义）；且 GTM 只探 `/api/status`，**无法感知"备 region 活着但主库链路断"**，所以 #39 的"链路不健康即阻断接管"必须配套一条"如何从 GTM 地址池摘除备 region"的 Runbook（当前只有阻断，没有摘除动作）。
