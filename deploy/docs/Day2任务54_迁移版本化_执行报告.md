### 4.4 ★ 锁观测（本卡最有价值的一条）

**观测窗口**：`migrate down 4`（5→1，执行 4 个 down）+ `migrate up`（1→5，**重放加列 + CONCURRENTLY 建索引 + 2000 行回填 + 删列**），
期间并发跑 **320 次 `UPDATE drill_accounts`**（每 20ms 一次，pg8000 独立连接），另一路每 200ms 采样 `pg_stat_activity`。

```json
{
  "samples": 42, "lock_events": 0, "max_lock_wait": 0, "max_active_sec": 0.059,
  "writer": {"n": 320, "p50_ms": 6.33, "p95_ms": 6.53, "max_ms": 7.34},
  "migrate": [
    {"cmd":"down 4","rc":0,"sec":0.116,"out":"5/d …(15.9ms) 4/d …(43.8ms) 3/d …(59.0ms) 2/d …(73.2ms)"},
    {"cmd":"up",    "rc":0,"sec":0.164,"out":"2/u …(15.1ms) 3/u …(30.4ms) 4/u …(108.7ms) 5/u …(123.2ms)"}
  ]

```

**判定**：整个 expand→migrate→contract 全流程，**并发业务写零锁等待、延迟无抬升**（p50 6.33ms 与无迁移时一致）。
这就是「`CREATE INDEX CONCURRENTLY` + 分批回填 + 无锁 DDL」策略的直接可测收益 —— 对照卡片坑 1
（普通 `CREATE INDEX` 持 SHARE 锁会让 `logs` 级表分钟级不可写，直接击穿 21.6 分钟/月的可用性预算）。

## 五、踩坑（5 条，全部已固化进 `migrations/README.md` 与 CI 门禁）

### 坑 1｜`-- +migrate NoTransaction` **在 golang-migrate 里不存在**（最贵的一条）

首跑照抄网上写法，文件首行加 `-- +migrate NoTransaction`：

```
$ migrate up
1/u baseline_marker (24.6ms)
error: migration failed: CREATE INDEX CONCURRENTLY cannot run inside a transaction block in line 0: -- +migrate NoTransaction
$ migrate version
2 (dirty)
```

- 该注解是 **goose** 的（`-- +goose NO TRANSACTION`），golang-migrate 无此语法（源码 `source/parse.go`、`source/migration.go`、`database/driver.go` 均无 `NoTransaction`）。
- 后果不只是报错：库被钉在 **`version 2 (dirty)`**，后续所有 `up` 都被拒（`Dirty database version 2. Fix and force version.`）。
- **恢复姿势**：`migrate force <上一个成功版本>`（只改 `schema_migrations`，不执行 DDL），**禁止手改表**。

### 坑 2｜CONCURRENTLY 必须**独占一个迁移文件**

官方口径（`database/postgres` README）：默认 `x-multi-statement=false` 时，驱动把**整个文件**当作**一条** statement 交给 `Exec`；
多条语句挤进一次 `Exec` = 隐式事务块 ⇒ 加第二条语句必然失败。

- 正确做法：`000002_expand_add_nickname`（加列，事务内）与 `000003_expand_concurrent_index`（建索引，事务外）**分成两个文件**。
- `x-multi-statement` **不是**「关闭事务」开关，打开它反而把多语句显式拆成多条 → 各语句独立 → 事务语义更难推理。

### 坑 3｜★ 采样连接停在 `idle in transaction`，**把要观测的迁移自己卡死**

首跑 `observe.py` 永不退出，云助手任务停在 `Running`，只能 `StopInvocation` 强杀。诊断发现：

```
pid=8409  usename=newapi_migrate  state=idle in transaction  wait=Client/ClientRead
          query="select coalesce(max(extract(epoch from (now()-query_start))),0) from p…"
```

- 根因：**pg8000（以及 psycopg 默认）每条 `execute` 后事务保持打开** ⇒ 采样连接停在 `idle in transaction`；
  而 **`CREATE INDEX CONCURRENTLY` 必须等所有并发事务结束**（它要取快照）⇒ 采样连接把迁移无限期挂住。
- 修复：所有观测/断言连接统一 **`c.autocommit = True`**，并加 `statement_timeout=5s`、线程 `daemon=True`、90s 硬超时兜底。
- **这条对生产同样成立**：任何长期持有 `idle in transaction` 的客户端（连接池泄漏、调试 session）都会让线上
  `CONCURRENTLY` 迁移卡死。⇒ 已进 `migrations/README.md` §3。

### 坑 4｜节点工作目录必须每轮清空

`/tmp/mig54` 残留上一轮的 `000003_backfill_*.sql`，与新一轮的 `000003_expand_concurrent_index.*` 版本号撞车：

```
error: failed to open source, "file:///tmp/mig54": duplicate migration file: 000003_expand_concurrent_index.down.sql
```

⇒ body 第 2 步改为 `rm -rf "$MIGDIR"; mkdir -p "$MIGDIR"`。（migrate 对目录做**全量扫描**，不看时间戳。）

### 坑 5｜节点 Python 3.6 与 PG 语法两个小雷

- `subprocess.run(capture_output=True, text=True)` 是 **Python 3.7+**；节点是 **3.6.8** ⇒
  `TypeError: __init__() got an unexpected keyword argument 'capture_output'`。
  改用 `stdout=PIPE, stderr=STDOUT, universal_newlines=True`。
- `select <单个表达式> … order by 1,2` 非法：`ORDER BY position 2 is not in select list`（PG 42P10）。
