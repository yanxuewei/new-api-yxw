# 阿里云 GTM 3.0 场景对比 · 「主备容灾」vs「多活负载」

> **日期**：2026-10-13
> **场景**：云解析 DNS → 全局流量管理 3.0 →「创建接入域名」→ **场景选择** 弹窗
> **本文回答**：这两个场景有什么区别 / 各自最佳场景 / 优缺点 / 最佳实践 / 全部坑点
> **关联本项目**：`deploy/aliyun/ph/gtm-address-pool.md`（G6 模板）· 指南 §8.4 任务 21（GTM 先只挂马尼拉）· 任务 36（备区接管演练）
> **结论先行**：**本项目只能选「主备容灾场景」** —— 因为底层数据面（马尼拉 RDS 单库）不支持多写，选多活会退化成"假多活"（见 §5）。

---

## 0. 一个必须先说清楚的认知

弹窗里的 6 个"场景"**不是 6 种不同的底层机制，只是预设模板**。它们最终都落到同一组配置上：

```
接入域名(GTM CNAME) + 地址池(含池内地址与权重) + 地址池间的负载策略 + 探测模板 + TTL
```

| 场景名 | 实质 = 地址池间负载策略 |
|---|---|
| 仅探活 | 不切换（只告警），单池 |
| **主备容灾** | **顺序**（主池 → 备池，主不可用才切） |
| **多活负载** | **权重 / 轮询**（多池同时服务，按比例分摊） |
| 单数据中心+多运营商出口 | 顺序/就近 × 运营商分层 |
| 主/备数据中心+多运营商出口 | 顺序 × 运营商分层 |
| 多数据中心多活+多运营商出口 | 权重 × 运营商分层 |

⇒ **选场景前先问一句："我的数据面能不能多写？"** 答案决定选哪个，而不是反过来。

## 1. 核心差异对照（一表看懂）

| 维度 | **主备容灾**（顺序） | **多活负载**（权重/轮询） |
|---|---|---|
| 池间语义 | 主池生效，**同一时刻只有一个池在服务** | **全部池同时服务** |
| 生效条件 | 主池被判"不可用"才切 | 一直按权重分摊 |
| 用户分布 | 全部集中在主池 | 按权重分散到各池 |
| 单池容量要求 | **每个池都要能独立承载全量**（N+1 冗余） | 各池合计承载全量，单池只需承载份额 |
| 数据面要求 | 备池能**接管读写**（或至少能读+可写回主） | **必须支持多写**（或明确单写多读的分片方案） |
| 常态成本 | 高（备池空转）或降为冷备（但 RTO 变长） | 低（资源利用率高） |
| 故障影响面 | 切换瞬间有窗口；切不过去就全挂 | 单池故障只损失**部分流量**，无需切换 |
| 切换依赖 | 探测 + TTL + 递归 DNS 缓存（**慢，分钟级**） | 不依赖切换 |
| 复杂度 | **低** | **高**（数据一致性 / 会话 / 幂等 / 配额 / 限流） |
| 典型 RTO 口径 | 秒级（GTM 判定）→ 实际分钟级（DNS 缓存 + 长连接不迁移） | 无需切换，但**要求各池随时可用** |
| 适用前提 | 单点写入 / 强一致 / 主备架构 | 无状态或可多写 / 分片 / 最终一致 |

**一句话**：**主备是"用冗余换简单"，多活是"用复杂度换资源利用率与影响面"。**

## 2. 各自的最佳场景

### 2.1 选「主备容灾」当

- **数据面是单点写入**：一个主库、主备复制、不允许双写（**本项目就是这种**）
- **会话/计费/额度等强一致要求**，双写会错账
- **流量不大、成本敏感**：备站常态 2 副本足够（不需要按份额分摊）
- **需要"区域级容灾"而非"负载均衡"**：目标是把用户从坏掉的 region 挪走
- 第三方依赖只有一套（如上游白名单、支付回调地址只登记一处）

### 2.2 选「多活负载」当

- 业务**无状态**或数据面**天然可分片**（如按用户 ID 分片、各池独立库）
- 目标不是"容灾"而是**提升整体吞吐 + 降低单池故障影响面**
- 各池之间**幂等、可去重**，双写不会产生资损
- 有**容量与成本优化诉求**（备站资源不想空转）
- 有成熟的**多活治理能力**（统一配置、灰度、流量染色、按池可观测）

> ⚠️ 如果业务"看起来无状态"但下游有单点库 —— 那就**不是多活场景**，而是"多活接入 + 单活数据"，属于**最危险的一种组合**（见坑 A1）。

---

## 3. 优缺点

### 3.1 主备容灾

**优点**
- 数据一致性压力小（同一时刻只有一处写）
- 配置简单，心智模型清晰
- 故障时行为可预测（全切或全不切）
- 与"上游 IP 白名单""支付回调地址"这类单点登记天然兼容

**缺点**
- **备池常态空转**（2 副本 + 节点 + 数据库连接），成本换可用性
- 若改冷备（0 副本），**RTO 从秒级掉到分钟级**（要等节点扩容 + Pod 拉起 + 池预热）
- 切换本身是**分钟级**事件（DNS 缓存），不是秒级
- 主池容量上限 = 单池容量，**无法靠备池分担高峰**

### 3.2 多活负载

**优点**
- 单池故障**影响面小**（只损失该池份额），无"切换窗口"
- 资源利用率高，可省常态成本
- 天然分散高峰，容量上限 = 各池之和
- DNS 层无需变更，规避缓存问题

**缺点**
- **数据面必须支撑多写**，否则产生错账/脑裂
- 会话、限流、缓存、上游配额全部要"按池"重新设计
- 出口 IP 数量翻倍 ⇒ **上游白名单、回调白名单、RDS 白名单都要按池登记**
- 观测复杂度上升（必须能按池切分指标）
- 灰度/回滚需要"权重"能力，不能只靠开关

---

## 4. 最佳实践

### 4.1 主备容灾（本项目采用的形态）

1. **池间策略 = 顺序**，主池放全部主站地址；**备池单独一个池**，不与主池混装。
2. **备池入池时机用"硬门禁"**，不要图省事提前加：
   - 本项目口径：**M4 接管演练通过前不得入池**；入池后**常驻但权重 0**。
   - 理由：0 副本 / 未预热的备池切过去**比不切更糟**（用户从"慢"变成"全 5xx"）。
3. **每池都要能独立承载全量**（含连接数预算），这是主备的成立前提。
4. **探测要探"业务可用"而不是"端口通"**：路径必须覆盖真实依赖（DB/缓存）。
5. **探测间隔 × 失败次数 要与 TTL 一起算端到端时间**，并把结论写进 SLA。
6. **备站预热**：连接池、本地缓存、上游 TLS 会话、限流桶，切流前打到稳态。
7. **回切要留观察窗**（本项目：回切后稳定 15 分钟再结束观察），防抖动来回切。
8. **强制演练**：把"切过去 + 切回来"当交付验收项（本项目任务 36），不演练就等于没有容灾。

### 4.2 多活负载（本项目不适用，供选型参考）

1. **先解决数据面**：改成可多写（分片/无冲突），或明确"单写多读 + 只把读流量分摊"。
2. **会话外置**：会话/令牌存 Redis 或 DB，且**密钥全局一致**（本项目 `SESSION_SECRET` 必须两地同源）。
3. **幂等 + 去重**：计费/扣额必须幂等（本项目 `BATCH_UPDATE_ENABLED=false` 是红线）。
4. **权重按容量与成本分配**，并保证能**一键归零**（应急）。
5. **灰度放量**：先 1% → 观察 → 放大，不要一次 50/50。
6. **出口与配额按池登记**：上游白名单、回调白名单、RDS 白名单都要覆盖各池出口 IP。
7. **按池打标可观测**：指标、日志、告警都要能分池，否则出问题分不清是谁。

### 4.3 两者共通

- **配置即代码**：接入域名/地址池/探测模板回写仓库真源（本项目 `gtm-address-pool.md`），禁止只在控制台改。
- **变更即演练**：任何池/策略变更都走"改配置 → 探测验证 → 演练切一次 → 记录"。
- **对外 SLA 用实测**，不要引用产品文案里的"秒级切换"。

## 5. 本项目为什么只能选「主备容灾」（关键判断）

| 约束 | 事实 | 对选型的影响 |
|---|---|---|
| 数据库 | **只有一个主库，在马尼拉**；新加坡不部署数据库（含只读副本与 DTS 都是红线） | 多活不可写 ⇒ 排除多活 |
| 计费一致性 | 双写会**双扣/超扣**（`BATCH_UPDATE_ENABLED=false` 红线） | 多活直接排除 |
| 会话 | `SESSION_SECRET` 必须全区域一致，否则切换后全员登出 | 属于"切换要治"的成本，不改变结论 |
| 备站容量 | 备站常态 2 副本，接管上限 = 主站 `maxReplicas 13 × 1.5 = 19.5 → 20 副本` | 满足"每池独立承载全量"⇒ 主备成立 |
| 延迟 | 马尼拉 RTT 5–15 ms；新加坡 30–45 ms（跨区写更差） | **绝不能把菲律宾用户分摊到新加坡** |
| 上游出口 | 马尼拉 4 + 新加坡 4 = **8 个 EIP**，须全部提交上游白名单并确认生效 | 多活会让白名单与配额复杂度翻倍 |

⇒ **结论：主备容灾（顺序）**。`pool-sg` 只作为**故障转移目标**，**绝不能填进主地址池集合**——否则 GTM 会按延迟/权重把用户分摊到新加坡，而新加坡比马尼拉慢 2–3 倍。

## 6. 坑点全集

> 分类：A 选型 · B 探测 · C 切换 · D DNS/记录 · E 数据一致性 · F 计费与合规 · G 运维 · H 本项目专属

### A. 选型类

| # | 坑 | 现象 / 后果 | 改进 |
|---|---|---|---|
| A1 | **把"多活"当高可用的默认答案，但下游数据面是单点** | 表面"双活接入"，实际"单活数据" ⇒ 读到旧数据、写冲突、错账；比单活**更危险**（问题被"看起来高可用"掩盖） | 先画数据流，确认是否可多写；不能多写就老实做主备 |
| A2 | 主备场景下把备池也放进"主地址池集合" | 用户被分摊到慢站点（本例：菲律宾用户跑到新加坡，RTT +25~30 ms） | 备池永远独立成池；池间策略选"顺序" |
| A3 | 用"权重"当"主备"（主池权重 100、备池 0 就以为主挂了会全切） | **权重不是顺序**：主池挂掉时若还有可用地址，权重分配仍会按比例，不一定全量切走 | 主备用"顺序"；权重只用于多活 |
| A4 | 单池内放多个地址却按"主备"心智配置 | 池内地址默认是"并列可用"，不是主备 | 池内多地址要明确权重/顺序语义 |
| A5 | 场景名当能力用（以为"主备容灾场景"自带了切换演练/回切保护） | 场景只是预设，**回切、观察窗、预热都要自己做** | 把演练与预热列进验收项 |

### B. 探测类

| # | 坑 | 现象 / 后果 | 改进 |
|---|---|---|---|
| B1 | **探测路径不反映真实依赖** | 典型：探 `/api/status` 但该接口不查 DB/Redis ⇒ 主库挂了 GTM 仍判健康 ⇒ **不切换** | 探"含依赖"的探针（本项目要求 G8 补 `/readyz` 后**必须切换探测路径**） |
| B2 | 探测间隔/超时/次数 与 TTL 没一起算 | 例：15 s × 连续 3 次 = 判定 45 s，再加 TTL 60 s ⇒ 端到端最坏 >105 s，但对外承诺了"60 秒" | 把"判定 ≤45 s + TTL 60 s + 递归缓存"三层分开写进 SLA |
| B3 | **探测源 IP 未加白** | 探测被 WAF / CC / 安全组 / 应用限流拦 ⇒ 误判不可用 ⇒ **抖动切换**（最恶劣的故障形态） | 探测源加入所有拦截层白名单；⚠ 本项目 `/api/status` 落在应用全局限流分组内，**探测与 ALB 健康检查共用同源 IP 时须合并计预算** |
| B4 | 探测频率与额度成本失控 | 探测点数量 × 频率 = 探测请求量，既是成本也是**限流压力** | 收敛探测点数与频率；给探测单独留预算 |
| B5 | 用 ALB 的 DNS 名做地址（域名型地址） | ALB DNS 解析异常时，探测直接判失败（把 DNS 抖动当业务故障） | 明确"地址类型"语义；对 DNS 依赖留观测 |
| B6 | 只探"200/端口通"，不探业务语义 | 上游全挂但网关仍 200 ⇒ 不切 | 加业务断言（`success:true` / 版本号 / mock 上游固定回包） |
| B7 | 探测点覆盖不足 | 海外探测点少，且**某些地域探测点不可用**（本项目需实测确认马尼拉探测点） | 实战前用"探测异常告警"反查探测点是否真在工作 |
| B8 | 探测判据只看"单点失败" | 单点网络抖动就判不可用 ⇒ 误切 | 用"连续 N 次失败 + 失败比例阈值"双条件 |

### C. 切换类

| # | 坑 | 现象 / 后果 | 改进 |
|---|---|---|---|
| C1 | **把 TTL 当 RTO** | 递归 DNS 实际缓存 5–30 分钟（取决于运营商/公共 resolver）⇒ 用户侧感知的切换远慢于 TTL | 三层延迟模型：①GTM 判定与摘除 ②递归 DNS 缓存 ③**已建长连接/SSE 不迁移**（RTO 真实上限）；**对外只承诺第③层实测值** |
| C2 | 切过去备站"没热" | 0 副本 / 冷连接池 / 空缓存 ⇒ 切过去 5xx，**比不切更糟** | 硬门禁：接管演练通过才入池；切流前 warmup（连接池/缓存/TLS/限流桶） |
| C3 | 没有回切观察窗 | 抖动来回切（flapping），用户被反复甩 | 回切后稳定观察（本项目 15 分钟）再收尾 |
| C4 | 未设"池可用地址最小数量阈值" | 例如池里只有 2 个 ALB IP，阈值设 2 ⇒ 单 AZ 抖动把**整池**判不可用 ⇒ 误切跨区 | 阈值设 **1**，让单 IP 抖动只影响部分流量 |
| C5 | 人工强切无审批 | 误操作把主站流量切走 | 强切纳入破坏性操作：远程第二方核准 + 留痕 |
| C6 | 切了但没告警/没记录 | 事后无法复盘，SLA 无法举证 | 切换动作 + 触发原因 + 时间戳全部留档 |

### D. DNS / 记录类

| # | 坑 | 现象 / 后果 | 改进 |
|---|---|---|---|
| D1 | 接入域名的 CNAME 与同名 A 记录冲突 | 解析不生效或结果不确定（同名 A/CNAME 互斥） | 切换前先清理冲突记录；`dig` 权威 + 递归双验 |
| D2 | TTL 一味求小 | 权威解析压力大、查询成本高 | TTL 与"可接受切换窗口"折中（本项目 60 s） |
| D3 | 各站点直接写 A 记录指向 EIP（而非 CNAME 到 ALB/GTM） | ALB 增删可用区或释放 EIP 后记录变哑 | 优先 CNAME 到 ALB DNS 名；若用 A 记录须把"IP 变更"纳入巡检 |
| D4 | 证书/SNI 没覆盖全部入口域名 | 切换后 HTTPS 报错（比 5xx 更难排查） | 用通配符证书覆盖所有入口子域（本项目 `*.likha.hk`） |
| D5 | 域名归属验证/接入域名被占用 | 建不了接入域名 | 提前做归属验证，别等到切换当天 |
| D6 | 只测 www 不测裸域/其他子域 | 切换后裸域仍指向旧池 | 把所有对外域名一起纳入验证清单 |

### E. 数据一致性类（多活特有，主备也需关注）

| # | 坑 | 现象 / 后果 | 改进 |
|---|---|---|---|
| E1 | **双写错账** | 同一请求落两池 ⇒ 重复扣费/额度超扣 | 计费幂等 + 禁止批量更新类非幂等操作（本项目 `BATCH_UPDATE_ENABLED=false` 为红线） |
| E2 | 会话/令牌不共享 | 切换后**全员登录失效** | 会话外置 + 密钥全局一致（`SESSION_SECRET` 两地同源） |
| E3 | 限流计数分散 | 无 Redis 时每副本各自计数 ⇒ **限流配额被放大 N 倍** | 统一计数后端；或按池显式设定配额 |
| E4 | 缓存不一致 | 各池缓存独立，改配置后行为不一致 | 明确缓存收敛口径（本项目 `SYNC_FREQUENCY=30`，与节点数无关） |
| E5 | 上游出口 IP 未按池登记 | 某池出口未进上游白名单 ⇒ 该池请求全被上游拒 | 每池出口逐条登记并回执确认 |
| E6 | 只读副本延迟读 | 读到旧数据，用户看到"数据回退" | 关键读走主库，非关键读容忍延迟并标注 |
| E7 | 同一 `request_id` 落两池 | 对账分裂 | 请求级去重键 + 对账工具 |

### F. 计费与合规类

| # | 坑 | 现象 / 后果 | 改进 |
|---|---|---|---|
| F1 | 只算实例费，漏了探测与请求计费 | 账单超预期 | 成本量化把 GTM 探测/请求量计入（本项目任务 52） |
| F2 | 上游配额未按池分配 | 多活后某池打爆上游 RPM/TPM | 配额台账按池登记并限流对齐 |
| F3 | 跨境数据流动未评估 | 合规风险（用户数据被带到另一 region） | 数据落点与合规口径书面确认 |

### G. 运维类

| # | 坑 | 现象 / 后果 | 改进 |
|---|---|---|---|
| G1 | 只在控制台改，未回写 GitOps 真源 | 配置漂移，重建时对不上 | 池/策略/探测模板入仓库（本项目 `gtm-address-pool.md`） |
| G2 | 实例规格能力没核对就写进方案 | 规格名/能力（探测点数、TTL 下限、池数上限）与实际不符 | 以购买页为准；本项目明确「国际站只有 Standard / Ultimate 两档，**勿把"旗舰版"写进工单**」 |
| G3 | 把"能切换"当"已容灾" | 从没演练过，真出事时不敢切也不会切 | 把接管演练列为交付硬门禁 |
| G4 | 没有独立于 GTM 的链路观测 | GTM 说不健康但不知道为什么 | GTM 探测告警 + 独立拨测（本项目任务 39：不健康时**阻止**接管） |

### H. 本项目专属坑点（已落档）

| # | 坑 | 本项目口径 |
|---|---|---|
| H1 | 备池提前入池 | **硬门禁：M4 接管演练通过前不得入池**；入池后常驻权重 0 |
| H2 | 马尼拉只有 2 个可用区 | 池可用地址阈值必须设 **1**（设 2 会因单 AZ 抖动误切跨区） |
| H3 | 探测路径 `/api/status` 不反映 DB | G8 补 `/readyz` 合并后**必须切换**探测路径；过渡期接受指标置信度下降 |
| H4 | 探测源被限流 | `GLOBAL_API_RATE_LIMIT` 曾致 ALB 健康检查 429；探测与 ALB 健康检查**共用同源 IP 时须合并计预算** |
| H5 | WAF 白名单 | 本项目 **F15 裁定本轮不购买 WAF** ⇒ 该坑当前无触发对象；**复评购买 WAF 时必须先加探测源白名单再切** |
| H6 | 备站不发 DDL | 备站固定 `NODE_TYPE=slave`，避免与主站 master 并发迁移同一 schema |
| H7 | 现网状态与设计口径不同 | **截至 2026-10-09 实测：GTM 尚未接入**，现网是 `@`/`www` 各 2 条 A 记录直指马尼拉 ALB 两个 EIP（TTL 600）。⇒ "GTM 调度"目前是**设计口径，不是现状** |
| H8 | 对外 SLA 口径 | 切换时间用第 3 层实测值（接管演练），**不引用"60 秒"** |

## 7. 决策清单（选型时逐条过）

```
☐ 数据面能不能多写？              否 → 只能主备容灾
☐ 会话/计费是否强一致？            是 → 只能主备容灾
☐ 每个池能否独立承载全量？          否 → 主备不成立（要么扩容量，要么降 SLA）
☐ 备池常态空转的成本可接受吗？      否 → 评估冷备（代价=RTO 变长）
☐ 探测路径覆盖真实依赖了吗？        否 → 先去补 /readyz 这类探针
☐ 探测源在所有拦截层加白了吗？      否 → 先加白，否则会抖动误切
☐ 端到端切换时间（含递归 DNS）实测过吗？ 否 → 先演练，再对外承诺
☐ 回切观察窗定了吗？               否 → 定 15 分钟
☐ 配置回写仓库真源了吗？           否 → 回写（本项目 gtm-address-pool.md）
```

curl -sS https://www.likha.hk/api/status | jq -e '.success == true and .version != ""'

## 9. 一页速记

| 问题 | 答案 |
|---|---|
| 两个场景的本质差别？ | 池间策略：**顺序**（主备） vs **权重/轮询**（多活） |
| 怎么选？ | **先看数据面能不能多写**；不能 ⇒ 主备 |
| 主备最大的坑？ | 备池没预热就切（比不切更糟）+ 把 TTL 当 RTO |
| 多活最大的坑？ | 数据面不可多写 ⇒ 假多活、错账、脑裂 |
| 两者共通的坑？ | 探测不反映真实依赖 / 探测源被拦 / 回切无观察窗 / 没演练 |
| 本项目选了哪个？ | **主备容灾（顺序）**：马尼拉为主池，新加坡为备池（M4 演练通过后才允许入池、权重 0） |
| 对外怎么承诺切换时间？ | 用接管演练实测的"第 3 层"值，不引用"60 秒" |
