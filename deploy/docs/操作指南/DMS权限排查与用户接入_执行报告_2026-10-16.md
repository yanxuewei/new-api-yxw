## 一、权限模型：三层授权（RAM 策略 / RAM 组 / DMS 实例）

DMS 能不能用，取决于**同时满足**下面三层；「进不去」和「进去看不到库」是**不同层**的问题。

| 层 | 管什么 | 载体 | 症状 |
|---|---|---|---|
| **① RAM 策略级** | 能否调 `dms-console:*` / `dms:*` 动作 | `newapi-enforce-mfa`（Deny 兜底）等 | 控制台门检直接拦下 |
| **② RAM 组级** | 组上挂的 Allow 集合 | `dev_group` / `ops-prod_group` / `dev-program_group` | 同上 |
| **③ DMS 实例级** | 能否看到/登录某个**具体实例** | DMS 租户内的 per-user 授权 | 进去了但弹「暂无录入 / 登录权限」 |

> ⚠ 与本项目既有的「RAM 策略 vs K8s RBAC 两套互不相通」并列，DMS 实例级授权是**第三套**：
> RAM 全放行，DMS 内部仍可能一点权限都没有。

## 二、诊断：四个独立的坑

### 坑 1 · `newapi-enforce-mfa` 盖住 `*-console:*`（主因）

`newapi-enforce-mfa` 的形态是：

```json
{
  "Effect": "Deny",
  "NotAction": ["ram:GetUser", "cr:*", "dms-console:*", "dms:*", "..."],
  "Resource": "*",
  "Condition": { "Bool": { "acs:MFAPresent": "false" } }
}
```

- **控制台网关**对 `dms-console:*` 的评估上下文**不带 MFA** ⇒ `MFAPresent=false` ⇒ Deny 命中 ⇒ 页面被拦。
- 但浏览器 SPA 发起的**普通 API 调用**（如 `ResourceManager:*`）带 MFA ⇒ `MFAPresent=true` ⇒ 不命中、一切正常。
- ⇒ **极易误判成「已经排除这条策略了」**。

**判别式**：同组挂 `enforce-mfa` 的用户**全挂**；不挂的（`super_group` / `AdministratorAccess`）正常。

**关键反证**：`yanxuewei` 走 `AdministratorAccess`（`*:*`）能进 DMS，而它**并不含**
`AliyunDMSLoginConsoleAccess` 这个名字 ⇒ **门检评估的是「动作的有效权限」，不是「策略名是否挂载」**。
那句 *policy is not attached* 是 DMS 的固定文案，**别照着文案去找策略**。

**同形态前科**：2026-10-15 ACR 的 `cr:*` 事故，同一策略同一个坑。

**修法**：把动作补进 `NotAction`。`NotAction` 只是**解除 Deny**，实际权限仍需别处 Allow
⇒ 放开面极小，安全。

### 坑 2 · DMS 门检判定**完全不落 ActionTrail**

用户侧 **0 条** `dms-console:*` / `Ram:` / `Ims:` 调用；`AliyunServiceRoleForDMS` 零调用。
⇒ **「ActionTrail 里没痕迹」不能证明服务端没拒绝**，必须走**对照实验**（换人复现）。

ActionTrail 使用注意：
- `LookupAttribute` 合法键**只有** `EventId` / `EventName` / `ResourceName` / `ResourceType` / `User`
  （`EventSource` 报 `InvalidLookupAttributesException`）。
- 事件字段**小驼峰**，`userIdentity` 常是字符串，需二次 `json.loads`。
- `StartTime` / `EndTime` 必须是 `%Y-%m-%dT%H:%M:%SZ`。
- 翻页有抖动。

### 坑 3 · 服务端按 `PolicyType=Custom` 查 **System** 策略（旁证，非主因）

`AliyunServiceRoleForResourceMetaCenter` 反复调
`Ram:GetPolicy --PolicyType Custom --PolicyName AliyunDMSLoginConsoleAccess`，恒报 `EntityNotExist.Policy`。

- 实测：`GetPolicy` **不带** `--PolicyType` 是 `MissingParameter`，**不会默认按 Custom 查**。
- **绕过**：建一条**同名 Custom 策略**再挂到同样的组/用户上 —— `ram CreatePolicy` **不接受
  `--PolicyType`**（默认即 Custom），且**允许与系统策略同名**，两条并存。
- 本次建了，但**不是决定性因素**；真解是坑 1。

### 坑 4 · DMS 实例级授权缺失

RAM 层放行后仍报「暂无**录入**该数据库实例的权限」/「暂未获取**登录权限**」。
⇒ 必须在 DMS 租户内**逐实例**给用户授权（见第四节）。

## 四、新用户接入 SOP

### 4.1 分层边界：一次性 vs 每人

| 层 | 内容 | 频率 |
|---|---|---|
| RAM 策略级 | `newapi-enforce-mfa` **v4** 已含 `dms-console:*` / `dms:*` | **一次性**（全局） |
| RAM 组级 | 同名 Custom 策略已挂 3 组 | **一次性**（新用户入组即继承） |
| RAM 组级 | 把用户加进 `dev_group` / `ops-prod_group` / `dev-program_group` | 每次（= 标准入职动作） |
| DMS | `RegisterUser` → `UpdateUser --UserNick` → `GrantUserPermission LOGIN` × N | **每用户必做** |

> **DMS 没有组级授权** —— 这是必须在 DMS 侧逐人、逐实例执行的根本原因。

### 4.2 一键脚本

```bash
# 干跑（先看将执行什么，不落写）
bash deploy/ops/onboard-dms-user.sh <RAM用户名> --group dev_group --group ops-prod_group --dry-run

# 正式执行（幂等，重复跑安全）
bash deploy/ops/onboard-dms-user.sh <RAM用户名> --group dev_group --group ops-prod_group

# 回滚
bash deploy/ops/onboard-dms-user.sh <RAM用户名> --revoke --yes
```

**脚本 5 步**：解析 RAM UserId → 校验/补齐组归属 → 注册进 DMS → 补昵称 → 逐实例授 `LOGIN` 并复核。

**默认目标实例** = 3 个「未托管」实例：`2997880` / `3004426` / `3004473`。
**自动排除** Tair ×3（`2998669` / `3004344` / `3000947`，天然免登录）与 `2998662`（陈旧 CK）。

**设计要点**：幂等（已注册/已授权自动跳过）、写操作**重试 3 次**、每步复核断言、
`--dry-run` 也走真实只读判定（干跑可信）。

**实测**：
- `yxw` 真实重跑 ⇒ 3×「已有 LOGIN，跳过」+ 3×`✅ LOGIN`，**1 秒**完成（幂等成立）。
- `dev-xiangdong` 干跑 ⇒ 正确走出「未注册 → RegisterUser → UpdateUser → 授权」全链。
- 三名用户 × 3 实例 = **9 条 LOGIN 全部在位**（只读扫全 3 人复核）。

### 4.3 `ops_group` 组级缺口（2026-10-16 11:13 **已补齐**）

**原状**：`ops_group` 只有 `newapi-ops-operator` / `newapi-enforce-mfa` / `newapi-prod-oss-guard` /
`newapi-prod-boundary` / `newapi-audit-protect`，**没有 DMS 控制台策略**
⇒ 只进 `ops_group` 的用户**进不去 DMS**。

**处置**（fanyan 决策 = 挂策略，而非给用户追加 `dev_group`）：

```bash

  --PolicyName AliyunDMSLoginConsoleAccess --PolicyType Custom
```

⇒ 已挂载，复核 `ListPoliciesForGroup ops_group` = **6 条**（原 5 条 + 本次 1 条）。
⚠ **`AttachPolicyToGroup` 必须带 `--PolicyType`**（`System` | `Custom`，是必填项）。

**与兄弟组的差异**：`dev_group` / `ops-prod_group` / `dev-program_group` 是 **System + Custom 两条并存**；
`ops_group` 只挂了 **Custom** 一条。**功能上等价** —— Custom 正文本就是
`{"Version":"1","Statement":[{"Effect":"Allow","Action":"dms-console:*","Resource":"*"}]}`，

## 六、DMS OpenAPI 速查与坑清单

**通道**：`aliyun dms-enterprise`（API 版本 `2018-11-01`）

| 坑 | 说明 |
|---|---|
| **地域** | **必须 `--region cn-hangzhou`**。dms-enterprise **无 ap-southeast-\* 端点**，传 `ap-southeast-6` 直接报 unknown endpoint |
| **Tid** | `7659207`（`GetUserActiveTenant` 取） |
| **关联键** | `ListUsers` 返回的 **`Uid` = RAM UserId**；`UserId` 才是 DMS 内部 ID。幂等判断用 `UserList.User[?Uid=='<RAM UID>']` |

**常用调用**：

```bash
R="--region cn-hangzhou"; T="--Tid 7659207"

# 用户
aliyun dms-enterprise ListUsers $T $R
aliyun dms-enterprise RegisterUser --Uid <RAM UserId> $T $R
aliyun dms-enterprise UpdateUser --Uid <RAM UserId> --UserNick <昵称> $T $R

# 实例
aliyun dms-enterprise ListInstances $T $R

# 授权 / 撤权
aliyun dms-enterprise GrantUserPermission $T $R \
  --UserId <DMS UserId> --DsType INSTANCE --InstanceId <id> \
  --PermTypes LOGIN --ExpireDate "2099-12-31 23:59:59"
aliyun dms-enterprise RevokeUserPermission $T $R \
  --UserId <DMS UserId> --DsType INSTANCE --InstanceId <id> \
  --PermTypes LOGIN --UserAccessId <accessId>

# 复核
aliyun dms-enterprise ListInstanceUserPermissions $T $R \
  --InstanceId <id> --UserName <昵称>
```

**API 坑清单**：

| # | 坑 | 正解 |
|---|---|---|
| 1 | `ListInstanceUserPermissions --UserId` 报非法 | 参数是 **`--UserName`**（不是 `--UserId`） |
| 2 | 解析键写成 `InstanceUserPermissions` | 正确结构 `UserPermissions.UserPermission[].PermDetails.PermDetail[]`（`PermType` / `ExpireDate` / `OriginFrom` / `UserAccessId`）——**写错会误判「无权限」** |
| 3 | `ListAuthorizedUsersForInstance` 显示无权限 | 它**只反映 QUERY 级**，不反映 `LOGIN`；别用它验证 `LOGIN` |
| 4 | `UpdateUser --NickName` 报非法 | 参数是 **`--UserNick`**，且**必填 `--Uid`**（int，可容 18 位；另有 `--UidString`） |
| 5 | 昵称为空 ⇒ `ListInstanceUserPermissions --UserName` 报 `InvalidParameterValid` | 先 `UpdateUser` 补昵称再复核 |
| 6 | `GetInstance --InstanceId` 报非法参数 | 改用 `ListInstances` 过滤 |
| 7 | `ram SimulatePrincipalPolicy` 不存在 | 国际站 CLI **无此 API**（`is not a valid api`）⇒ 只能真实调用 + 对照实验 |
| 8 | `ram GetPolicy` 不带 `--PolicyType` 报 `MissingParameter` | 它**不会默认按 Custom 查**；`Create/Delete` 版本接口**不吃** `--PolicyType` |
| 9 | **`\| [0]` 在 CLI 的 JMESPath 上不稳** | `UserAccessId` 曾回 `[ 84875060 ]` 脏值 ⇒ 需 `grep -o '[0-9]\+' \| head -n1` 规范化 + 合法性守卫 |

## 附录 A：脚本自检记录（2026-10-16）

开发过程中脚本自身踩到两个坑，均已修复，记录备查：

1. **★ `GROUPS` 是 bash 内建保留数组**
   （名为 `GROUPS` 的变量是「当前用户组 ID」数组，root 下 = `(0)`）
   ⇒ `GROUPS=()` 赋值**被静默忽略**，数组恒非空、元素恒为 `0`，
   表现为「没传 `--group` 却去执行 `AddUserToGroup yxw -> 0`」。
   **与本项目既有的 `UID` 只读变量是同一类坑** ⇒ 改名 `REQ_GROUPS`。

2. **★ 只读查询静默吞错会把「API 抖动」误判成「没授权」**
   初版用 `q() { aliyun "$@" 2>/dev/null; }` 判权限，首次真跑时 `3004473` 被**重复授权**一次。
   服务端幂等 ⇒ 无实害，但**诊断失真**，属本项目最忌的「静默漏判」。
   ⇒ 引入 `has_login()` **三态**判定（有 / 确认没有 / 查询失败），失败必打 `WARN`；
   并新增通用 `read_retry()` 让所有只读查询带 3 次重试。
