## 1. 生产程序身份：RRSA 角色（新建）

### 1.1 需求

正式环境程序跑在 ACK Pod 内，需要读写生产 OSS。

### 1.2 决策：不用 AK，也不用用户组

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 长期 AK + 用户组 | ❌ | AK 无法自动轮转；生产写权限落进 K8s Secret 风险高 |
| **RRSA 角色 + STS** | ✅ | 集群已开 RRSA（`ack-rrsa-cd57e40ce9a634c1698c2f5c5e09bd93c`）；Pod 已用 `serviceAccountName: new-api-app`（`new-api` 命名空间） |

> 关键认知：**用户组只对 RAM 用户生效，角色不能进组**。因此"策略只挂组"的铁律在这里不适用，策略直接挂角色。RRSA 的 token 文件由 ACK 自动挂载到使用该 SA 的 Pod，无需额外 volume。

### 1.3 权限设计

策略 `newapi-prod-program`（v1）三条 Statement：

| Effect | Action | Resource | 说明 |

| Allow | `oss:PutObject/GetObject/DeleteObject/ListObjects/GetBucketInfo` + 分段上传全套 | `acs:oss:*:*:oss-newapi-mnl`、`acs:oss:*:*:oss-newapi-mnl/artifacts/*` | 只到指定前缀 |
| Deny | `oss:*` | `acs:oss:*:*:oss-newapi-mnl/actiontrail`、`.../actiontrail/*` | 该桶同时是 ActionTrail 落盘桶，必须挡 |
| Deny | `ram:*`、`account:*`、`bss:*`、`oss:DeleteBucket` | `*` | 程序身份永不需要 |

| 站点 | 集群 / region | 桶 / 前缀 | 策略 | RRSA 角色 | AK 组 / 用户 |
| --- | --- | --- | --- | --- | --- |
| `mnl` | `ack-newapi-mnl` / ap-southeast-6 | `oss-newapi-mnl` / `artifacts` | `newapi-prod-program` | `new-api-prod-program`（`new-api/new-api-app`）✅ | `prod-program_group` / `prod-program` ⏸ |

要点：

- 两种认证共用**同一条策略**（同一份 JSON 生成），权限范围完全一致，不存在"AK 比 RRSA 权限大"的偏差；
- 每个集群的 OIDC Provider 独立（`ack-rrsa-<cluster_id>`），issuer 也不同 ⇒ **角色不能跨集群复用**；
- RRSA `apply` 会先探测 `rrsa_config.enabled`，未开启时直接拒绝，不会留下半成品；
- AK `add-program-ak` 会校验用户**没有控制台登录**，Secret 只写入 `$AK_SECRET_DIR/newapi-<site>-program-ak.json`（0600），**不回显到终端**；
- 支持 `OSS_BUCKET` / `OSS_PREFIX` 覆盖（`OSS_PREFIX` 传空 = 整桶，会打印告警）；`actiontrail` 前缀有硬拒绝；
- 修过一处自身缺陷：`verify` 末尾的 `A && B || C && D` 在 bash 中被解析为 `((A&&B)||C)&&D`，导致成功时也打印失败分支；已改 `if/else`。

### 1.8 集群外场景：AK 路线（新增能力）

集群外程序无法拿 Pod token，只能走长期 AK。设计上与 RRSA **并列**而不是替代：

| 项 | 设计 |
| --- | --- |
| 身份 | RAM 用户 `prod-program`（无控制台、无 LoginProfile） |
| 权限载体 | 用户组 `prod-program_group` ← `newapi-prod-program` + `newapi-audit-protect` |
| 权限范围 | 与集群内角色**完全相同**：`oss-newapi-mnl/artifacts/*`，`actiontrail/*` 被 Deny |
| 密钥落盘 | `$HOME/.aliyun/newapi-mnl-program-ak.json`（0600），仅创建时写一次 |
| 轮转 | 90 天：`new-ak` → 切换 → `toggle-ak 旧 Inactive` → 观察 → `del-ak` |

执行：

```bash
bash deploy/ops/ram_user_mgmt.sh add-program-ak mnl       # 建/补齐 组+用户+AK
bash deploy/ops/ram_user_mgmt.sh verify-program-ak mnl    # 回读校验
```

风险与约束（必须一并接受）：

1. AK 长期有效，泄露即等于生产桶写权限 → 只发给集群外那一台/一个程序，禁止进 git、镜像层、聊天记录；
2. 无法按 Pod 区分调用方，ActionTrail 只能看到 `prod-program` 这个用户 → 需要定位具体实例时靠 `sourceIpAddress`；
3. 与集群内 RRSA 并存意味着**同一权限有两个入口**，撤销时要两处都处理（删角色 / 禁用 AK）；
4. 若该集群外程序将来迁入 ACK，应删除 AK 用户并切回 RRSA，不要两套长期并存。

## 3. DMS 同名策略冲突：`AliyunDMSLoginConsoleAccess`

### 3.1 结论

`dev-program_group` 列表里该策略出现两条，**不是重复绑定，而是同名不同命名空间**：

| PolicyType | 版本 | 内容 | 来源 |
| --- | --- | --- | --- |
| `Custom` | v1 | `dms-console:*` on `*` | 2026-10-16 02:27:25 `yanxuewei` 手工 `CreatePolicy` |
| `System` | v1 | `dms-console:*` on `*` | 阿里云托管策略，2026-10-15 已在使用 |

RAM 允许自定义策略与系统策略同名，因此列表同时出现两条，权限完全相同。

> 三人均已在两个组内，组已覆盖同一权限 ⇒ 用户级挂载**完全冗余**，且违反《用户设置指南》§0.2「策略只挂用户组」。

### 3.4 根因

1. 10-15 系统策略正常挂到 3 个组 + 3 个用户；
2. 10-16 02:27 要给 `ops_group` 授权，`aliyun ram AttachPolicyToGroup` 的 `--PolicyType` 默认 `Custom`，未带 `System` ⇒ 报"策略不存在"；
3. 于是 `CreatePolicy` 建同名自定义策略，并重复挂到已有系统策略的对象；
4. 10-16 03:12 用它补挂 `ops_group`，表面修好，实际留下双份与错位。

### 3.5 风险

| 风险 | 说明 | 级别 |
| --- | --- | --- |
| 双份同权 | 审计与对账易误读 | 低 |
| 覆盖面错位 | `ops_group` 只依赖 Custom，直接删会**失去 DMS 权限** | 中 |
| 程序身份多余授权 | `dev-program_group` 是纯 AK 无控制台，`dms-console:*` 无用；将来若开控制台会静默带入 | 中 |
| 违反铁律 | 3 个用户直挂策略，破坏"用户级策略应为空"基线 | 中 |
| 命名歧义 | 只能靠 `PolicyType` 区分；`ram_user_mgmt.sh detach` 默认按 `Custom`，易解错 | 中 |

### 3.6 建议清理顺序（**未执行**）

```bash
# 1. 系统策略补挂 ops_group（否则第 2 步后该组失去 DMS 权限）
aliyun ram AttachPolicyToGroup --GroupName ops_group \
  --PolicyName AliyunDMSLoginConsoleAccess --PolicyType System --region ap-southeast-1

# 2. 解绑自定义策略（4 组 + 3 用户）
for g in ops_group dev_group ops-prod_group dev-program_group; do
  aliyun ram DetachPolicyFromGroup --GroupName "$g" \
    --PolicyName AliyunDMSLoginConsoleAccess --PolicyType Custom --region ap-southeast-1
done
for u in yxw xiangdong zhangzijun; do
  aliyun ram DetachPolicyFromUser --UserName "$u" \
    --PolicyName AliyunDMSLoginConsoleAccess --PolicyType Custom --region ap-southeast-1
done

# 3. 解绑用户级系统策略（组里已有，恢复"只挂组"）
for u in yxw xiangdong zhangzijun; do
  aliyun ram DetachPolicyFromUser --UserName "$u" \
    --PolicyName AliyunDMSLoginConsoleAccess --PolicyType System --region ap-southeast-1
done

# 4. 删除自定义策略
aliyun ram DeletePolicy --PolicyName AliyunDMSLoginConsoleAccess --PolicyType Custom \
  --region ap-southeast-1
```

清理后校验：4 个组各只剩 `System` 一条；3 个用户均为空。

## 6. 附录：从 AK/SK 迁移到 RRSA

### 6.1 现状盘点

| 位置 | 内容 | 现状 |
| --- | --- | --- |
| `setting/system_setting/task_artifact_store.go` | `TASK_ARTIFACT_STORE_S3_ACCESS_KEY` / `_SECRET_KEY` 静态凭证 | S3 模式**未实现**，启动强制回落 upstream（同文件 `:70`） |
| `pkg/jsplugin/utils.go` | `volcSignV4` 的 `AccessKey` / `SecretKey` | 火山引擎签名，与阿里云无关，**不在本次范围** |
| `go.mod` | 无 `aliyun-oss-go-sdk`；有 `aws-sdk-go-v2/credentials` | 若走 S3 兼容协议，改造点在 aws-sdk 的凭证提供者 |

> 结论：本仓库当前没有可迁移的阿里云 OSS 客户端。下面的方案适用于"业务代码持有静态 AK 调 OSS"的情形，落地时按实际 SDK 选 A 或 B。

### 6.2 方式 A：阿里云 OSS Go SDK v3（有官方凭证提供者）

```go
import (
    "os"

    "github.com/aliyun/credentials-go/credentials"
    "github.com/aliyun/oss-go-sdk/v3/oss"
)

// 1) 凭证源：三类信息全部来自 Pod 环境变量（§1.5）
cfg := new(credentials.Config).
    SetType("rrsa").
    SetRoleArn(os.Getenv("ALIBABA_CLOUD_ROLE_ARN")).
    SetOIDCProviderArn(os.Getenv("ALIBABA_CLOUD_OIDC_PROVIDER_ARN")).
    SetOIDCTokenFilePath(os.Getenv("ALIBABA_CLOUD_OIDC_TOKEN_FILE")).
    SetRoleSessionName("new-api-prod")

baseCred, err := credentials.NewCredential(cfg)

// 2) 交给 OSS SDK：用一个实现了 CredentialsProvider 接口的对象包住 baseCred。
//    接口签名随 SDK/credentials-go 版本不同（v1: GetCredentials() (*Credentials, error)；
//    v2: GetCredentials(ctx context.Context)），按锁定版本实现，别照抄字符串。
client, err := oss.New(endpoint, "", "", oss.SetCredentialsProvider(provider))
```

SDK 内部缓存并在过期前刷新，无需自己写定时器。

### 6.3 方式 B：S3 兼容（aws-sdk-go-v2，需适配层）

S3 SDK 不认识阿里云 RRSA，要把 STS 结果包装成 `aws.CredentialsProvider`：

```go
type rrsaProvider struct{ cred credentials.Credential }

func (p rrsaProvider) Retrieve(ctx context.Context) (aws.Credentials, error) {
    m, err := p.cred.GetCredential()
    if err != nil {
        return aws.Credentials{}, err
    }
    return aws.Credentials{
        AccessKeyID:     *m.AccessKeyId,
        SecretAccessKey: *m.AccessKeySecret,
        SessionToken:    *m.SecurityToken, // 必须带，否则 STS 凭证无效
        CanExpire:       true,
        Expires:         m.Expiration,
    }, nil
}

cfg, err := config.LoadDefaultConfig(ctx,
    config.WithCredentialsProvider(aws.NewCredentialsCache(rrsaProvider{cred: baseCred})))
```

要点：`SessionToken` 不能漏；用 `aws.NewCredentialsCache` 避免每次请求都打 STS。

### 6.4 方式 C：过渡方案（不改 SDK）

后台 goroutine 定时 `GetCredential()`，每次拿到 STS 后重建 client 并原子替换指针。可用，但过期/并发/失败回退都要自己管，**不建议长期保留**，只适合"先跑通再重构"。

### 6.5 RRSA vs AK/SK

| 维度 | AK/SK | RRSA |
| --- | --- | --- |
| 生命周期 | 长期有效，人工轮转 | STS 临时凭证，自动续期 |
| 泄露面 | Secret/环境变量可被复制走 | token 只在 Pod 内，离开集群无法兑换 |
| 身份粒度 | 一用户一把 AK，多工作负载共用 | 精确到 `namespace/serviceaccount` |
| 撤销 | 禁用 AK 影响所有使用者 | 改 `oidc:sub` 或删角色，秒级、只影响目标 |
| 审计 | ActionTrail 只到 RAM 用户 | 可通过 role session 区分工作负载 |
| 代码改动 | 无 | 需改凭证获取 + 注入 §1.5 的 3 个 env |
| 环境依赖 | 无 | 需支持 OIDC 的运行时（ACK / 已配 OIDC 的 K8s） |
| 排障 | 直接 | 三层排查：token 是否存在 → 信任策略条件 → 策略授权 |
| 冷启动 | 无额外调用 | 首次多一次 STS 调用 |
| 本地调试 | 直接可用 | 不可用，需 `sts AssumeRole` 换临时凭证模拟 |

一句话：**RRSA 把"保管密钥"换成"验证身份"**，安全与运维更优，代价是环境绑定与一次性改造成本。

### 6.6 适用 / 不适用

**适合**

- ACK / ECS 上的常驻服务访问 OSS、SLS、MPS、OSS-HDFS（即当前场景）
- 多集群 / 多环境隔离：马尼拉与新加坡是两个独立 OIDC Provider，天然不能互相 assume（见 `deploy/tasks/task17/rrsa.sh` 的历史结论）
- CI/CD 的 OIDC 联邦（GitHub Actions / GitLab），短任务拿短凭证

**不适合**

- 本地开发与个人脚本 → 用 `sts AssumeRole` 换 1 小时临时凭证，或受限 RAM 用户
- 自建 K8s 未配 OIDC、传统虚机、不支持 OIDC 的托管平台 → 实例 RAM 角色或 AK
- 依赖"固定不变凭证"的遗留系统（改造成本高于收益）

### 6.7 本项目落地步骤（渐进、可回滚）

1. 配置新增 `TASK_ARTIFACT_STORE_CRED_MODE=rrsa|static`，默认 `static`，保证现有行为不变；
2. `ValidateTaskArtifactStoreConfig` 当前在 `mode=s3` 时**强制要求** AccessKey/SecretKey（`:123` 附近），改为**仅 `static` 模式要求**；`rrsa` 模式校验三个 `ALIBABA_CLOUD_*` 变量；
3. 启动探测：`GetCredential()` + 一次 `ListObjects`。失败**显式报错，禁止静默回落**——现有 `LoadTaskArtifactStoreConfig` 配置非法时悄悄退回 upstream，线上极难发现，不要复制这个模式；
4. 灰度：canary → stable；先只读（`ListObjects`），再写（`PutObject`），最后负向（写 `actiontrail/` 前缀应 403）；
5. 稳定后收口：Secret 里的 AK 先 `toggle-ak Inactive` 观察 1–2 天，再 `del-ak`。
