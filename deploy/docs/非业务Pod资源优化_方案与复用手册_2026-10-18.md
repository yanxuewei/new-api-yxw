# 非业务 Pod 资源优化 · 方案与复用手册

> **版本**：v1.1（2026-10-18，新增第 2/3 节：瓶颈分析方法 · 方案选择与对比）
> **适用**：ACK 集群中 `kube-system` / `arms-prom` / `deploy` 等**非业务命名空间**的 Pod
> **已落地**：雅加达 dev（`ap-southeast-5`）· 马尼拉主站（`ap-southeast-6`）· 新加坡备站（`ap-southeast-1`）
> **脚本位置**：`deploy/pub_bodies/`（两个站点通用，`ack_remote.sh <mnl|sg> <body.sh>` 直接跑）

---

## 1. 为什么要做

业务 Pod 能不能调度上去，只取决于两件事：**节点 `allocatable`** 和 **已占用的 `requests`**。非业务 Pod（控制面、CNI、CSI、监控采集）每台必装，是**固定的底噪**。底噪越高，业务可用的天花板越低。

三个量化口径：

| 指标 | 含义 | 决定什么 |
| --- | --- | --- |
| `requests.cpu` 合计 | 调度器记账的「预留量」 | **能否再调度新 Pod**（决定性） |
| `limits.cpu` 合计 ÷ allocatable | 控制台的「超卖率」 | 只是展示；>150% 黄、>200% 红。**但决定了单节点 CPU 打满时互相挤压的幅度** |
| DaemonSet 每台开销 | 每加一台节点自动付出的代价 | 节点池扩一台的**有效容量**（总 allocatable − 底噪） |

**关键认知**：`requests` 是**账**，`limits` 是**闸**。降 `requests` 直接换来调度空间；降 `limits` 换的是「真打满时不至于一起卡死」，不改变可调度数量。两者都要动，但优先级是 **requests 优先**。

## 2. 瓶颈分析：怎么找到真正的瓶颈

### 2.1 先分清是「哪一种」瓶颈

「Pod 起不来」有五种完全不同的成因，解法互不通用。**先看 Event，不要先猜**：

```bash
kubectl -n <ns> describe pod <pod> | sed -n '/Events/,$p'
```

| Event 关键句 | 真正的瓶颈 | 属于哪一层 | 有效解法 | 无效解法 |
| --- | --- | --- | --- | --- |
| `0/3 nodes are available: 3 Insufficient cpu` | `requests` 记账已满 | 调度记账 | 降非业务 requests / 扩节点 / 换机型 | 降 limits |
| `0/3 nodes are available: 3 Too many pods` | **槽位**（`maxPods`）满 | 网络（ENI IP 数） | 换机型提 ENI 上限 / 扩节点 / 减少每台 DaemonSet Pod 数 | 降 requests、降 limits |
| `didn't match pod anti-affinity rules` | 拓扑约束 | 调度策略 | 降副本数 / 放宽 affinity | 任何资源调整 |
| `Insufficient memory` | 内存记账满 | 调度记账 | 降 memory requests | 只降 cpu |
| Running 但 `cpu.stat` 有 `nr_throttled` | `limits.cpu` 太低 | 运行时 | **提** limit | 降 request |
| `OOMKilled`（`lastState.terminated.reason`） | `limits.memory` 太低 | 运行时 | **提** memory limit | 降 request |

> **最容易搞混的一对**：`Insufficient cpu` 与 `Too many pods`。前者是「账不够」，后者是「号不够」。`maxPods` 由 `EniQuantity × EniPrivateIpAddressQuantity − 1` 决定，**和 CPU 无关**。加 CPU 一点用没有。反过来，槽位还有富余但 CPU 满，加节点才有效。

### 2.2 三层下钻（L1 → L2 → L3）

```
L1  节点水位        requests ÷ allocatable        → 这台节点还有多少空间
L2  owner 拆分      DaemonSet 每台 vs 非 DS 一次性  → 底噪有多重、优化空间在哪
L3  容器级          usage ÷ requests               → 哪些是虚占、能压多少
```

**L1 一眼看水位**：

```bash
kubectl describe node <node> | sed -n '/Allocated resources/,/Events/p'
```

**L2 拆出「每台底噪」与「集群级一次性开销」**——这是最关键的分解，因为两者优化手段不同：

```bash
kubectl get pods -A --field-selector=status.phase=Running -o json > /tmp/a.json
python3 - <<'PY'
import json, collections
d = json.load(open('/tmp/a.json'))
def q(v):
    if not v: return 0
    v = str(v); return int(v[:-1]) if v.endswith('m') else int(float(v)*1000)
ds = collections.defaultdict(float); cnt = collections.Counter(); other = 0.0
for p in d['items']:
    if p['metadata']['namespace'] == 'new-api': continue          # ← 换成你的业务 ns
    o = (p['metadata'].get('ownerReferences') or [{}])[0]
    c = sum(q(((x.get('resources') or {}).get('requests') or {}).get('cpu')) for x in p['spec'].get('containers', []))
    if o.get('kind') == 'DaemonSet':
        ds[o.get('name')] += c; cnt[o.get('name')] += 1
    else:
        other += c
per = sum(v / cnt[k] for k, v in ds.items() if cnt[k])
print('  每台 DaemonSet 开销（底噪）= %.0fm' % per)
print('  集群级一次性开销            = %.0fm' % other)
print('  --- 按 DaemonSet 明细 ---')
for k, v in sorted(ds.items(), key=lambda x: -x[1]):
    print('    %-40s 合计%6.0fm / %d 台 = 每台 %5.0fm' % (k, v, cnt[k], v / cnt[k]))
PY
```

**判读**：
- 每台底噪 > 1,000m（8C 节点）⇒ 底噪过重，**先做本手册的方案**
- 非 DaemonSet 一次性 > 2,000m ⇒ 集群级组件堆得太多，看 2.3 的虚占率
- 底噪 < 400m 且一次性 < 800m ⇒ **优化收益已接近 0，别再动**（详见 3.6）

**L3 找虚占**——`requests` 定得远高于实际用量，就是纯账面浪费：

```bash
kubectl top pods -A --no-headers 2>/dev/null | awk '{print $1"\t"$2"\t"$3}' > /tmp/top.tsv
kubectl get pods -A -o json > /tmp/a.json
python3 - <<'PY'
import json
def q(v):
    if not v: return 0
    v = str(v); return int(v[:-1]) if v.endswith('m') else int(float(v)*1000)
req = {}
d = json.load(open('/tmp/a.json'))
for p in d['items']:
    k = (p['metadata']['namespace'], p['metadata']['name'])
    if p['metadata']['namespace'] in ('new-api',): continue        # ← 排除业务 ns
    req[k] = sum(q(((c.get('resources') or {}).get('requests') or {}).get('cpu')) for c in p['spec'].get('containers', []))
rows = []
for line in open('/tmp/top.tsv'):
    f = line.split('\t')
    if len(f) < 3 or not f[2].endswith('m'): continue
    k = (f[0], f[1]); use = int(f[2][:-1])
    r = req.get(k, 0)
    if r >= 100:
        rows.append((use / r if r else 9, r, use, k))
rows.sort()
print('%-8s %-8s %-8s %s' % ('usage', 'request', 'usage/req', 'pod'))
for ratio, r, u, k in rows[:20]:
    print('%-8s %-8s %-8.1f%% %s/%s' % ('%dm' % u, '%dm' % r, ratio * 100, k[0], k[1]))
PY
```

**判读**：`usage/request < 10%` 且 `request ≥ 100m` ⇒ 典型虚占，可压到 `usage × 2~3`。上表按比值升序，**前 10 名就是主战场**。

> ⚠ `kubectl top` 是 `metrics-server` 的采样值，突发负载会被平滑掉。**压 `requests` 的下限不能按 top 值定，要按 P95 定**。一次性任务（Job、CronJob）会被 top 低估，别拿它当依据。

### 2.3 四个比值（诊断打分卡）

| 比值 | 计算 | 健康区间 | 超标含义 |
| --- | --- | --- | --- |
| **① 节点水位** | `Σ requests ÷ Σ allocatable` | 40% ~ 70% | >80% 无法承接 HPA 扩容尖峰 |
| **② 底噪占比** | `每台 DaemonSet 开销 ÷ 单台 allocatable` | < 15% | >20% 每加一台白付 1/5 容量 |
| **③ 虚占率** | `usage ÷ requests` | 30% ~ 80% | <10% = 账面浪费；>100% 会被节流 |
| **④ 超卖率** | `Σ limits ÷ Σ allocatable` | 100% ~ 200% | >200% 控制台标红；打满时互相挤压严重 |

**四个一起看才能定位**：

- ① 高 + ③ 低 ⇒ **纯虚占**，降 requests 立刻见效（本次三站的典型情形）
- ① 高 + ③ 高 ⇒ 真的不够用，降 requests 会引发节流，只能扩容量
- ① 低 + ④ 高 ⇒ 账面宽松但单点打满会雪崩，降 limits
- ② 高 ⇒ 节点池的「有效容量」被吃掉，优先压 DaemonSet

### 2.4 有效容量公式

选机型、算能开几个 Pod，都用这个：

```
EffectiveCapacity(节点) = allocatable.cpu − DaemonSet 每台开销 − 非 DaemonSet 一次性开销 ÷ 节点数
可容纳业务 Pod 数       = ⌊EffectiveCapacity ÷ 单 Pod requests⌋
```

**三站实测代入**（单 Pod requests = 1,500m）：

| 站点 | allocatable | 每台底噪 | 一次性 ÷ N | 有效容量 | 可容纳 Pod |
| --- | --- | --- | --- | --- | --- |
| jkt dev（2 台 4C） | 3,920m | 430m | 1,100 ÷ 2 = 550m | **2,940m** | 1 个 + 余 1,440m |
| mnl（2 台 8C） | 7,910m | 430m | 1,100 ÷ 2 = 550m | **6,930m** | 4 个 + 余 930m |
| sg（1 台 8C） | 7,910m | 430m | 1,050 ÷ 1 = 1,050m | **6,430m** | 4 个 + 余 430m |

> 注意 jkt 的 `EffectiveCapacity` 反过来印证了为什么它只跑得动 1 个业务 Pod —— 4C 的节点，底噪 + 一次性就吃掉 980m，再被 quota 和 1,500m request 一卡，就是「2 台只有 1 个能调度」。

### 2.5 判别树（照这个走，不要跳步）

```
业务 Pod 起不来？
├─ Pending？
│   ├─ Events: Insufficient cpu ──→ 看 ① 水位
│   │     ├─ ① > 80% ──→ 看 ② 底噪
│   │     │     ├─ ② > 20% ──→ 【方案 A】降非业务 requests（本手册）
│   │     │     └─ ② < 20% ──→ 看 ③ 虚占
│   │     │           ├─ ③ < 10% ──→ 【方案 A】降业务 requests
│   │     │           └─ ③ 正常 ──→ 【方案 D】扩节点 / 【方案 E】换机型
│   │     └─ ① < 80% ──→ 有 Pending 但账面有余 = 碎片化或 affinity → 查 2.6
│   └─ Events: Too many pods ──→ 【方案 E】换机型提 ENI（加 CPU 无用）
├─ Running 但慢？
│   ├─ throttled > 0 ──→ 【方案 B】提 limits
│   └─ OOMKilled     ──→ 提 memory limit
└─ 创建 Namespace / 写操作全挂？
    └─ gatekeeper webhook failurePolicy=Fail ──→ 见 5.2
```

### 2.6 常见误判（花了时间还找错方向）

| 误判 | 真相 | 怎么区分 |
| --- | --- | --- |
| 「节点 CPU 使用率才 20%，肯定不缺 CPU」 | 调度看 **requests**，不看利用率 | `describe node` 的 `Allocated resources` ≠ `kubectl top` |
| 「Pod 数才 20/48，槽位还很空」 | 槽位按 **`maxPods`** 算，单个节点满就 Pending | 看 Events 是 `Too many pods` 还是 `Insufficient cpu` |
| 「`kubectl top` 显示用了 5m，request 可以设 10m」 | 采样平滑 + 突发尖峰，压太低会节流 | 看 P95、看 `nr_throttled` |
| 「`limits` 降了就能多调度 Pod」 | `limits` **不参与调度** | 只有 `requests` 影响调度器 |
| 「节点池还有余量，CA 会自动加」 | CA 受 `max_instances` 与 `min_instances` 双向约束 | `DescribeClusterNodePools` 查 actual min/max |
| 「deployment 副本少 = 省资源」 | 副本少了但单 Pod request 没变，省的是**可调度数**不是**底噪** | 分开看 ② 与 ③ |

## 3. 方案选择：候选方案与取舍

### 3.1 六类候选方案总览

| # | 方案 | 直接收益 | 代价 / 风险 | 可逆 | 适用条件 |
| --- | --- | --- | --- | --- | --- |
| **A** | 降**非业务** requests | 直接扩业务可调度空间，**零成本** | 控制面组件滚动变慢；压过头会节流 | ✅ 秒级 | ② 底噪占比 > 20% 或 ③ 虚占率 < 10% |
| **B** | 降 `limits` | 只改善「打满时互相挤压」，**不增容量** | 峰值时可能节流 | ✅ 秒级 | ④ 超卖率 > 200% |
| **C** | 下线 / 降副本冗余 addon | 省整份 requests + 每个 Pod 槽位 | 功能缺失（如成本分析、策略校验） | ✅ 秒级 | 组件确认未使用；⚠ 先查 webhook |
| **D** | **扩节点**（加台数） | 容量等比增加 | **真金白银**；多一份底噪 | ✅ 异步 | ③ 正常且容量真不够 |
| **E** | **换机型**（同钱换大核/多 ENI） | 同成本提核数或槽位 | 需重建节点（drain + 换池） | ⚠ 慢、有中断 | 槽位不足，或机型性价比明显更优 |
| **F** | 降**业务** requests | 立竿见影扩可调度数 | HPA 阈值线下移，扩缩更敏感；压太低会节流 | ✅ 秒级 | ③ 虚占率高，且压测确认 |

### 3.2 决策树：先判断「缺什么」

```
容量不够，选哪个？
├─ 缺的是【槽位】（Too many pods）
│   └─ 【E】换机型  ≫  【D】扩节点
│       理由：maxPods = ENI数量 × ENI IP数，换机型是「质变」；扩节点是「量变」且多付一份底噪
├─ 缺的是【CPU】且 ③ 虚占率 < 10%
│   └─ 【A】降非业务 requests  →  不够再 【F】降业务 requests  →  仍不够才 【D】/【E】
├─ 缺的是【CPU】且 ③ 虚占率正常（30~80%）
│   └─ 【D】扩节点 或 【E】换机型（比较单位核成本，见 3.4）
└─ 不缺口，只是「控制台红」
    └─ 【B】降 limits（唯一需要做的事）
```

### 3.3 优先级排序（按「单位收益 ÷ 风险」）

```
【C】下线冗余 addon     ← 最高：整份资源 + 槽位一起省，且不碰业务
  ↓
【B】降 limits           ← 次高：零风险零中断，但收益只体现在超卖率
  ↓
【A】降非业务 requests   ← 主力：本手册核心，收益最大
  ↓
【E】换机型             ← 需要重建节点，但性价比可能是数量级差异
  ↓
【F】降业务 requests     ← 有业务影响面，要压测
  ↓
【D】扩节点             ← 最后手段：花钱最多，且每台再加一份底噪
```

**为什么 A 在 E 前面**：A 是**零成本**把已有容量释放出来，E 要停机重建节点。只有当 A 做到收益归零（② 底噪 < 15%，③ 虚占正常）之后，E 才有意义。

**为什么 D 在最后**：扩一台节点不仅要付实例钱，还要**再付一份 430m 的底噪**。底噪没压下来就扩节点，是在放大浪费。

### 3.4 量化对比：扩节点 vs 换机型（jkt 真实算例）

**原始状态**：4 × `ecs.g9i.large`（2C8G），每台 `maxPods` = 15。

| 方案 | 台数 | 总核数 | 总槽位 | 可用容量（扣底噪后） | 月成本 | 相对 |
| --- | --- | --- | --- | --- | --- | --- |
| 现状 4×`g9i.large` 2C8G | 4 | 8 核 | 4×15 = **60** | 4×(1,930−800) = 4,520m | 基准 | — |
| **扩节点** 5×`g9i.large` | 5 | 10 核 | 75 | 5×1,130 = 5,650m | +25% | ❌ 多付一份底噪 |
| **换机型** 2×`g9i.xlarge` 4C16G | 2 | 8 核 | 2×48 = **96** | 2×(3,920−430) = 6,980m | **−4.5%** | ✅ 同核数、槽位 +60%、成本更低 |
| 换机型 3×`g9i.xlarge` | 3 | 12 核 | 144 | 3×3,490 = 10,470m | +43% | 容量过剩 |

**结论**：换机型同时拿到「槽位 +60%」「成本 −4.5%」「可用容量 +54%」三项改善，而扩节点只换来 +25% 成本下的 +25% 容量。**槽位瓶颈一律先比机型，不要先加台数**。

关键差异来源：`g9i.large` 的 ENI 是 3×6（`maxPods` 实取 15），`g9i.xlarge` 是 4×15（实取 48）。**核数翻倍，槽位翻了 3.2 倍** —— 槽位不是线性的。

### 3.5 方案组合的收益叠加关系

不是简单相加，有**依赖顺序**：

| 组合 | 是否叠加 | 说明 |
| --- | --- | --- |
| C + A | ✅ 叠加 | A 的基线包含 C 省下的部分 |
| A + B | ✅ 叠加（不同维度） | A 改 requests、B 改 limits，互不影响 |
| A + E | ✅ 叠加 | E 之后 A 要**按新 allocatable 重跑一遍**（jkt 就是这么从 3,000m 再压到 1,960m） |
| D + A | ⚠ 顺序有关 | 先 A 再 D，否则按未优化的账扩容会多买 |
| E + D | ❌ 不建议同做 | 两个都在动拓扑，混做无法归因 |

> **jkt 的两段收敛**就是 A+E 叠加：先做 A（5,370 → 3,000m），再换机型（4×2C → 2×4C），最后按新基线再跑一次 A（3,000 → 1,960m）。

### 3.6 什么时候**不该**优化（反模式）

| 情形 | 为什么不优化 | 判据 |
| --- | --- | --- |
| 节点水位 < 50% 且无扩容压力 | 收益为 0，只剩风险 | ① < 50% |
| 底噪 < 400m、一次性 < 800m | 已到合理区间，再压是自找麻烦 | ② < 10% |
| 单节点集群 | 降副本会丢掉最后一份冗余 | 节点数 = 1 ⇒ `coredns` 只能 1 副本 |
| 控制面组件 request < 实际 P95 | 会节流，故障时表现异常 | ③ > 100% 就别再压 |
| 只改 limits 不改 requests | 不解决调度，纯心理安慰 | 目标是「多放 Pod」时 |
| 生产环境压 `terway` / `csi-plugin` 的 **requests 低于用量** | CNI/CSI 抖动会直接打业务 | 保留 ≥2 倍裕量 |

### 3.7 决策矩阵（可复用的打分表）

对候选方案按 5 个维度 1~5 分打分（**5 = 最好 / 最优**），加权后选最高：

| 维度 | 权重 | 说明 |
| --- | --- | --- |
| 收益（扩容量） | 30% | 能多放几个业务 Pod |
| 风险（业务影响） | 25% | 中断面、节流风险 |
| 可逆性 | 20% | 能否秒级回滚 |
| 工期 | 15% | 参与人力与时间窗 |
| 成本影响 | 10% | 月账单增减 |

**三站实际打分**（针对「扩业务容量」这同一个目标）：

| 方案 | 收益 | 风险 | 可逆 | 工期 | 成本 | 加权 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **A** 降非业务 requests | 5 | 4 | 5 | 5 | 5 | **4.75** | ✅ 采用 |
| **B** 降 limits | 2 | 5 | 5 | 5 | 5 | 3.85 | 附带做 |
| **C** 下线 addon | 3 | 3 | 5 | 5 | 5 | 3.90 | 先做 |
| **D** 扩节点 | 4 | 5 | 4 | 3 | 1 | 3.70 | 最后手段 |
| **E** 换机型 | 5 | 2 | 2 | 2 | 5 | 3.55 | 槽位瓶颈时首选 |
| **F** 降业务 requests | 5 | 2 | 4 | 4 | 5 | 4.05 | 压测通过才做 |

> 打分的意义不是算出一个绝对正确值，而是**逼自己把「风险」和「可逆性」摆上台面**。A 之所以压过 E，不是因为收益更大（都是 5），而是风险 4 vs 2、可逆 5 vs 2。

### 3.8 落到本次三站的具体选择

| 站点 | 当时的主要症状 | 判定 | 采用的方案 | 为什么没选别的 |
| --- | --- | --- | --- | --- |
| **jkt dev** | Pod 起不来（`Insufficient cpu`）+ 槽位只有 15 | ① 高、② 极高（800m/1,930m = 41%）、③ 低 | **C → A → E → A** | 单靠 A 只能腾出 2,400m，仍不够 3 个业务 Pod；必须 E 换 4C16G 才能同时解决槽位与核数 |
| **mnl 主站** | 缩节点后 requests 顶住，无法再调度 | ② 高（800m/7,910m = 10%，但一次性 3,610m 太重） | **A**（两批） | 2 台 8C 的核数本身够，只是非业务虚占；不需要 D 或 E |
| **sg 备站** | 同上，且单节点无法承接更多副本 | ② 中、单节点约束 | **A** + `coredns` 降 1 副本 | 单节点 ⇒ 不能靠 E（无冗余）；D 会永久多付一台，备站不值得 |

## 4. 三站实测结果

### 4.1 汇总

| 站点 | 拓扑 | 非业务 requests 前 → 后 | 降幅 | 每台 DaemonSet | 节点水位（后） | 可调度余量 |
| --- | --- | --- | --- | --- | --- | --- |
| **jkt dev** | 2×`g9i.xlarge` 4C16G | 5,370m → **1,960m** | **−63.5%** | 800m → **430m** | 约 50% | ≈ 5,880m / 7,840m |
| **mnl 主站** | 2×`g9ae/g9i.2xlarge` 8C | 5,210m → **1,960m** | **−62.4%** | 800m → **430m** | 70.8% / 55.1% | 5,860m / 15,820m（37%） |
| **sg 备站** | 1×`g9ae/g9i.2xlarge` 8C | 1,950m → **1,480m** | **−24.1%** | 800m → **430m** | 56.6% | 3,430m / 7,910m（43%） |

## 5. 措施清单（逐组件）

### 5.1 批次划分（这个顺序不能乱）

| 批 | 对象 | 是否有中断 | 为什么排这个序 |
| --- | --- | --- | --- |
| **批 0** | 下线/降副本冗余 addon | 无 | 先腾地方，后面滚动才不至于 Pending |
| **批 1** | Deployment / StatefulSet | **无**（滚动更新，副本间无缝） | 不碰网络与存储链路，最安全 |
| **批 2** | DaemonSet | **有**（逐节点重建） | `terway` 重建期间该节点新建 Pod **短暂无网络**；`csi-plugin` 重建期间该节点**挂载新卷失败** |
| **批 3** | `limits` 收敛 | 无（仅记账） | 与批 1/2 合并做亦可，但建议独立一轮便于回看 |

**批 2 必须放最后**，且要能接受「滚动期间的新 Pod 起不来」。

### 5.2 批 0：下线冗余 addon

| `gatekeeper` | 降到 **1 副本**（不可 0） | ⚠ 见下 | jkt 最终 1 副本，被托管 addon 纠回 3 |

> ⚠ **`gatekeeper` 不能 scale 到 0**：`gatekeeper-validating-webhook-configuration` 里有一条 `failurePolicy=Fail`、`rules.resources` 含 `namespaces` 的 webhook。打到 0 会让**整个集群无法创建 Namespace**（写操作全挂）。

>         res=[r for rule in (wh.get('rules') or []) for r in (rule.get('resources') or [])]

## 6. 执行步骤（复用模板）

### Step 1：盘点

```bash
cat > /tmp/audit.sh <<'EOF'
#!/usr/bin/env bash
kubectl get pods -A -o json > /tmp/p.json
python3 - <<'PY'
import json
d=json.load(open('/tmp/p.json'))
def q(v):
    if not v: return 0
    v=str(v); return int(v[:-1]) if v.endswith('m') else float(v)*1000
r=l=0.0; rows=[]
for p in d.get('items',[]):
    if p['metadata']['namespace']=='new-api': continue
    if p.get('status',{}).get('phase') in ('Succeeded','Failed'): continue
    o=(p['metadata'].get('ownerReferences') or [{}])[0]
    rc=lc=0.0
    for c in p['spec'].get('containers',[]):
        x=c.get('resources') or {}
        rc+=q((x.get('requests') or {}).get('cpu')); lc+=q((x.get('limits') or {}).get('cpu'))
    r+=rc; l+=lc
    rows.append((rc,lc,p['metadata']['namespace'],o.get('kind','?')+'/'+o.get('name',''),len(p['spec'].get('containers',[]))))
rows.sort(reverse=True)
print('%-6s %-7s %-13s %-44s %s'%('req','limit','NS','OWNER','容器数'))
for a,b,c,dd,e in rows: print('%-6.0f %-7.0f %-13s %-44s %d'%(a,b,c,dd[:44],e))
print('\n合计 requests.cpu = %.0fm   合计 limits.cpu = %.0fm'%(r,l))
PY
EOF
bash deploy/lib/ack_remote.sh mnl /tmp/audit.sh
```

**读法**：按 `req` 降序，前 5 名就是降本主战场；`容器数 > 1` 的必须走 5.5 的逐容器流程。

### Step 4：验收

```bash
cat > /tmp/verify.sh <<'EOF'
#!/usr/bin/env bash
kubectl get pods -A --field-selector=status.phase=Running -o json > /tmp/a.json
python3 - <<'PY'
import json,collections
d=json.load(open('/tmp/a.json'))
def q(v):
    if not v: return 0
    v=str(v); return int(v[:-1]) if v.endswith('m') else float(v)*1000
agg=collections.defaultdict(lambda:[0.0,0,0.0])
for p in d['items']:
    n=p['spec'].get('nodeName') or '?'
    agg[n][0]+=sum(q(((c.get('resources') or {}).get('requests') or {}).get('cpu')) for c in p['spec'].get('containers',[]))
    agg[n][2]+=sum(q(((c.get('resources') or {}).get('limits') or {}).get('cpu')) for c in p['spec'].get('containers',[]))
    agg[n][1]+=1
for n,(r,k,l) in sorted(agg.items()):
    print('  %-32s req=%5.0fm  limits=%6.0fm  pods=%d'%(n,r,l,k))
PY
echo "--- 非 Running ---"; kubectl get pods -A | grep -vE 'Running|Completed|NAME' | head -6; echo "(空=正常)"
echo "--- 业务 Pod ---"; kubectl -n new-api get pods -o custom-columns='N:.spec.nodeName,S:.status.phase' --no-headers | sort | uniq -c
EOF
bash deploy/lib/ack_remote.sh mnl /tmp/verify.sh
```

**通过判据（四条全中才算完）**：

1. 非 Running Pod = **0**
2. 业务 Pod 全部 `Running`，且**每台节点都有分布**（不能全堆一台）
3. `requests` 合计下降，且**总账自洽**：`业务 requests + 非业务 requests = 各节点 requests 之和`
4. 节点数符合预期（没有被 CA 偷偷扩容）

第 3 条是最容易漏的验证——数字不自洽说明某个组件被漏改。

## 7. 踩坑与处置

| # | 现象 | 根因 | 处置 |
| --- | --- | --- | --- |
| 1 | 超卖率只从 456% 降到 331% | `set resources -c <主容器>` 只改一个容器 | 逐容器改（见 5.5） |
| 2 | `gatekeeper` scale 到 0 后集群无法建 Namespace | `failurePolicy=Fail` + `rules=namespaces` 的 webhook | 只降到 1 副本；先跑 Step 2 ① 自检 |
| 3 | `gatekeeper` 副本被纠回 3 | ACK **托管 addon** 有纠偏机制 | 接受，或从控制台「组件管理」改 |
| 4 | DaemonSet 滚动期间节点数变多 | 出 Pending → **cluster-autoscaler 立即扩容** | **先锁 `max`** 再操作；滚动结束后缩回 |
| 5 | `RemoveNodePoolNodes` 报 `InvalidRemovingNodes.Autoscale.LessThanMinSize` | 移除后低于/等于 `min_instances` 都拒 | 先 `ModifyClusterNodePool` 临时降 `min` |
| 6 | `ScaleClusterNodePool --body '{"count":N}'` 把 2 台变 5 台 | `count` 是**增量**语义 | 禁用；规模一律用 `ModifyClusterNodePool` 的 `min/max` |
| 7 | `DescribeClusterNodePoolDetail` 报参数非法 | 参数名是 `--NodepoolId`（小写 p） | 按报错里的 `did_you_mean` 改 |
| 8 | `--NodepoolId np-mnl-app` 报 `ErrorNodePoolNotFound` | 节点池 **ID ≠ 名字** | 用 `DescribeClusterNodePools` 拿真实 ID |
| 9 | 单节点集群 `coredns` 第 2 副本永远 Pending | pod anti-affinity | `scale deploy coredns --replicas=1` |
| 10 | `terway` 重建期间新 Pod 起不来 | CNI 短暂不可用 | 提前告知；避开业务高峰；逐台滚 |
| 11 | 缩容后旧实例还在计费 | `ModifyClusterNodePool` 是异步的 | `aliyun ecs DescribeInstances --InstanceIds` 查无才算释放 |

## 8. 回滚

改动全是 `kubectl set resources` / `scale`，回滚 = 反向赋值。

```bash
# 单组件回滚示例
kubectl -n arms-prom set resources deploy/arms-prometheus-ack-arms-prometheus \
  -c arms-prometheus-operator --requests=cpu=1000m --limits=cpu=3000m

# 恢复副本
kubectl -n kube-system scale deploy/ack-koord-manager --replicas=1
kubectl -n kube-system scale deploy/ack-cost-exporter --replicas=1
```

**无需回滚的情形**：只是 `requests` 定得低了导致调度过于拥挤（节点水位 >85%）→ 挑高水位节点上最重的那个业务 Pod 调回即可，系统组件不必动。

**必须回滚的情形**：`metrics-server` 起来后 `kubectl top` 报错、`coredns` 解析失败、`csi-plugin` 挂卷失败 —— 说明 request 压得比实际用量还低，恢复原值。
