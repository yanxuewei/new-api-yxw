# SG 侧两个服务器组「一模一样」—— 成因、能否删除、如何合并

**日期**：2026-10-12 · **站点**：新加坡 `alb-amdwm60xmznh7s1nae`（ap-southeast-1）
**触发**：控制台「服务器组」页出现两个名字完全相同、后端完全相同的组，fanyan 问「为什么一模一样？可以去掉其中一个吗？去掉会有副作用吗？」
**结论**：**正常现象，不是残留、不是配置错误**。**不能手删**（三重拦截）。真要减成一个，唯一合法做法是**把两个 Ingress 合并成一个**——但收益仅「列表少一行」，建议不做。

---

## 1. 现象（实测）

控制台勾选区域内的两个组：

| | A | B |
|---|---|---|
| ServerGroupId | `sgp-8m8eknlyw0z1busl6r` | `sgp-rlxs1mqishcxcfkx7u` |
| 名称 | `new-api-new-api-ph-standby-80` | `new-api-new-api-ph-standby-80` |
| 创建时间 | 2026-10-06T07:19:03Z | 2026-10-06T06:29:39Z |
| 后端 | `10.1.19.127:3000` w100 / `10.1.38.123:3000` w100 | **完全相同** |
| 类型 / 协议 / 调度 | Instance(Eni) / HTTP / Wrr | **完全相同** |
| 健康检查 | on · HTTP · `/api/status` · `http_2xx` | **完全相同** |
| 会话保持 | 关 | 关 |
| VPC / ALB | `vpc-t4nimmwvruexbnene0a3r` / `alb-amdwm60xmznh7s1nae` | **完全相同** |
| **`ingress_name` 标签** | **`new-api-ph-standby-ip`** | **`new-api-ph-standby`** |

后端一致性程序化比对：`A == B → True`。

**两者唯一的结构性差异就是 `ingress_name` 标签** —— 这一个字段解释了全部。

---

## 2. 成因：Controller 的派生粒度是 **Ingress**，不是 Service

SG 侧是两个**不同 Ingress**，各自引用了**同一个** Service `new-api/new-api-ph-standby:80`：

| Ingress | `spec.rules[].host` | `order` | 被引用端口 | 派生组 |
|---|---|---|---|---|
| `new-api-ph-standby` | `sg-standby.internal.likha.hk`, `sg.likha.hk` | 默认 | HTTP:80 + HTTPS:443 | `sgp-rlxs1mqishcxcfkx7u` |
| `new-api-ph-standby-ip` | **（无 Host）** | **50** | HTTP:80 + HTTPS:443 | `sgp-8m8eknlyw0z1busl6r` |

> 服务器组命名规则 `<namespace>-<service>-<port>` ⇒ 两个 Ingress 指向同一 Service:Port ⇒ **名字必然相同**。
> Controller 用标签 `ingress.k8s.alibaba/ingress_name` 记录**所有权** ⇒ **不会因为名字撞车而合并**。

**判定公式**：

```
服务器组数 = 引用该 Service:Port 的「不同 Ingress 数」
```

### 交叉验证：同一个 Ingress 内部是**复用**的

`new-api-ph-standby` 一个 Ingress 里有**两条 rule**（`sg-standby.internal.likha.hk` 与 `sg.likha.hk`），ALB 上展开成 4 条规则（80 的 prio3/4 + 443 的 prio2/3），**全部指向同一个组 `sgp-rlxs1mqishcxcfkx7u`**。

⇒ **同 Ingress 内多条 rule 复用一组；跨 Ingress 各派生一组。** 这就是「规矩」的全部。

### mnl 侧为什么只有一个？

| 站点 | 具名 host 与无 Host 兜底 的 Ingress 形态 | 组数 |
|---|---|---|
| **mnl** | 都在 **同一个** Ingress `new-api-stable-ip` 内（`hosts=ph-verify.internal.likha.hk,(无 Host)`） | **1** 个（`sgp-j4qrgy3f7bcv1r67na`，443 prio2/3 + 80 prio5 共用） |
| **sg** | 拆成 **两个** Ingress（`new-api-ph-standby` / `new-api-ph-standby-ip`） | **2** 个 |

同类现象在 mnl 也能看到：`new-api-canary-weight` 与 `new-api-canary-header` 两个 Ingress 指向同一 Service ⇒ 两个 `new-api-new-api-canary-80`（`sgp-1eevkvsn0c32t3e1ya` / `sgp-slwubl6v6sb2xtsxrz`）。

**所以这不是 bug，是任务 19（mnl）与任务 25（sg）落地形态不同留下的差异。** 功能完全等价。

## 3. 能不能去掉一个？—— 不能手删（三重拦截）

| 拦截层 | 实测 |
|---|---|
| ① **规则引用** | `aliyun alb DeleteServerGroup --DryRun true` → **两组均被拒**：`ResourceInUse.ServerGroup` / *The specified resource is in use*。因为 443 的 prio2/3/4、80 的 prio3/4/5 都挂在它们身上 |
| ② **托管归属** | 标签 `ack.aliyun.com=ca75829e3492d491d9d434de087913798` + `ingress.k8s.alibaba/albconfig=kube-system/sg-alb` + `ingress.k8s.alibaba/resource=<sha>` ⇒ ALB 实例/监听/规则/**服务器组全由 ACK Controller 派生**。此前已实测同类写操作 3/3 回 `OperationDenied.ServiceManagedResource` |
| ③ **reconcile 重建** | 就算绕过 ①② 删成功，Controller 下一次调谐会**重新建回来**（大概率换新 ID） |

> ⚠️ 探针说明：`DryRun` 在 `ResourceInUse` 处就短路了，**没走到托管校验那一层** —— 托管属性由标签直接坐实，不能靠这个 DryRun 结果反推「如果是非托管就能删」。
> 探针跑完复核：服务器组数**仍为 4**，零变更。

### 删掉的副作用

- **立刻 502**：承载规则失去目标组 —— 443 侧的「无 Host 兜底」或「`sg.likha.hk` 具名转发」会立刻失败。
- **不持久**：Controller 秒级重建，白忙一场，还吃一次故障窗口。
- **无收益**：ALB 不按「服务器组个数」计费。

**唯一真实成本（保留现状的成本）**：每个组会**独立**对同一批后端发健康检查 ⇒ 2 组 × 2 Pod = 4 条探针流，合并后 2 条。量级极小（`/api/status` 轻量接口），不影响 LCU 结论。

## 4. 真想减成一个：把两个 Ingress 合并（唯一合法路径）

**思路**：让无 Host 兜底与具名 host 回到**同一个 Ingress** 里（即 mnl 的形态），Controller 就只派生 1 个组。

### 4.1 改法

改 `deploy/manifests/ingress-sg-standby.yaml`（对应 `new-api-ph-standby`）：在 `spec.rules` 追加一条**不带 host** 的 rule，backend 仍指 `new-api-ph-standby:80`；`listen-ports` 已是 `[{"HTTP":80},{"HTTPS":443}]`，无需改。然后删除 Ingress `new-api-ph-standby-ip` 及其真源 `ingress-sg-standby-noHost.yaml`。

### 4.2 关键约束：`order` 是 **Ingress 级**，不是 rule 级

合并后 `order` 只能取一个值。**用默认值**即可（不要沿用 `-ip` 那个 `50`）：
- 组内优先级由 Controller 按 rule 顺序排 ⇒ 无 Host 那条自然排最后；
- 组间由 `order` 排 ⇒ 默认值让整个组排在 `new-api-sg-*-redirect/canonical`（`order=1`）之后。

合并前后 ALB 规则布局**完全等价**：

| | 合并前 | 合并后 |
|---|---|---|
| 443 | prio1 canonical · prio2 `sg-standby.internal` · prio3 `sg.likha.hk` · prio4 noHost | prio1 canonical · prio2/3/4 同上（同一组） |
| 80 | prio1 `www`跳转 · prio2 `likha.hk`跳转 · prio3 `sg-standby.internal` · prio4 `sg.likha.hk` · prio5 noHost | prio1/2 同上 · prio3/4/5 同上（同一组） |

⚠️ **绝不能**把无 Host rule 排到具名 host rule 之前 —— 它会吃掉所有流量（无 Host 条件 = 匹配一切）。这正是 `order` 必须留默认的原因。
⚠️ `new-api-ph-standby` 的另一条 rule（`sg-standby.internal.likha.hk`）保留不动。

### 4.3 执行顺序（无窗口）

1. **先 apply 合并版** `new-api-ph-standby`（多出一条 noHost rule）→ 瞬时 3 个组；
2. 校验 ALB 规则数（80: 5→6、443: 4→5）；
3. **再 delete** Ingress `new-api-ph-standby-ip` → Controller GC 掉 `sgp-8m8eknlyw0z1busl6r` → 回落 **1 个组**；
4. 双协议验收：`curl -H 'Host: sg.likha.hk'` 200、无 Host 200、`sg-standby.internal.likha.hk` 200。

过渡期两条 noHost 规则同时存在、指向不同组但**同一 Service** ⇒ 行为等价，**不存在错误路由窗口**。

### 4.4 建议

**不做。** 收益仅为「控制台列表里少一行」，代价是动一次生产 Ingress + 一份 yaml 重构。若确有洁癖要合并，选低峰期，走 `add-domain.sh` 的 `plan → apply → verify` 流程并保留回滚（真源 `git revert` + 重新 apply 旧 Ingress）。

## 5. 顺手修掉的一个显示缺陷

`add-domain.sh ls` 的 Ingress 表此前**漏显无 Host 的那条 rule**（go-template 的 `{{if .host}}` 把空 host 直接跳过）。已修：

```diff
- {{range .spec.rules}}{{if .host}}{{.host}},{{end}}{{end}}
+ {{range .spec.rules}}{{if .host}}{{.host}},{{else}}(noHost),{{end}}{{end}}
```

修复后 mnl 侧正确显示 `new-api-stable-ip … hosts=ph-verify.internal.likha.hk,(无 Host)` —— **一个 Ingress 同时含具名与无 Host 规则**，正是「mnl 只有 1 个组」的直接证据。

---

## 6. 本次新增铁律

1. **服务器组派生粒度 = Ingress**（不是 Service、不是 rule）：`组数 = 引用该 Service:Port 的不同 Ingress 数`；同 Ingress 内多 rule 复用一组。
2. **同名不同 ID 是必然**，不是残留；判定归属**只看标签 `ingress.k8s.alibaba/ingress_name`**，不看名字。
3. **托管服务器组删不掉**：先撞 `ResourceInUse.ServerGroup`，再是 `ServiceManagedResource`，最后还有 reconcile 重建。
4. **`order` 是 Ingress 级**：合并多 rule 时，含「无 Host」rule 的 Ingress 必须用默认 order 或确保整组排在具名规则之后，否则无 Host rule 会吃掉全部流量。
