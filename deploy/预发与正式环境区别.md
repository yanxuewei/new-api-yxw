## 1. 术语澄清：rc 的含义

**问题**：tag 规则中「发布 tag 一律 `vX.Y.Z` 打在 main 上；预发 `vX.Y.Z-rc.N` 打在 `release/*` 上」——这个 rc 的含义是？

**结论**：`rc` = **Release Candidate（发布候选版本）**，是 SemVer 规范中的预发布标识。

- `v1.2.0-rc.1` 表示「候选第 1 版」：内容基本冻结，理论上就是将来要发布的 v1.2.0，只是还没有经过预发环境验证、尚未正式官宣。
- 每修复一个回归问题重出镜像，就递增编号：`rc.1 → rc.2 → rc.3`……
- 候选在 staging 通过回归 + 冒烟后，最终正式版 `v1.2.0`（不带 rc 后缀）打在 `main` 上，发布到 prod。
- 带 `-rc.N` 的 tag 会触发 `release.yml` 构建镜像并自动部署到 staging；不带 rc 的正式 tag 才允许走 prod 通道。

**在流程中的位置**（对应规范 10.2 节版本火车）：

```
D-2  切 release/x.y.z
D-1  CI 出 rc.1 镜像 → staging 部署 → 回归发现 bug → 修复 → rc.2 → 再验证 → …
D0   rc.N 验证通过 → PR 合入 main → 打正式 tag vX.Y.Z → 发布 prod
```

## 2. 术语澄清：Staging 的含义

**问题**：「Staging 与 Prod 差异」——这个 staging 的含义是？

**结论**：Staging = **预发布环境（预发）**，是一套配置尽量与生产保持一致（同版本中间件、同规模节点、同网络拓扑）但**不承接真实用户流量**的独立集群。

- 定位：正式发布前的「彩排舞台」，用真镜像、真配置、假流量做最后一道质量验证。
- 与 prod 共用同一个镜像 digest（一次构建、多环境复用），环境差异全部收敛在 ops 仓库的 `overlays/staging` 与 `overlays/prod` 中。
- 触发方式：`rc.*` tag 自动部署、自动合并生效；prod 则必须正式 tag + 人工批准 ops PR。

## 3. 发布流水线中的 Trivy 扫描与 SBOM

**问题**：流水线图中红框的 Trivy 扫描的作用是什么？SBOM 又是什么？

**Trivy**：开源的镜像/依赖漏洞扫描器（Aquasecurity 出品）。在 `release.yml` 中对推送到 ACR 的镜像做 CVE 漏洞扫描：

- `trivy image --exit-code 1 --severity CRITICAL <image>` —— 发现 **CRITICAL 级漏洞即让流水线失败，阻断发布**；
- HIGH 级不阻断但限时修复（≤2 个迭代，见规范 9.3）；
- 作用位置在「推镜像之后、开 ops PR 之前」，即带毒镜像根本到不了 staging/prod。

**SBOM**：Software Bill of Materials，**软件物料清单**——这份镜像里到底包含哪些依赖包、什么版本、什么许可证的完整清单。

- 流水线用 `syft` 生成 **CycloneDX 格式** SBOM（`sbom.json`），随 GitHub Release 附件留存；
- 价值：上游爆出某个组件漏洞（如 log4shell 类事件）时，可立即反查「哪些版本、哪些环境用过这个组件」，而不必重新扫镜像；也是安全合规审计的要求。

**与预发/正式的关系**：这两个检查对 rc 镜像和正式镜像一视同仁——**同一 digest 通过扫描后才可能进入任一环境**，不存在「预发可以跳过扫描」的通道。

## 4. 预发不承接真实用户流量，如何测试验证

**问题**：staging 不承接用户流量，那我们如何测试验证？

**结论**：「不承接真实用户流量」指的是不暴露给公网真实客户，不等于没有流量。预发的流量来源是**人为注入的验证流量**，按成本从低到高：

1. **自动化冒烟/E2E（规范内置）**
   - `e2e-nightly.yml` 每日 02:00 对 staging 跑冒烟集，失败 @值班人；
   - rc 镜像部署到 staging 后，发布窗口 D-1 由测试同学执行回归用例。
2. **测试账号 + 造数**
   - 预发使用独立的测试数据（脱敏后从 prod 导入或用脚本生成）；
   - 团队用专用测试账号走真实业务链路（登录、下单、支付回调用 sandbox 等）。
3. **手工/内部真实使用（dogfooding）**
   - 组内同学直接在预发环境操作真实功能，等价于「自己当用户」。
4. **流量回放 / 影子流量（进阶，可选）**
   - 录制 prod 真实请求（脱敏），在 staging 重放，比对响应差异；
   - 这是最接近真实流量的方式，4 人小组按需引入即可，不作为强制要求。
5. **专项演练**
   - 回滚演练（每季度，在 staging 模拟）、容量/压测、故障注入等，都安排在预发做而不是 prod。

**关键点**：预发验证的本质是把「prod 才暴露的问题」提前在等价环境里用可控流量暴露出来；验证通过的标准是回归 + 冒烟全绿、P0/P1/P2 清零（见规范 10.6 发布时间线的 gate）。

## 5. Canary 是不是 staging 环境

**问题**：（流程图中的）canary 是不是 staging 环境？

**结论**：**不是。** 两者是完全不同维度的概念，只是都发生在「正式全量放开之前」。

| | Staging（预发） | Canary（金丝雀发布） |
|---|---|---|
| 位置 | **独立集群**，在 prod 之外 | **prod 集群内部**的一小部分实例 |
| 流量 | 真实用户流量**不进入** | **真实用户流量**按 1%→5%→25%→100% 逐步切分 |
| 目的 | 用等价环境验证功能正确性 | 用小比例真实流量验证线上风险可控 |
| 回答的问题 | 「这个版本是对的吗？」 | 「这个版本上线安全吗？炸了影响多大？」 |
| 失败代价 | 零（用户无感知） | 有限（仅切到金丝雀的那部分真实用户受影响，随时切回） |

- 「Canary」一词来源于矿井金丝雀：先让一小批实例「试毒」，指标（错误率、P99、告警）正常再逐步放量。
- 顺序是：**rc 镜像 → staging 验证 → 正式 tag → prod 全量或金丝雀式放量**。
- 在当前 4 人小组的规范里，prod 发布默认采用 ArgoCD 滚动发布 + 30 分钟观察窗口；金丝雀（如 Argo Rollouts）是后续按需引入的增强手段，引入后它发生的地点仍然是 prod 集群，不会变成第二套预发。

## 6. Staging 与 Prod 详细差异对比

**问题**：请详细对比 staging 与正式环境的差异？

### 6.1 总对比表

| 维度 | Staging（预发） | Prod（正式） |
|------|----------------|--------------|
| **服务对象** | 团队自己（测试、演练、冒烟） | 真实用户 |
| **用户流量** | 无真实流量，全部为注入流量（E2E、测试账号、回放） | 100% 真实流量 |
| **入口** | 仅内网/VPC 可达，不公开 DNS、不加公网 LB | 公网正式域名 + LB + CDN/WAF |
| **触发部署的 tag** | `vX.Y.Z-rc.N`（预发候选）或 develop 合入（可选） | `vX.Y.Z` 正式 tag（经 release PR 合入 main） |
| **镜像** | 与 prod **同一 digest**（一次构建多环境复用，禁止为预发单独构建不同镜像） | 同左，通过 digest 严格对应 |
| **部署批准** | ops PR **自动合并生效**，无需人工 | ops PR 需 **≥1 名值班人批准**；紧急 hotfix 可电话批准事后补记录 |
| **配置来源** | ops 仓库 `overlays/staging/` | ops 仓库 `overlays/prod/` |
| **节点规模/规格** | 同版本中间件、拓扑一致；副本数与节点规格可缩至约 1/2~1/3（成本考虑），但必须能覆盖功能与链路验证 | 全量容量、含高可用多可用区 |
| **数据库/中间件** | 独立实例，数据为脱敏导入或造数；账号/密钥是 staging 专用一套 | 生产实例，敏感数据，最小权限访问 |
| **外部依赖** | 对接第三方一律 **sandbox/模拟环境**（支付、短信、AI 上游等） | 真实对接，计费 |
| **回滚方式** | 自动（健康检查失败即回退），无人感知 | revert ops PR，目标 ≤10 分钟，人工盯守 |
| **观察要求** | 冒烟 + 回归通过即可 | 发布后 **30 分钟观察窗口**（错误率、P99、日志、告警） |
| **告警等级** | 失败 @值班人，不计 SLA 故障 | 7×24 P0-P3 分级 SLA（P0 响应 ≤10 分钟） |
| **发布窗口约束** | 任意时间可部署（这正是它的价值：不打扰用户） | 固定周二/周四 10:00–12:00；节前冻结窗口内禁止发布 |
| **变更红线** | 允许为演练临时改动（压测、故障注入、回滚演练） | 任何变更必须体现为 ops 仓库一次 commit，禁止手工 kubectl 操作 |

### 6.2 刻意保持「一致」的部分（预发之所以可信的前提）

1. **同一镜像 digest** —— 环境差异全部放 overlay，杜绝「预发验的镜像不是上线的镜像」。
2. **同版本中间件与网络拓扑** —— DB/Redis/MQ 大版本一致，VPC 内网拉镜像路径一致（`-registry-vpc` 域名）。
3. **同一 GitOps 链路** —— staging 和 prod 都只能经「tag → Actions → ACR → ops PR → ArgoCD」这条路进入，审批严格度不同但机制相同，保证预发验证过的发布链路本身就是真实链路。
4. **同一套 CI 门禁** —— Trivy CRITICAL 阻断、SBOM 生成对两个环境一视同仁。

### 6.3 在端到端时序中的位置

```
release/x.y.z ──rc.N tag──▶ 构建+扫描 ──▶ ACR ──▶ ops PR(自动合并) ──▶ ArgoCD ──▶ staging 回归+冒烟
                                                                        （失败：自动回退，修复后重出 rc）
rc 验证通过 ──PR 合 main──▶ tag vX.Y.Z ──▶ 同一 digest ──▶ ops PR(值班人批准) ──▶ ArgoCD ──▶ prod 滚动发布
                                                                        （异常：revert ops PR ≤10min 回滚）
```

## 7. 核心结论速查

| # | 结论 |
|---|------|
| 1 | `rc` = Release Candidate 发布候选，`vX.Y.Z-rc.N` 打预发、编号递增，验证通过后正式 `vX.Y.Z` 上 prod |
| 2 | staging = 预发布环境：配置对齐生产、独立集群、不承接真实用户流量的「彩排场」 |
| 3 | Trivy 扫镜像漏洞（CRITICAL 阻断发布）；SBOM 是镜像的软件物料清单，用于漏洞反查与合规审计；两者对 rc/正式镜像同等生效 |
| 4 | 预发不接真实流量 ≠ 没有流量：用 E2E 冒烟、测试账号+造数、内部 dogfooding、（可选）流量回放来验证 |
| 5 | Canary 不是 staging：金丝雀发生在 **prod 集群内**、切**真实用户流量**逐步放量；staging 在 **prod 之外**、用**注入流量**验证功能 |
| 6 | 两环境差异集中在：流量来源、入口暴露、部署批准（自动 vs 人工）、数据与外部依赖（sandbox vs 真实）、回滚与观察要求、发布窗口约束；而镜像 digest、中间件版本、GitOps 链路、CI 门禁刻意保持一致 |
