## 17:52 · fanyan 决定「保持 ACR_REPO=newapi-master 不动 + 改回用 tag 不用 digest」

理由：ACR 仓库**已开启「不可变」**（tag 不可覆盖/不可删除）⇒ tag 与 digest 等价稳定，但可读性远好于 64 位串；且镜像不会删除，没有「digest 被清理导致拉不到」的风险。

**落地**：
- 业务仓 PR #15（`ci/use-immutable-tag`）：`bump-ops` 由 `set-image.sh "${IMAGE}@${DIGEST}"` 改为 `"${IMAGE}:${TAG}"`，digest 仅打印日志；文件头补第 4 条红线「镜像用不可变 tag，不是 digest，也不是 latest」。
- ops 仓 `15d287b`：`overlays/jkt-dev` 的 `digest:` → `newTag:`；README 红线 3 改为「写不可变 tag」并**标注前提：ACR Immutable 必须保持开启**（关掉则 revert 会指向错误镜像）。
- **实测**：ArgoCD 同步后 Deployment `spec.image` = `...newapi-master:dev-20261027-5878218`，而 Pod `status.containerStatuses[].imageID` 仍是 `...@sha256:45c680a2…` —— **K8s 会自动记录解析后的真实 digest**，所以「tag 可读 + digest 可审计」两者兼得。这是 tag 方案的关键论据。
- 注意：`deploy/` 目录在本仓 development 上已被整体删除（运维脚本只在私有 ops 仓），所以文档只改 ops 仓。

**保留的判据**：用 tag 后要核对「线上到底跑的哪个 digest」，看 `kubectl get pod -o jsonpath='{...imageID}'`，不要看 `spec.image`。
