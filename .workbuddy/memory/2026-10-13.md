### ★ 备站 conns 覆盖 `10/5` 被删 —— 判定：**不建议删，建议恢复**

用户反馈：「sg Deployment env 覆盖成 10/5 我删了，帮我判断一下，是否要删除？」

**实测（纯只读）**：
- sg `deploy/new-api-ph-standby` 的 container env **只剩 `NODE_TYPE` + `GOMAXPROCS`** ⇒ 两个 conns 覆盖**已被移除**；新 RS `new-api-ph-standby-65c4b9576b` 创建于 **2026-10-13T02:56:23Z = 10:56 HKT**（用户操作）。
- Pod 内实测**已回落 `100` / `50`**（来源 CM `new-api-config`）；`SQL_DSN` = `pgm-5tstdhko64x2c01wpub.pgsql.ap-southeast-6….com:6432` ⇒ **与主站共用同一 PgBouncer**（同一 `max_client_conn=2000` 池）。
- mnl 未受影响：stable/canary `100`/`50`（来自 CM）、master `100`/`50` 且 `SQL_DSN` 端口 `5432`。

**判定依据（4 条）**：
1. 它是**书面裁定**：`standby-deployment.yaml` 明文「卡片裁定②（2026-09-29）… **覆盖** cm 里的 100/50」；指南任务 17/28/41 多处以 `10`/`5` 为**验收期望值**（如任务 28 卡「期望 10（IDLE 期望 5）」）。
2. 它是 **I-1 预算的组成部分**：§2.2 的 `20×10 = 200` 就是它。删后 worst-case `1300 + 100 + 20×100 = 3400 > 2000` ⛔ 击穿 `pgbouncer.max_client_conn`。
3. 备站定位是**低流量旁站**，不应长期占主库连接位；`IDLE 5→50` 让每 Pod 常驻 50 条空闲连接（16 副本 = 800 条），挤占共享预算。
4. **经池也拿不到额外吞吐**：`(newapi_sg,newapi)` 池 server 侧仍被 `default_pool_size=50` 封顶 ⇒ 抬 client 槽位只增排队。

⇒ **结论：建议恢复 `10`/`5`**（恢复命令见 G11 报告 §6.2）；**当前待用户确认**。
**现状影响**：删除后**无即时故障**（`ConnectionUsage` < 5%，备站仅 2 副本）；风险只在「两地同时扩容」时兑现。
