### B. 本机出网的真实边界（实测，非"抖动"）
- **Windows 10 19045 / 22H2** ⇒ `networkingMode=mirrored` **用不了**（需 Win11 22H2+，build ≥22621）。WSL 2.7.14.0 / kernel 6.18.33.2。
- 并发新建 TCP 到**同一目标**（`/dev/tcp` 探测，宿主机 WSL）：
  `n=2/5/10/20` → **100% 成功**；`n=40` → 33/40；`n=80` → **0/80**；`n=160` → **0/160**。
  且突发后**连单条也短暂 FAIL**，数秒~数十秒自行恢复（**不是墙、不是 conntrack 满**，conntrack 仅 112/262144）。
- 换目标（aliDNS、Cloudflare、其它 CDN）同样在 n=40 就大量失败 ⇒ **与目标站无关**。
- **宿主机与容器一样失败**（`--network host` 也是）⇒ 瓶颈在 **WSL2 VM 的整条上行（Windows 侧 NAT）**，与 Docker 无关。
- `BUN_CONFIG_MAX_HTTP_REQUESTS=16` 对 `bun install` **实测无效**（仍 214 条 SYN_SENT）⇒ 降并发旋钮不可用。
- Windows 侧代理是 `quickqservice-g90.exe`，**只监听 127.0.0.1:8800** ⇒ WSL 不可达（172.18.0.1:8800 closed）；`gh` CLI 未安装。

### C. 解法：本地「限并发 CONNECT 代理」
`deploy/logs/conc_proxy.py`（Python 标准库，~120 行）：
- 监听 `0.0.0.0:8899`，用 `Semaphore(max_upstream)` **只限制上游 `connect()` 的并发**（默认 8，落在 n≤20 安全区）。
- 容器 → 代理走 **docker bridge（172.17.0.1）**，不经 WAN NAT ⇒ 本地建连不丢包；上游由代理串行化。
- 实测：bun 认 `HTTPS_PROXY`（代理日志出现 `[conn] registry.npmmirror.com:443`），`bun add lodash` 427ms 成功。
- 灌进构建：`bash deploy/logs/push_acr.sh -n prod -t <tag> --build-only --go-proxy aliyun --proxy http://172.17.0.1:8899`
  ⇒ 运行时 `active: 8` 恒定、`fail: 0`（对比裸跑：214 SYN_SENT / 全挂）。
- 脚本：`deploy/logs/setup_proxy.sh`（起代理+自测）、`deploy/logs/run_build.sh`（脱离会话启动构建）、`deploy/logs/peek_build.sh`（看阶段）。

### D. 本次新增的两个 WSL 坑
- **长任务必须 `setsid nohup … &` 脱离会话**：`wsl.exe` 退出/后台任务收尾会 **SIGHUP 连带杀掉** WSL 侧的构建进程（实测 `buildx`+`bun install` 一起消失）。
- **`pkill -f 'xxx'` 会匹配自己的命令行**：外层 `wsl … bash -c "sed -i … xxx.py && bash …"` 里出现 `xxx.py` ⇒ `pkill -f 'xxx.py'` **自杀（exit 15）**。改用**不含该字面量**的模式（如按参数名 `max-upstream`）。
