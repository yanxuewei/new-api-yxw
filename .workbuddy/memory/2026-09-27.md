## 12:1x GTM 池间语义澄清（回答"GTM 平时是否给新加坡分摊流量"）

**答：不分摊。** 方案口径 = 主备地址池（failover），不是多主池分摊。
方案内证：xlsx `sheet2#16` / `sheet3#9`「主地址池 = 马尼拉 ALB；备地址池 = 新加坡 ALB」；指南 `:2440` 坑5「备站只接 GTM 备地址池，**常态零流量**」；指南 `:234`「虚线那条路径常态**不承载流量**」；指南 `:3787`/`:4186` 备池最终决策「**常驻但权重 0**」；指南 `:3812`「SG→MNL RDS 探测失败率 >10% → **自动把备池权重置 0**，禁止切换」。

**官方语义（2026-09-27 查证 `help.aliyun.com/zh/dns/principles` + `/document_detail/2782188.html` + `/zh/dns/gtm2-access-policy`）**：
- 「访问策略」= 策略类型（按地域 / 按延迟）+ **主地址池集合 / 备地址池集合** + **生效地址池集合切换策略**，三者正交
- 主池健康 → **优先返回主池 IP**；主池不可用 → 自动切备池
- 「基于访问延时的访问策略」**仅旗舰版**，官方自警「延时调度库精准性与更新时效性问题，有可能出现个别地域延时无法做到最优」+「可能用户请求会集中调度到某个IP上」
- 触发条件含「**地址池集合可用 IP 最小数量阈值**」：健康 IP 数 < 阈值 → 整池判不可用 → 切备池
- 池内「负载均衡策略」= 返回全部地址（默认，**平均分配**）/ 按权重

**核心口径**：把跨区切换判定点从 GTM（DNS 层，45–60s 判定 + 不可控传播）下沉到 **DCDN 回源层**（主动四层探测 2.5s × 3 = 7.5s 判定，客户端连 CDN 边缘 IP 不变 → 传播 0）→ 端到端 RTO **10–20s**（对比现状乐观 105s / 中位 6.8min / 长尾 31.8min）。净增 **≈ +74 USD/月**（下行流量 60 + 动态请求数 14.4）。

**官方机制（`configure-an-origin-server`，2026-09-10 更新）**：源站支持直接填 ALB 实例域名；主备优先级 0–127（默认主 20 / 备 30，非默认须工单）；**主动四层 TCP**，每 2.5s 探一次、连续 3 次失败判不可用；恢复每 5s 重探；回源超时 TCP 建连 10s / 写 30s / 读 30s，全链路最长 150s；默认透传 `Ali-Cdn-Real-Ip` 等；动态资源默认「性能优先回源」。

**三个硬约束**（不解决方案空转）：① 四层探测对应用层故障免疫（Pod 全挂时 ALB 返 5xx，DCDN 不摘源站）→ 工单开七层屏蔽 或 叠加 GTM；② 动态资源性能优先回源会绕过主备优先级；③ 回源读超时默认 30s → SSE 截断。另：**DCDN 不支持内网源站** → 两 ALB 必须有公网地址。

**拓扑三选一**：纯主备（仅兜 ALB 不可达）/ CDN>GTM 联动（~47s）/ **双层叠加（推荐，全兜）**。

**实施顺序**：先做零成本项 GTM `Ttl` 60 → **1s**（旗舰版支持，把可控路径 105s → 46s），再提 2 个工单，再采 2 周基线，最后才动生产 DNS。

**遗留**：DCDN 对 SSE 的缓冲/首字节行为无官方文档（须实测）；DCDN 对 5xx 回源重试可能触发 POST 重复计费；`§8.2`「60s」与 `§8.4`「≤5 min」口径打架、`§7.4.4` 缺 HPA vs 指南「HPA 2-24」矛盾 —— 4 处文档冲突待统一。

用户复跑仍报 `EOF` ＋ 本机 `host` `NXDOMAIN`、`curl` `Could not resolve host`。逐层排查后确认**根因是 ACL**。

| 检查 | 结果 | 结论 |
| --- | --- | --- |
| `cr GetInstanceEndpoint --EndpointType internet` | `Enable=true` · `Status=RUNNING` · `Domains=[…-registry.ap-southeast-6.cr.aliyuncs.com]` | 入口没问题 |
| alidns DoH `223.5.5.5/resolve` | `A → 8.220.143.202`（TTL 60） | **公网 DNS 有记录**，不是没发布 |
| `ListInstanceEndpoint` | `AclEnable=true` · `AclEntries=[{127.0.0.1/32}]` | **真实客户端 IP 必被拒** |
| 沙箱直连 `8.220.143.202:443`（修前） | `Connection timed out after 15002 ms` | ACL 静默丢包 |
| 同上（修后） | **`HTTP/1.1 401 Unauthorized`** | 修好 |

**关键认知**
- ACR **没有 ACL 总开关接口** —— `--help-search Acl` 只返回 `CreateInstanceEndpointAclPolicy` / `DeleteInstanceEndpointAclPolicy`；`AclEnable` 由条目存在性决定。
- 删光条目后 **`AclEnable` 仍为 `true`**（不会自动关闭）→ 空名单 = **Block All**，比原来更死。
- **ACR 拒收 `0.0.0.0/0`**：`CreateInstanceEndpointAclPolicy --Entry 0.0.0.0/0` → `INSTANCE_ACCESS_ACL_ENTRY_INVALID`。
- 实测 `/1`、`/8`、`/32` **都接受** → **全放行 = `0.0.0.0/1` + `128.0.0.0/1`**（拼接覆盖全部 IPv4）。

**已执行的修复（用户选择「全放行」）**
```
cr DeleteInstanceEndpointAclPolicy … --Entry 127.0.0.1/32      # 清掉无效占位
cr CreateInstanceEndpointAclPolicy … --Entry 0.0.0.0/1   --Comment "allow-all-ipv4 (push.sh)"
cr CreateInstanceEndpointAclPolicy … --Entry 128.0.0.0/1 --Comment "allow-all-ipv4 (push.sh)"
```
最终 `AclEntries = [128.0.0.0/1, 0.0.0.0/1]`。

**push.sh 同步增强（`bash -n` + dry-run 双分支验证通过）**
- `detect_egress_ip()`：依次试 `checkip.amazonaws.com` / `api.ipify.org` / `ifconfig.me/ip`。
- `acr_acl_add()` 抽出单条放行；`acr_allow_ips()` 支持关键字 **`auto`**（探测本机出口 IP → `/32`）与 **`all`**（自动展开成两条 `/1`）。
- `acr_open_internet_endpoint()`：新增 **「白名单为空但 AclEnable=true」** 的 Block-All 告警（原来只判 `127.0.0.1/32`，漏了这一种）。
- `diagnose_login_failure()`：连接层分支**新增 ACL 检查**（原来只查入口 Enable，把矛头指向 DNS/代理 → 误导）。现在空名单 / 只有 127.0.0.1 会直接点名 ACL 并给出 `--allow-ip auto|all`。

**用户本机 DNS 侧仍待观察**：`host` NXDOMAIN 但公共 DoH 有记录 → 疑为 macOS 负缓存或 Clash DNS。建议 `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder` + `dig @223.5.5.5 <域名> +short` 复核；Docker Desktop 走 Clash 时建议把 `*.cr.aliyuncs.com` 加代理直连规则（否则出口 IP 随节点漂移，白名单会失效）。

**副作用提醒**：本次调用身份仍为 `yanxuewei`（`AdministratorAccess`）。当前 ACR 公网对**全 IPv4 开放**，安全依赖「命名空间 PRIVATE + 访问凭证 + 生产 tag 不可变」；后续若要收紧，用 `--allow-ip auto` 换成具体 `/32`。

### 18:58 校正：**白名单为空 = 全放行**（我先前「空 = Block All」判断错误）

查官方文档 [配置公网的访问控制](https://help.aliyun.com/zh/acr/user-guide/configure-access-over-the-internet) 明确写：**「希望所有公网下的 ECS 均可访问企业版实例 → 保持公网访问入口开启并删除所有公网白名单」**。本人**实测复核**：

| 步骤 | 结果 |
| --- | --- |
| 删掉 `0.0.0.0/1` + `128.0.0.0/1` → `AclEntries` 空 | `AclEnable=true`（仍显示 true） |
| 空名单下沙箱直连 `curl --resolve …:443:8.220.143.202 https://<域名>/v2/` | **`http=401`** → 可访问 ✅ |
| 还原两条 `/1` | `AclEntries=[0.0.0.0/1, 128.0.0.0/1]` |

结论：真正拦路的只有**预置的 `127.0.0.1/32` 占位条目**（`AclEnable=true` + 名单非空 = 白名单模式，只放行名单内）。
「删光条目」是官方全放行口径；push.sh `--allow-ip all` 仍用两条 `/1`（**非破坏性**，不清别人加的条目），两者功能等价。

## 19:45–20:05 · 排障：构建报 `ResourceExhausted … no space left on device` + Dockerfile 加 cache mount

**症状**：本机 `push.sh` 构建 6m24s 后失败
`ERROR: failed to build: failed to solve: ResourceExhausted: failed to open writer: mkdir /var/lib/docker/buildkit/content/ingest/<hash>: no space left on device`

**根因（实测）**

| 检查 | 值 |
| --- | --- |
| `settings-store.json` → `DiskSizeMiB` | **16384（16 GiB）** ← 上限过小 |
| VM 内 `df -h /`（alpine 探针容器） | 15.6G 总 · 8.0G 已用 · **6.8G 可用** |
| `docker system df` | Images 2.338GB · Volumes 2.27GB · Build Cache 684.8MB（可回收 652.7MB） |
| `Docker.raw` | apparent 16G（= 上限）· 宿主实际 5.9G（稀疏） |
| macOS 宿主 `/System/Volumes/Data` | 192Gi used · **13Gi avail（94%）** |

结论：**虚拟盘上限 16 GiB 太小** —— 构建峰值（bun 前端 + Go 编译中间层，通常 4–8 GiB）叠加已用 8 GiB → 写 BuildKit ingest 时耗尽。

**已执行**
1. `docker buildx prune -af` → 回收 684.8MB，VM 可用 **6.8 → 8.4 GiB**（Build Cache 归零）。
2. `Dockerfile` 加 BuildKit cache mount（备份 `.workbuddy/backup/Dockerfile.bak_20260927_195859`）：
   - bun 阶段：`ENV BUN_INSTALL_CACHE_DIR=/root/.bun/install/cache` + `RUN --mount=type=cache,target=… bun install`
   - golang 阶段：`ENV GOMODCACHE=/go/pkg/mod GOCACHE=/root/.cache/go-build`，`go mod download` 与 `go build` 各加 `--mount=type=cache`
   - 效果：编译/模块缓存落 build cache（可 `buildx prune` 回收），不进镜像层 → 峰值磁盘下降 + 重复构建加速。
   - 前置探测：`oven/bun:1.4.0` 默认 **root**、`HOME=/root`、`BUN_INSTALL_CACHE_DIR` 未设（默认 `/root/.bun/install/cache`）。

**push.sh 本轮新增**
- `check_docker_disk()`（build 阶段前置）：读 `DiskSizeMiB` + `Docker.raw` + VM 内 `df`（alpine 探针）+ 宿主 `df`；`< --min-disk(默认4 GiB)` 告警并打印「清理/扩容/换构建机」三选一，`<2 GiB` 直接阻断，`6–8 GiB` 提示偏紧。
- `--prune`（构建前 `docker buildx prune -af`，仅缓存）、`--min-disk <GiB>`、`--skip-disk-check`。
- `diagnose_build_failure()`：`no space left on device`/`ResourceExhausted` → 磁盘水位 + 修复指引；`failed to authorize`/`dial tcp` → 拉取/网络；`returned a non-zero code` → RUN 逻辑。

**踩坑**
- `docker system df` 的 `Reclaimable` 带百分比后缀（`652.7 MB (95%)`）不好解析 → 直接展示原文。
- VM 内剩余空间**无 CLI 直读接口**，只能起探针容器 `df`（加 `--pull=never` 防意外拉取）。
- `Docker.raw` 的 `ls -l` 是 apparent size（恒等于上限），`du` 才是宿主真实占用 → **不能**用 apparent 判水位。
