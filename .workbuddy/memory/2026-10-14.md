## 11:2x–11:4x｜disk_init 显式化可行性取证 + 修正上条口径

**问**：不做缩容，能否把 `disk_init` 空值补成显式配置？

### 一、先纠上条的两处不准确

1. **`disk_init` 不是"空数组"，而是 API 从不返回该字段**（`DescribeClusterNodePoolDetail` 的 `scaling_group` 44 个字段里没有它；但 `Modify/CreateClusterNodePool` 的**入参**支持它）。
2. **降容评估口径偏低**：数据盘**同时 bind 承载 `/var/log/pods`**，应看整盘 used。实测 **7.9 GiB / 290 GiB = 2.7%**（非 imageFs 的 4.4–4.8 GiB）⇒ 降 100G 后 ≈ 8.2%（≈12 倍余量，结论不变，数字已修正进成本表）。

### 二、挂盘到底是谁做的 —— 实测溯源

- `kubernetes_config.user_data` = **nofile 调优脚本**（任务 11 Step 3，句柄数），**与挂盘无关**；`pre_user_data` 空。
- `/var/log/ack-deploy.log` 中 **`[step=diskinit]`**（代码 `auto_disk.go`）：
  `udevadm info --query=symlink --name=/dev/nvme1n1` → `sed -i '\|…|d' /etc/fstab`（**先删同项，幂等**）→ `mount /dev/nvme1n1 /var/lib/container/` → `mount -a`
- 落盘 `/etc/fstab` 四条：数据盘 UUID→`/var/lib/container`(ext4)；bind `/var/lib/kubelet`、`/var/lib/containerd`、`/var/log/pods`
- `lsblk`：`nvme0n1` 100G（系统，三分区）/ `nvme1n1` 300G（数据，`/var/lib/container`）

⇒ **结论：ACK 内置引导步骤自动完成，属产品基线行为**，6 台节点一致。

### 三、若要显式化：契约与风险（OpenAPI meta）

`DiskInit`：`disk_name`（**必填**，且必须与 `data_disks[].disk_name` 匹配）· `mkfs_type`（留空=不格式化）· `mount_target`（留空=不挂载）· `mount_for_runtime`（容器运行时数据存该盘）· `local_disk`。
⚠ 现状 `data_disks[0].disk_name = null` ⇒ 要配 `disk_init` **必须同时给数据盘命名**。
⚠ `mount_target` ↔ `mount_for_runtime` 组合语义**官方无文档**。
⚠ `scaling_group` 传参增量/全量**未文档化**（最坏清空其他字段 → 影响下次扩容，但**不影响存量节点**）。

**官方生效范围**（原文）：「节点池编辑过程中不会影响节点池内已有节点和业务的运行……**不会修改节点池已有节点的配置，仅作用于新增节点**」⇒ **改 disk_init 不会重建存量 6 台**（会滚动重启 kubelet 的是另一个接口 `ModifyNodePoolNodeConfig`）。

### 四、结论：**不建议补（收益为负）**

现状不是缺陷 —— ACK 的 diskinit 是受支持的基线路径。补配置 = 从"ACK 默认"切到"按我给"，而关键参数语义无文档 ⇒ **写错会让新节点 containerd 落 100G 系统盘，重演任务 11 坑 3 的 disk-pressure 雪崩**。若确要显式化，**必须与「新建 1 台节点灰度验证」绑定**（mnl ASG min4/max8 现有 4 台，可临时扩 1 台，成本 < $1；或先在 dev 集群验证语法）。

**落点**：`gen_cost_table.py` 降本行修正（整盘 7.9 GiB + 「挂盘由 ACK 内置 diskinit 完成，无需改 disk_init」）→ `--apply`（备份 `cost_20261014_112727_*.md`）；REFERENCE 加「ACK 数据盘挂载机制与 disk_init 显式化评估」节；MEMORY 修正 `disk_init=[]` 记法。
**取证**：`deploy/logs/t_diskinit_{pool,ud,meta2,node,trace}.sh`。
