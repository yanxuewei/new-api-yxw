**阿里云 RAM 关键实测结论（可长期复用）**：
1. **`BoolIfExists` 与 `Null` 条件算子阿里云不支持** → 报 `The condition operator 'IfExists/Null' is not supported`，只能用 `Bool`。
2. **强制 MFA 的策略写法必须用 `Deny NotAction`**，且 NotAction 要白名单放行 `ram:CreateVirtualMFADevice`/`DeleteVirtualMFADevice`/`BindMFADevice`/`UnbindMFADevice`/`GetUserMFAInfo`/`ListVirtualMFADevices`/`GetUser`/`GetLoginProfile`/`UpdateLoginProfile` 等。否则 `Deny *` 会把绑定动作本身挡掉 → **用户永远绑不上 MFA，账号直接锁死**。同理，其他策略里的 `Deny ram:*` 会覆盖该白名单，必须移除。
3. **`acs:MFAPresent` 对 AccessKey 调用完全无效**（探针实测 3 次全通过）。AK 调用时该键不存在，`Bool` 不匹配，而 `BoolIfExists` 又不支持 → **纯策略手段无法对 AK 强制 MFA**。MFA 兜底策略只约束控制台会话。程序用户的 API 侧管控**只能靠 IP 白名单**。
4. **`acs:SourceIp` + `NotIpAddress` 条件对 AK 调用有效**（探针实测：白名单外 IP 调 `ram:ListUsers` 被拒；`sts:GetCallerIdentity` 豁免，不受影响）。
5. **RAM 高频写操作会间歇返回 `NoPermission`**（不是 `Throttling`，无任何限流提示），冷却 20–60s 自动恢复。自动化必须退避重试，否则误判为权限配置错误。本次触发 3 次。
6. 截图文档里的条件键 `acs:RAMMFAPresent` 是错的，正确为 **`acs:MFAPresent`**。
7. 「要求所有控制台用户绑定 MFA」的全局开关**无 OpenAPI**，只能用 `CreateLoginProfile --MFABindRequired true` 逐用户强制。
8. `aliyun configure set` **不支持 `--output` 参数**；创建 profile 后必须保证 `config.json` 的 `current` 指向存在的 profile，否则所有命令报 `load current configuration failed`。
9. 多凭据并存时**用 `--profile <name>` 才能确定身份**：`ALIBABA_CLOUD_ACCESS_KEY_ID` 环境变量存在时，`sts GetCallerIdentity` 仍可能返回 profile 身份，无法据此判断实际使用者。验证权限必须用独立 profile。

### 5 条可长期复用的阿里云 OSS 实测结论

1. **双可用区地域的 ZRS 桶只能存标准存储，不能降冷**。官方原文 "dual-zone ZRS is supported only for the Standard storage class"。马尼拉仅 6a/6b（双 AZ）→ 配 IA/Archive 转换报 `400 InvalidArgument: Invalid StorageClass`；同一规则在 LRS 桶上成功。ZRS 的 IA/Archive 仅多可用区地域（新加坡等）提供。**冗余类型创建后不可改**。
2. **Bucket Policy 的 `acs:PrincipalArn` 条件键被接受但不执行**。实测：无条件 `Deny oss:*` 生效（连 bucket owner 一起拦）；`Deny` + `StringNotEquals acs:PrincipalArn` 对非 owner RAM 用户完全无效。→ 主体管控只能走 RAM 身份策略。另：`acs:SourceIp` 单独使用被拒（`acs:SourceVpc should be set if acs:SourceIp is set`）。
3. **CRR 的 SyncRole 必须是 OSS 服务关联角色** `acs:ram::<uid>:role/aliyunosssystemdefaultrole`。自建普通角色（即使信任策略 `Principal.Service=oss.aliyuncs.com` + 权限策略挂全）不会被 AssumeRole，**规则状态正常显示 doing、进度无报错，但零对象复制** —— 静默失败。该角色可用 `ram CreateRole --RoleName aliyunosssystemdefaultrole` 直接建，未被保留名拦截。
4. **CRR 其它硬约束**：`Destination/Location` 必须带 `oss-` 前缀；`SyncRole` 必须在 `<ReplicationConfiguration>` 层级（放 `<Rule>` 内报 `contains some illegal characters`）；源/目标版本控制状态必须一致；删除规则后状态 `closing`，约 90–180s 内无法重建（`BucketReplicationAlreadyExist`），需退避重试。
5. **桶名全局唯一，删除后会被他人抢占**。`oss-newapi-sgp` 删除后重建报 `BucketAlreadyExists` → 改用 `oss-newapi-backup-sgp`。

### ⚠️ zsh 变量修饰符坑（本轮导致 3 次错误结论，务必记住）

写 JSON 时 `"acs:oss:*:$ACC:tmp-lrs-probe/*"` 中的 `$ACC:t` 被 **zsh** 当作参数修饰符 `${ACC:t}`（tail）求值，落库 Resource 变成 `5108890064395960mp-lrs-probe/*`（少一个 `t`）→ 策略永不匹配，一度误判「Bucket Policy 完全不生效」。同类：`:r` 去扩展名、`:u` 转大写。
**规避**：拼接含冒号字符串一律用 `${ACC}` 花括号，或改用 Python 生成 JSON。

5. **`vpc DeleteVSwitch` / `ecs DeleteInstance` 的资源存在性校验先于鉴权** → 返回「资源不存在」而非 AccessDenied → **不能用不存在的资源 ID 做权限探测**。
6. **权限探测脚本严禁用文本子串判定**：`actiontrail LookupEvents` 返回的审计事件正文含 `AccessDenied`（正是测试自身产生的事件）→ v1 判定器误判 DENY。必须按结构化字段（JSON 顶层 `error_code` / XML `<Code>` / ossutil `Error Code: Xxx.`）判定，并忽略业务成功码（`Code: success`、`IsSuccess:true`）。
   - 另：**ossutil 错误走 stderr，是纯文本不是 XML**；`cms DescribeMetricList`、`vpc DescribeRouteTables` 等读 API 仍有必填参数，不能当"无参读"用。

**代价**：云 API 层生产变更只能走 `iac-terraform`（IaC）；K8s 层 kubectl 运维不受影响（走 RBAC）。
