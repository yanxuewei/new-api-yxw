## dev 环境关闭 Passkey 登录（dev.likha.hk，jkt dev）

**诉求**：启用 passkey 后登录失败，要求从数据库关掉该功能、解除 passkey 登录。

**定位**：
- 开关在 `options` 表，键 **`passkey.enabled`**（`setting/system_setting/passkey.go:147` `config.GlobalConfig.Register("passkey", …)`，
  前缀 `passkey.` + json 字段名）。
- dev 库：`postgres://newapi_migrate:***@pgm-d9j9p421lzx4gw73.pgsql.ap-southeast-5.rds.aliyuncs.com:5432/newapi?sslmode=require`
  （Secret `new-api-secrets` 的 `SQL_DSN_MIGRATE`；日志库另一条 `LOG_SQL_DSN` 指向 `/newapi_logs`，走 6432 池）。
- 库内现状（改前）：`passkey.enabled=true`、`rp_id=dev.likha.hk`、`origins=http://localhost:3000,https://dev.likha.hk`、
  `legacy_rp_ids=localhost`、`rp_display_name=LikhaPasskey`；**`passkey_credentials` 0 行**（没人注册过凭证）。
  用户表：admin(role100) / xiangdong(role1) / yxw(role10)，均有密码。

**做法**：
1. 节点/业务 Pod 都**没有 psql/mysql 客户端**；集群可拉 `postgres:16-alpine`（`crictl pull` 实测 OK）。
2. 在 `newapi-dev` 起一次性 psql Pod（DSN 从 Secret 注入），执行
   `UPDATE options SET value='false' WHERE key='passkey.enabled';` → `UPDATE 1`。
3. **不需要重启**：`main.go:115 go model.SyncOptions(common.SyncFrequency)` 每 60s 重载 options（`SYNC_FREQUENCY` 默认 60）。
4. 验证：`curl https://dev.likha.hk/api/status` → **`passkey_login = False`**（`controller/misc.go:118`），`/sign-in` 200。

**产出**：`deploy/ops/dev_disable_passkey.sh status|on|off`（幂等，改完自动等 90s 并回读 `/api/status`）。
**回滚**：`bash deploy/ops/dev_disable_passkey.sh on`（或直接改库 `UPDATE options SET value='true' WHERE key='passkey.enabled';`）。
**注意**：passkey 的 rp_id/origins 配置行**保留**（未删），重新启用只需把开关翻回 true。

## 10:0x · 登录 429（RateLimit）排查与清理

**现象**：passkey 关掉后登录仍报 `Request failed with status code 429`。

**根因**：`POST /api/user/login` 挂了 `middleware.CriticalRateLimit()`（router/api-router.go:79）——
阈值 `CRITICAL_RATE_LIMIT=20 次 / CRITICAL_RATE_LIMIT_DURATION=20*60 秒`（common/init.go:131-133），
键格式 `rateLimit:v2:ip:CT:<clientIP>`（middleware/rate-limit.go:15/44，Redis 启用时落 Tair dev db `/0`）。
排查 passkey 期间反复点登录 → 把自己的 IP 打进限流窗口（TTL 剩余 ~1198s）。

**处置**：
1. 集群内起一次性 `redis:7-alpine` Pod（REDIS_CONN_STRING 由 Secret 注入），`--scan --pattern` 找到
   `rateLimit:v2:ip:CT:194.56.225.46` / `:14.155.111.126`，while 循环 DEL 掉；顺手清 `rateLimit:v2:user:UC:security-verification:*`（admin=user 1、yxw=user 3 的二次验证限流）。
2. 服务端日志佐证：`09:01:32–09:02:05`（Jakarta, =HKT-1）三次 `POST /api/user/login` 返回 **429**；
   **09:04:16 / 09:04:23 已返回 200**，09:04:40 `GET /api/option/` 200 ⇒ 会话已建立。
3. 复核：`curl -X POST /api/user/login`（假凭据）→ **200** + `{"message":"Username or password is incorrect..."}`（不再是 429）。

**沉淀**：
- IaC `deploy/ops/dev_clear_ratelimit.sh status [IP] | clear <IP> | clear-all`。
- 坑：`xargs` **不能**调用 shell 函数（`xargs: rc: No such file or directory`）⇒ 统一 `while read`；已在脚本内修掉。
- 坑：`ack_remote_jkt_dev.sh` 的 body **在节点上执行**，不能引用 `/mnt/e/...` 仓库路径 ⇒ 逻辑必须内联。
- 教训：调试登录类问题不要连点——CT 限流 20 次/20 分钟，一次错误密码也会计数。

## 14:xx · Windows 弹窗「没有文件扩展".vbs"的脚本引擎」修复

**现象**：每隔一段时间弹出 Windows Script Host 报错框。

**根因**：Notepad3（`C:\Program Files\Notepad3\Notepad3.exe` v7.26.602.1）安装时在
`HKCU\Software\Classes\.vbs` 写入用户级覆盖，把默认关联从 `VBSFile` 改为 `Notepad3_assoc.vbs`。
HKCU 优先级高于 HKCR，WScript 找不到脚本引擎，每次 `\Microsoft\Windows\NetTrace\GatherNetworkInfo`
任务触发（调用 `%windir%\system32\gatherNetworkInfo.vbs`）就弹窗。

**修复**：
```powershell
Set-ItemProperty -Path "HKCU:\Software\Classes\.vbs" -Name "(default)" -Value "VBSFile"
```
验证后 `HKCU\.vbs = VBSFile`，`HKCR\.vbs = VBSFile`，`VBSFile\Shell\Open\Command = WScript.exe "%1" %*`。

**注意**：Notepad3 v7.26 的 ini（`%APPDATA%\Rizonesoft\Notepad3\Notepad3.ini`）无 FileAssoc 段，
没有 UI 管理文件关联——重装 Notepad3 时可能再次写回，届时重跑上述命令即可。
