**通道 = `aliyun arms GrafanaWorkspaceHttpApiProxy`**（RPC，`--GrafanaWorkspaceId` + `--RegionId` + `--OrgId` + `--BodyStr`）。
- **`BodyStr` 结构**（权威，来自官方 API 文档）：**就是被代理的 Grafana 请求本身**，不是包装对象：
  `{"method":"GET","path":"/api/datasources"}`
  可选 `url`（与 path 二选一）、`queryParams`、`headers`、`body`。
  ⚠️ **`body` 必须是转义后的 JSON 字符串**（不是嵌套对象）；POST 必须显式带 `Content-Type: application/json`。
  ❌ 我曾误写成 `{"q1":{"_method_":"GET",...}}` → 报 `601 method is not supported:`（method 解析为空）。
- **两个必踩坑**：
  1. **调用者必须先加入工作区**，否则任何路径报 `40300 sub account is not authorized on this workspace, operateUserId:<uid>`。
     → `CreateGrafanaWorkspaceAccount --AliyunUid <RAM用户UserId> --Role Admin --OrgId 1`（RAM 用户 UserId 取自 `sts GetCallerIdentity` 的 `UserId`/`PrincipalId`）。
     ⚠️ **`UID` 是 bash 只读变量**：脚本里 `UID=...` 静默失败（`readonly variable`）→ 建出 `aliyunUid="0"` 的空账号（accountId=1118，已删）。**务必换名（RAMUID）**。
  2. **代理有路径白名单**：`/api/health`、`/api/ds/query` → `40300 proxy path is not allowed`；
     可用：`/api/datasources`、`/api/datasources/uid/<uid>/health`、`/api/dashboards/db`、`/api/dashboards/uid/<uid>`、`/api/search`。

## RAM 策略 v3 扩展 + ACK 集群 RBAC 核验（daimingming 控台权限）

### 触发
用户反馈 RAM 用户 `daimingming`（`218577891456544282`，属组 `ops-prod_group`）：① 控制台看不到 **SSL 数字证书 / Tair（兼容 Redis）**；② ACK「无状态应用」报 `APISERVER.403 deployments.apps is forbidden`。

### ★ 核心认知：**两套互不相通的授权体系**
| 体系 | 管什么 | 报错长相 |
|---|---|---|
| RAM 策略 | 能否调 OpenAPI（控制台的 API 面） | 控制台「无权限查看」 |
| K8s RBAC | K8s 里能否 list/get/update 资源 | `APISERVER.403 … is forbidden: User "<uid>" cannot list resource "deployments"` |

### ① RAM 策略 `newapi-ops-operator` v2 → **v3**（已发布并设为默认）
- 原 v2 Allow **既无 `kvstore:*` 也无 `yundun-cert:*`**，且**正文只存在于控制台、无 IaC**。
- v3 新增 Allow：`kvstore:*` `hdm:*` `yundun-cert:*` `arms:*` `clickhouse:*` `quotas:*` `resourcemanager:Get*|List*` `ram:Get|ListResourceGroup*` `tag:Get*|List*|Describe*` `*:ListTagResources` 等。
- v3 新增 Deny：`kvstore:DeleteInstance`（与 `rds:DeleteDBInstance` 同口径，**本次唯一收紧项**）。
- 核验：`VERIFY=PASS`；`AttachmentCount=3`；链路 `daimingming→ops-prod_group→DefaultVersion=v3` ✅；描述已用 `UpdatePolicyDescription` 同步。

### ★ 前缀必须逐个核准（凭记忆写会静默失效）
`kvstore`(Tair) · `hdm`(DAS) · **`yundun-cert`(数字证书/原SSL)** · `clickhouse`(CK) · `quotas` · `resourcemanager` · `tag` — 全部取自系统策略正文（`AliyunKvstoreFullAccess`/`AliyunHDMFullAccess`/`AliyunYundunCertFullAccess`/`AliyunClickHouseFullAccess`/`AliyunQuotasFullAccess`/`AliyunTAGReadOnlyAccess`）+ 官方《RAM用户使用资源组》只读示例。**证书服务只有 `yundun-cert` 一个前缀，无 `cas:`/`ssl:`。**

### ② ACK 集群 RBAC（**本次未动，用户已自行完成**）
实测 `DescribeUserPermission`（⚠️ **该 API 不分地域**，一次返回该用户全部集群授权）：17:21 仅 SG 一条 `ops`；**17:24:59 变为 3 集群全 `admin`** ⇒ 403 已解除。**未执行 RBAC 写入**，避免降权。

### ★★ 两条 ACK API 语义坑（已固化进脚本护栏）
1. **`cs GrantPermissions` 是全量覆盖**（"overwrites all existing cluster permissions"）⇒ body 必须列出要保留的**全部**集群，否则抹掉其它集群授权。脚本 `apply` 改为「读现状→原样保留所有集群→只改角色」。
2. **防降权护栏**：目标角色低于现状（admin→ops）时 `apply` **直接拒绝**，需显式 `ALLOW_DOWNGRADE=1` —— 本次正因此挡住一次误降权。
3. 请求体字段 = `{cluster, role_name(预置角色名), role_type(cluster|namespace|all-clusters), namespace?, is_custom, is_ram_role}`；**响应**里预置角色名落在 `role_type`、`role_name` 为空 —— **请求/响应字段名不一致，勿互相套用**。
4. ⚠️ **`UID` 是 bash 只读变量**（root 下=0）—— 脚本里用它作变量名会静默取到 0，建出空授权。本脚本用 `RAM_UID`。
