## 结论摘要

方案整体骨架（双主站 + 单备 region、取消 DTS/双写、RDS 单主库、ACK Pro + 多 AZ + PDB）方向正确，**但存在 5 个会导致 SLA 目标不成立的架构级缺口、18 个实施前必须补齐的漏项，以及 19 处排期与数据错误**。其中 3 项在 D1 就会阻塞：

1. **T-3 前置期实际是 0 天**（B19 = B20 = 2026-09-22），而 G0 门禁依赖的实名认证（1–2 工作日）、配额审批（2–3 工作日）、NS 生效（24–48h）**物理上不可能在 D1 前闭环** → 5 天工期从第一天起就不成立。
2. **备 region 容量只有主站点 50%**（PH 备 2 副本 vs 主站 4 副本），而设计文档明确要求"备 region 单站点全量接管 × 1.5"。
3. **SLA 99.95% 依赖的 4 项代码改造零人时零任务**（/healthz、/readyz、/metrics、限流降级），80 人时全部是部署工时。

## 一、P0：架构级问题（不改则目标不成立）

### P0-1 备 region 容量与接管能力要求不匹配 → SLA 链条断裂

| 项 | 内容 |
| --- | --- |
| 现状 | 资源清单-新加坡 #8「ECS 节点池 ≥ 2，PH 备 2 副本」；落地计划 #28「PH 备 replicas=2」；**备 region 无 HPA 配置、无节点池自动伸缩** |
| 文档要求 | `impl_deploy.md:1012`「新加坡备 region 必须具备单站点全量接管能力（PH 备 + TH 备的可扩容上限 ≥ 被接管站点峰值 × 1.5）」；`:999`「DNS 切到新加坡备 region（容量已预留 1.5 倍）」 |
| 影响 | 2 副本 = 主站点 4 副本的 50%。`impl_deploy.md:970` 的「网关数据面 99.99%」正是建立在「≥4 副本跨 2 AZ」之上；接管期容量腰斩将出现大面积 5xx，99.95% 不成立 |
| 建议 | 明确备 region 常态副本数 + 峰值扩容路径（HPA + cluster-autoscaler 或 ACK 弹性节点池 + 预留规格），并把「接管容量压到 1.5× 峰值」写入 M4 验收 |

### P0-2 HPA 上限与配额矛盾，且缺文档已明确要求的 PgBouncer

| 项 | 内容 |
| --- | --- |
| 现状 | 资源清单-马尼拉 #12「HPA min 4 / max 16」；账号表 #7 配额申请「ECS vCPU ≥ 64（马尼拉）」 |
| 冲突 1 | 16 副本若按 1 副本/节点铺开需 128 vCPU > 64 配额；且**无 cluster-autoscaler**，HPA 扩到 16 会 Pod Pending |
| 冲突 2 | `impl_deploy.md:1014` 明确「主站点扩到 16 实例时**必须配 PgBouncer（或 RDS 代理）**，否则 4,800+ 连接会打爆 PG」——xlsx 资源清单 29 项、落地计划 39 项、门禁 G1–G9 **全无此条目**，主站点 `SQL_MAX_OPEN_CONNS` 也未给值 |
| 建议 | 三件同时补：① 节点自动伸缩（或把 HPA max 与节点数/配额对齐）② PgBouncer / RDS 代理资源条目 + YAML + 落地任务 ③ 按 `impl_deploy.md:1014` 公式填出连接数预算表 |

### P0-3 上游 IP 白名单与 GA 的角色矛盾 → 上游调用可能被拒

| 项 | 内容 |
| --- | --- |
| 现状 | B11「马尼拉 / 新加坡 NAT 固定 EIP 池 → 全球加速 GA → OpenAI…」；资源清单-马尼拉 #5 备注「用于供应商白名单与 GA 回源」；网络与安全规划 EIP 区块备注「提交给 OpenAI/Anthropic/Google 做 IP 白名单」 |

| 附带 | GA 在资源清单（马尼拉 29 / 新加坡 18）、产品开通（账号表 #8–#12）、落地计划（39 项）**全部缺失**；`impl_deploy.md:940` 也只写"建议…对上游出口走 GA"（建议态，非既成态） |
