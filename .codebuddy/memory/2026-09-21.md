## 区域级 ALB 故障 + 切区登录分析（追问梳理）

- ALB 故障粒度：单实例/单 AZ → ALB 每区域 2 个且多 AZ，流量走同区另一 AZ，近零影响；整区 ALB 全挂 → GTM（15s 探测）切到另一区，指标「故障切换 ≤60s」（7.2）/「整区域故障 RTO ≤5min」（8.4）；切换后 PH 用户 RTT 5–15ms 劣化到 60–90ms，BKK 按 1.5 倍容量预留可扛全量（8.5）。
- 但已建立的 SSE 长连接救不回（DNS 切换只影响新连接）；文档未给 DNS TTL 值，客户端 DNS 缓存可能把恢复时间拖长；ALB「假可用」（SSE 被 idleTimeout 掐断但 HTTP 探测通）不会触发切换 → 所以 7.4.3 强制网关 ping 心跳 15–20s。
- 切区后登录能力（核对 `docs/authentication.md` 后确认）：
  - Session 权威在**主库表 `user_sessions`**，Redis 只是缓存（TTL = min(剩余寿命, SYNC_FREQUENCY=60s)，未命中/无 Redis 时回源 DB）。MNL↔BKK 主库 DTS 双向增量同步（2 链路、冲突检测、延迟告警 >5s）→ BKK 有 PH 用户完整认证数据，能登录、令牌可用。
  - `SESSION_SECRET` 派生 Access Token JWT 密钥、Refresh Token HMAC 摘要、Security Proof、AuthFlow 摘要 → **跨区域不一致会导致全部会话失效**（需重新登录，非不可登录）。
  - 两区域 Redis（Tair）互相独立 → Session 缓存冷启动回源 DB，非致命；限流计数各算各的，短暂超额。
- 三个文档未覆盖的真实缺口（判断切区是否"纸面可用"的关键）：
  1. **备用区域 Ingress host/TLS 未给出**：7.4.3 只配了 `api.example-ph.com` + 对应证书；GTM 把该域名切到 BKK 时，BKK 的 ALB/Ingress 必须接纳同一 host 与证书，否则是 404/证书错误而非降级可用。
  2. **DTS 冲突解决策略未定义**（只写"冲突检测"），双主可写的写-写冲突无规则。
  3. **DB 租约去重前提被破坏**：1.2 的"定时任务用 DB 租约去重 → 多实例安全"假设**单库多实例**；双区域双主库各自可写时，两区 master 各读自己库的租约表，失去全局互斥，可能重复执行清理/结算。计费的 `request_id` 唯一索引也是库内约束，跨库需 DTS 兜底，须实测。
  - 数据陈旧窗口约 5s（DTS 告警阈值）：切换前刚写的 session 行/改密/撤销可能在 BKK 未生效。

## 三项缺口核实报告（产出 `impl_deploy_review.md`）

- 核实结论：`impl_deploy.md` 的「双库可写 + DTS 双向同步」方案，与应用侧所有互斥/幂等机制（DB 租约、唯一索引、行锁、CAS）的**单库作用域**不匹配，产生三个高severity 缺口，仓库代码级确认。
- 缺口一（备用区域入口）：仓库**不存在任何 K8s/ALB 清单**（`*.yaml` 仅 `web/cz.yaml` + i18n；`*.yml` 仅 docker-compose 与 .github）。文档中唯一 Ingress 是马尼拉的 `api.example-ph.com`（`impl_deploy.md:402-451`），曼谷侧 host/TLS 完全缺失；且文档内部矛盾（7.4.1 双域名 vs 7.5 单域名）。GTM 切区不改 Host/SNI → 证书错误或 404，且 GTM 探测通过不告警 = 静默全损。修复：两区域 Ingress 声明同一 host 集合 + SAN 互认证书（或改单域名 + GTM）；应用层无需改动（`SESSION_COOKIE_TRUSTED_URL` 已列双域名）。
- 缺口二（DTS 冲突策略）：文档仅「冲突检测、延迟告警 >5s」，无胜负规则。代码内幂等键全为库内：`model/subscription.go:1240` request_id uniqueIndex、`:1312-1318` 事务查重、`:1408` lockForUpdate、`model/system_task.go:30,33` uniqueIndex、`model/task.go:533-539` CAS（注释明确只对「同一数据库内的另一个进程」有效）。修复：显式选定 DTS 冲突策略写入文档；或改单向同步消除双写；幂等键加区域前缀全局化；**必须新增跨区对账任务**。
- 缺口三（DB 租约跨区失效，证据最硬）：`model/system_task.go:43-49` SystemTaskLock 主键 = Type（每库一条锁）；`:313-352` acquireSystemTaskLock 全为单库 INSERT/条件 UPDATE；`service/system_task.go:125-127` 仅 master 启动 runner；`common/init.go:89` `IsMasterNode = NODE_TYPE != "slave"`，而 7.4.2 要求每区域各一个 master → 同一任务两区同时跑。受影响：`channel_test`（渠道被测两遍、上游额度翻倍）、`model_update`（可能各自自动应用）、`midjourney_poll`/`async_task_poll`（15s，各自结算）；另有 `service/auth_cleanup.go:15-21`、`service/subscription_reset_task.go:29-35`（订阅重置绝对值写）、`service/codex_credential_refresh_task.go:35-39`、`service/authz/enforcer.go:34,57` 同样双份。结算 CAS 保护不足：`service/task_polling.go:596-620` 的 `UpdateWithStatus` 只在单库仲裁。修复：R3-1 部署层只让一个区域跑 master（`replicas: 0` + runbook）；R3-2 代码层锁表主键改 `(Scope, Type)` + active-region 开关（注意 SQLite 不支持 ALTER COLUMN，需按 AGENTS.md 三库验证）；R3-3 长期需引入跨区域仲裁点。
- 连带发现：日志库 ClickHouse 每区域独立、不参与 DTS（切区后用量明细「看起来丢失」）；`model/usedata.go:19-25` QuotaData 带 node_name 维度 → 双区写两行不双倍但分裂；Redis 限流按区域独立计数。

## 面向「99.95% 不断服 + 计费误差 <0.001」的方案修订（产出 `impl_deploy_fix.md`）

- 用户新标准：A1 新请求切换期不断服（100% 成功）/ A2 断流后 ≤15s 恢复且不重复计费 / A3 零配置型全损；C1 重复扣费与漏扣 = 0 笔 / C2 误差率 <0.001（小时窗口，月取最大）/ C3 故障后 1h 内收敛。
- **新增发现 H5（最致命）**：`BATCH_UPDATE_ENABLED=true` 时额度变更只写进程内存 `batchUpdateStores`，`BATCH_UPDATE_INTERVAL` 默认 5s（`common/init.go:111`）才 flush（`model/utils.go:35-42,44-63`）；入口在 `main.go:161-165`，条件分支在 `model/user.go:1340-1347,1390-1393`。进程被 kill / 区域故障 → 最多 5s 的扣费直接丢失，且各实例缓冲互不可见。修复：`BATCH_UPDATE_ENABLED=false`（直接落库的 `gorm.Expr("quota - ?")` 是原子增量，可重放）或降 interval+preStop flush。
- 修订方案核心：四条不变量 I1 单写者 / I2 可转移（epoch fencing，校验必须落到 SQL 的 WHERE 条件更新）/ I3 事实不丢（计费事实流，DTS 数据订阅 + after-commit 双写）/ I4 入口无 DNS 依赖（用 GA 终端节点组替代 GTM DNS 切换）。
- 关键设计决策：① 表分三类——分区表（按 `users.home_region` 单写，DTS 两条单向按分片过滤）/ 全局表（仅 global_owner 写）/ 区域本地表（日志、perf_metrics 不同步）；单写者使 DTS 双向不再产生写-写冲突（H3 根因是"同一行两个写入者"而非双向同步本身）。② 修 H4 用"全局任务只在 owner 跑 + 分区任务按 home_region 过滤轮询"，`system_task_locks` 主键改 `(Scope, Type)`。③ 最常态故障（ALB/Pod/AZ）只需改路由不改数据 → 应用无状态可远程写故障区 DB（+60–90ms），这是 A1+C1 同时成立的关键。④ 仅整区故障才 promote + 事实流回放。
- 分期：P0 纯部署（GA/证书/master 归零/batch 关闭/DTS 策略）2–3 人日；P1 小代码（REGION_ID、分区调度、锁表主键、只读对账）8–12 人日；P2 架构（分片列迁移、所有权 fencing、事实流、仲裁器）20–30 人日。
- 文档末尾给了「与 impl_deploy.md 的对应修订点」表（7.1/7.2/7.4.1/7.4.2/7.4.3/7.7/8.1/8.2/8.4/8.5/8.6），供后续合并。

## 新路线评估：单主 + 跨区 PG 复制（`impl_deploy_fix.md` 附录 A）

- 用户提出换思路：不双写、单写，PG 主库在马尼拉、备库经外网同步到新加坡。评估结论：**可行且明显优于双主路线**，但三个必改点：
  - M1 **必须 quorum 同步复制**，`synchronous_standby_names = ANY 1 (mnl_sync, sg_sync)`（PG 9.6+ 支持 quorum 语法）。本地同区副本承担 ack（<1ms，WAN 不参与）→ 常态提交延迟不受跨区影响；SG 断连完全无影响；本地副本故障才降级为 +30–45ms；两个副本都不可达时提交阻塞，需监控脚本临时置空 `synchronous_standby_names` 降级为异步（有意识的可用性优先取舍）。收益：**已提交事务在 SG 必有副本 → 整区故障 RPO=0 → 事实流与跨区重放不再需要**。
  - M2 **应用必须与主库同地**：跨区写延迟 = 语句数 × RTT。实测写路径语句数——`PreConsumeUserSubscription` 4–6 条（`model/subscription.go:1312-1394`）、`PostConsumeUserSubscriptionDelta` 2+ 条（`:1517-1522`）、`IncreaseTokenQuota` 1 条独立提交（`model/token.go:397-406`）、`DecreaseUserQuota` 1 条（`model/user.go:1397-1403`）→ 单请求约 6–12 次 DB 往返 → BKK 写 MNL 主库额外 330–960ms、SG 写 MNL 额外 180–540ms。⇒ 单主 + 双区域就近服务不成立。
  - M3 **禁止自动跨区 failover**（脑裂二选一：CP 会因链路抖动让主站点自杀、AP 会产生双写历史）→ 常态 DB 永不切换（只切应用路由）；区域级故障走人工/半自动 promote（需 GA 确认整区不可达 ≥5min + 复制链路已断 + 双人确认）；仲裁点只判定「允许 promote」，绝不强制 demote；Patroni 只用于同区高可用。
- 两种形态：
  - **形态 1 单服务区（推荐先做，1–2 周）**：主库 MNL + 同区同步备 + SG 跨区同步备，应用 MNL 热 + SG 热备，BKK 不部署应用。H3/H4/事实流/对账全部消失；代价是 TH 用户 RTT 55–80ms（与 1.3 的 TH ≤45ms 冲突）。
  - **形态 2 分片单主**：MNL 分片（PH 用户）+ BKK 分片（TH 用户）各自本地主库，互为对方只读副本，用户归属固定 → 每行单写者无冲突；应用需第二个 DSN 读对方副本，代码已有现成模式可照搬（`LOG_SQL_DSN` → `LOG_DB` + `common.UsingLogDatabase`，`model/main.go:230-256`）。跨区复制推荐**异步**（同步会给本地写加 30–45ms），区域故障走人工 promote + 对账补偿。
- 待向阿里云核实的 blocker：V1 RDS PG 是否允许外部跨地域物理从库（否则改自建 PG on ECS / PolarDB GDN / RDS 灾备实例）；V2 是否可改 `synchronous_standby_names`/`synchronous_commit`；V3 跨地域复制实际延迟与带宽。
- 配套配置调整（两形态通用）：`BATCH_UPDATE_ENABLED=false`；`SQL_MAX_LIFETIME` 60→600（跨区重连含 TLS 握手 2–3 RTT）；`SQL_MAX_OPEN_CONNS` 按单主库重算；只读副本承担报表/对账/管理查询。

## 阿里云官方文档核实：RDS 跨地域灾备实例（`impl_deploy_fix.md` 附录 B）

- **方向确认**：官方《一键容灾搭建》只支持「自建/其他云/阿里云 RDS → **阿里云 RDS PG 灾备实例**」单向；**不存在「RDS 作源 → 外部实例作物理从库」路径**。官方跨地域方案 = RDS→RDS 灾备实例。
- **目标实例（灾备）硬性要求**：大版本与源相同；必须是**主实例**（只读实例不支持）；按量或包年包月（Serverless 不支持）；**实例必须为空、无数据**且存储 ≥ 源数据总量（⇒ 首次搭建做全量初始化传输）。
- **源实例**：自建源需同步账号（`CREATEROLE REPLICATION LOGIN` + `pg_monitor`，必要时 `SUPERUSER`）+ `pg_hba.conf` 两行 `host replication`；**RDS 作源时这些由平台处理**（用户拿不到 superuser）。网络：跨 VPC 需**云企业网或公网 NAT 网关**。
- **搭建两步**：① 可行性评估（目标实例→一键上云/容灾搭建→可行性评估，填源公网地址/端口/同步账号，评估期目标实例变"维护实例中"）；② 容灾搭建（创建容灾关系→选评估任务；**「搭建阶段」显示"增量同步"即完成**）。管理仅两项：**重建容灾关系**（延迟/中断时）、**提升容灾实例**（源故障时一键提升为主库）。
- **对本方案的关键结论**：① 复制为**异步** → RPO>0，且 **M1（把灾备节点纳入 `synchronous_standby_names`）在 RDS 上不可实现**；② 灾备实例提升前不可写、文档未说能否承载业务读（待工单确认）；③ 提升是**人工流程**，RTO 分钟级，属 8.1 排除项②覆盖范围。
- **关键补充（方案可行的核心）**：RPO>0 的损失**可挽回**——多数情况原主库只是"不可用"而非"数据损毁"。故障切换 runbook 必须包含第 7 步**回捞**：MNL 恢复后从**原主库**导出 `T0` 之后的计费变更（`quota_data`、`subscription_pre_consume_records`、`users.quota` 快照、`tasks`），与 SG 库按 `request_id` 对账并幂等补齐 → 这是满足 C1（零漏扣）的决定性环节，成本远低于双主常态对账。
- 待工单确认 7 项：灾备实例提升前能否被业务连接/只读、一主可挂几个灾备、复制延迟有无 SLA 与观测口径、提升的 RTO 与连接闪断（SQL Server 版文档提约 10s，PG 版待确认）、提升后原主实例状态与回切步骤、计费构成、参数是否随主实例同步。

## 单区域方案评估（`impl_deploy_fix.md` 附录 C）

- 用户提出：牺牲泰国体验，PH/TH 共用 MNL 的 PG（主备只在 MNL）。结论：**可行，且是所有版本里最简单、最快达标的，代码零改动**。
- 关键认知：**双区域在 impl_deploy.md 里是为「TH 延迟 ≤45ms」而非可用性**；放弃该延迟目标后单区域在排除项口径下仍达 99.95%。
- 一个必须选对的形态（代价差 6–12 倍）：① ❌ BKK 也部署应用、跨区写 MNL 库 = 330–960ms 额外延迟（6–12 次写往返 × 55–80ms）；② ✅ **只在 MNL 部署应用**，TH 用户远程访问 = 一次请求往返 55–90ms。必须选 ②。
- 收益：H1（GTM DNS 切换）、H2（备用区域证书/host）、H3（DTS 冲突）、H4（双 master）**全部消失**；事实流/常态对账/跨区重放全部不需要；BKK 整套资源（ACK/RDS/Tair/CH/DTS/证书）全省；代码零改动。H5（`BATCH_UPDATE_ENABLED=false`）仍必须修。
- **发现文档算错**：`impl_deploy.md` 8.2 写「0.9999 × 0.9999 × 0.9999 × 0.9999 × 0.9999 ≈ 0.9996」，但 5 项实际 = **0.999500（99.95%）**，0.9996 是 4 项的结果 ⇒ 原方案把「刚好达标」误写成「有余量」。
- 单区域串联（GA/ALB/应用数据面/RDS HA/Tair，各 99.99%）≈ 0.99950 → 99.95%，**刚好达标但无余量**。因此把三项从「优化项」升级为「达标必要条件」：R-05 限流降级放行（现在 fail-closed 返 500）、日志写失败不阻塞中继、Tair 主备版 + 连接池超时按故障态配。任一项低于 99.99% 即破线。
- 建议保留**廉价异地冷备**：SG RDS 灾备实例（异步）+ SG 应用 `replicas: 0`，出事时提升 + 拉起 + GA 切流，分钟级恢复；否则须在 SLA/合同中写明区域级故障不赔付。
- 上游出口建议仍保留 SG 汇聚（MNL→SG +30–45ms 相对 LLM 时延可忽略，换来更好国际出口与固定白名单）；GA 可用于改善 TH→MNL 路径（需确认曼谷接入点并实测 RTT）。
- 三方案最终对比（附录 C.7）：C 单区域（数天上线/零代码/TH 55–90ms/区域故障全停或冷备分钟级）｜A 形态 1（1–2 周/极小改动/区域故障分钟级）｜A 形态 2 双主分片（1–2 月/20–30 人日/TH 就近/秒级自动）。

## 双栈 + 主库在新加坡方案评估（`impl_deploy_fix.md` 附录 D）

- 用户提案：PH+MNL 与「新加坡1」共用一个 PG（PG 位于 SG1）；TH+BKK 与「新加坡2」共用一个 PG（位于 SG2）。
- 关键澄清：**阿里云只有 ap-southeast-1 一个新加坡地域**，所以 SG1/SG2 只能是同地域内两套独立部署 ⇒ 两个主库在同一故障域。
- 三条致命问题：① 读法「MNL/BKK 应用 + SG 主库」= 跨区写 180–540ms（6–12 次写往返 × 30–45ms PH→SG）不可用；读法「只有 SG 跑应用」= PH 30–45ms，**同时破 1.3 的两条 KPI**（PH RTT ≤15ms、网关开销 P99 ≤80ms），而 TH 25–40ms 恰好达标。② **故障域未隔离**：两个主库同在新加坡 ⇒ 新加坡地域故障 = 双栈同时挂，故障域仍为 1 个地域，收益为零、代价为正。③ **合规方向变差**：PH/TH 用户数据出境到 SG，与数据本地化趋势相反（方案 C 把 PH 数据留在菲律宾更容易满足）。
- 值得保留的思想：「双栈隔离」（PH/TH 各自独立，故障/发布/容量互不影响）+「每栈两地域」+ SG 作国际出口与跨市场报表中心。
- **D 修正版（推荐）**：主库留在服务区（MNL/BKK 各自 RDS 高可用版，本地写 <1ms），SG 放**跨地域灾备实例（附录 B）+ 只读副本**跑报表，上游出口汇聚到 SG。**成本与原提案相同（4 个 RDS + 2 套 ACK），但延迟/故障域/合规三项全面更优。**
- 选型准则：PH/TH 是两块独立业务（各自结算运营）→ 选 D 修正版（两个独立栈）；同一套业务需统一后台与跨市场报表 → 选 A 形态 2（一套系统内按用户分片）；嫌 4 个 RDS 贵 → 退回方案 C（单区域 MNL + 一个 SG 冷备）。
- 一句话总结：**主库要跟着写的人走，灾备要跟着故障走，出口要跟着网络质量走**——原提案把主库放到了出口的位置。
